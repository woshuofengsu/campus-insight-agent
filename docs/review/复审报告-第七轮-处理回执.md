### 落地内容

1. **迁移 `_m46_phone_enc_and_schema_drift`**（`data/db_core.py`，注册进 post 列表 = 版本 46）
   - 加加密列 → 存量回填 `_enc_text(明文)` → 清空明文列；
   - **只在加密成功时清空明文**（加密异常则保留明文等下次迁移重试，绝不丢数据）；
   - 幂等：列用 PRAGMA 检查、回填只处理非空明文、重复跑不改写已有密文（有测试断言）。
2. **写路径**：`db_proposal.submit_proposal / save_draft`、`db_repair.create_draft`
   一律「明文列写空串 + 真号只进 `*_enc`」；
   **读路径**：`get_proposal / get_proposals / get_my_proposals / view_full_phone / get_draft(s)`
   解密回明文（展示层继续 `mask_phone` 脱敏，字段契约不变）。
   加解密复用 `db_repair._enc_phone/_dec_phone`（**单一实现**，不搞两套 crypto 调用）。
3. **账号注销**（`api_routes/auth.py`）：原来只清提案明文列，现补 `*_phone_enc`，并级联
   `proposal_drafts / issue_drafts` —— 否则「已注销」用户仍留可解密号码。
4. **`seed.py`**：已有密文却残留明文时一并清空（防回滚明文）。
5. **新增门禁**：
   - `scripts/audit_phone_encryption.py`：逐表体检「有没有加密兄弟列 + 明文计数」，退出码可当门禁；
   - `demo_preflight.py` 第 8 项**手机号加密覆盖**（现在自检 9 项）：现场 8 张含手机号表全部明文=0；
   - `tests/test_proposal_phone_encryption.py` 6 项：写入即密文（`g1$` 前缀）/ 读回原值 /
     全库明文计数=0 / 两张草稿表 / **迁移回填与幂等** / 非法号仍被拒 / 全新建库无缺口。
6. **迁移前已备份生产库**（`data/community_insight.db.bak_20260912_202902`），
   并额外写 `scripts/check_crypto_consistency.py` 验证 **13 条新密文与运行期密钥一致可解密**
   （加密类改动的头号事故是「密钥不一致导致存量数据解不开」，已验证：8 张表解密 3/3 成功）。
