## 3. 本轮新发现问题（按严重度排序）

> 结论先行：**无致命、无 P1/P2**。以下均为 P3，前两个建议现在就顺手收掉。

### F1（P3 · 安全加固）`serve_public.py:151-153` 默认绑 `0.0.0.0`，不开隧道也对整个局域网免密敞开
- **现状**：起服务用的是 `uvicorn api_web:app --host 0.0.0.0 --port 8000`。这意味着**即使你不加 cloudflared 隧道**，只要你电脑连在校园网 / 宿舍 / 公共 WiFi 上，同网段任何人扫到 `你电脑IP:8000` 就能免密进演示站（居民/老年免密、网格弱口令 demo123）。
- **为什么是问题**：cloudflared quick tunnel 是**本机出站拨号**，它只连 `127.0.0.1:8000`——所以把服务绑回环口，隧道照样能用，但局域网这条多余的暴露面就关掉了，属于"纵深防御 + 默认最小暴露"。
- **改法（改 `scripts/serve_public.py`，约 10 行）**：
  ```python
  # argparse 里加一个显式开关，默认不开
  ap.add_argument("--lan", action="store_true", help="同时对局域网开放（默认仅本机+公网隧道）")
  # start_server() 内 151 行：
  host = "0.0.0.0" if getattr(args_global, "lan", False) else "127.0.0.1"
  subprocess.Popen([sys.executable, "-m", "uvicorn", "api_web:app",
                    "--host", host, "--port", str(PORT)], ...)
  ```
  （把 args 传进 start_server 或用模块级变量即可。）隧道 `cloudflared tunnel --url http://127.0.0.1:8000` 无需改动。
- **验证**：默认起后 `netstat -ano | findstr :8000` 应只见 `127.0.0.1:8000` LISTEN；同网段另一台设备访问 `http://你IP:8000` 应不通，而公网 trycloudflare 链接仍 200（`probe_public.py` 8/8）。

### F2（P3 · 健壮性 / 体验）提案详情页对"不可议论阶段"的提案，打开就发 400 并误弹错误提示
- **复现（我已用真实 HTTP 复现）**：居民打开首个提案（id=189，处于不开放议论的阶段）时，前端 `GET /proposals/189/comments` 返回 **400 `code 1003「该提案暂不支持议论」`**。
- **根因**：后端 `api_routes/proposals.py:230-232` 规定居民仅当 `is_public 且 status ∈ {公示中,待执行,执行中,待提案人反馈,重新执行}` 才能取评论；而前端 `web/src/views/resident/ProposalDetail.vue` 的 `load()`（16–21 行）**不分阶段、无条件**请求 comments。虽然外层有 try/catch，但 catch 里是 `message.error(e.message)`——结果是**用户什么都没做错，只是打开一个提案，就被弹了一个红色错误 toast**，控制台同时留一条 400。
- **改法（`ProposalDetail.vue`，与后端白名单严格对齐）**：
  ```js
  const CAN_DISCUSS = new Set(["公示中","待执行","执行中","待提案人反馈","重新执行"])
  async function load() {
    try {
      p.value = await proposals.detail(route.params.id)
      comments.value = (p.value.is_public && CAN_DISCUSS.has(p.value.status))
        ? await proposals.comments(route.params.id) : []   // 不可议论阶段不发请求
    } catch (e) { message.error(e.message) }
  }
  ```
  议论输入框也用同一条件 `v-if` 门控（若模板还没门控的话）。
- **测试**：① 打开"草稿/待审核"提案 → Network 无 comments 400、无错误 toast；② 打开"公示中"提案 → 评论正常加载、可匿名发言；③ 加 1 条前端/接口测试覆盖"非议论状态返回空而非抛错"。

### F3（P3 · 打磨 / 确定性）暗色 class 在 `onMounted` 才挂，存在首帧闪烁，并让 ui_audit 偶发抓到"假对比度问题"
- **现象**：我第一次用**旧 dist** 跑 ui_audit 报 6 处，重新 build 后降到 1 处（暗色工单"处理结束" 2.96:1）。但我用 Playwright 等 211 行列表真正渲染完再测，同一个字实测是 **#6EE7B7（正确、高对比）**，body 上 `--ink-success` 也是 #6ee7b7。
- **根因**：`App.vue` 在 `onMounted` 里才 `theme.apply()`（给 body 加 `.dark`），而 Naive 的暗色是 JS 主题、两者生效差一帧；`main.js` 在 `app.mount()` 前没有先落暗色类。审计在这一帧采样，就会出现"Naive 已把卡片染暗、CSS 变量还停在亮色值"的瞬间 → 抓到 #047857（2.96:1）。真实用户看到的是一次极短的暗色闪烁（FOUC）。
- **改法（`web/src/main.js`，`app.mount` 之前加 4 行，挂载前先定类）**：
  ```js
  try { if (localStorage.getItem('ci_theme') === 'dark') document.body.classList.add('dark') } catch {}
  app.mount('#app')
  ```
  `App.vue` 的 `theme.apply()` 保留（切换主题仍以它为准）。这样首帧即暗色、无闪烁，ui_audit 也能稳定 0（不再靠采样运气）。
- **验证**：build 后连跑 2 次 `ui_audit.py`，`grid-workorders-dark` 对比度应为 0、结果稳定可复现。

### F4（P3 · 流程 / 工具）改完 `web/src` 不重新 build，审计和演示测的是旧包——本轮就真实发生了
- **现象**：我接手时 `web/dist` 构建于 18:39，但 `Issues.vue` 源码 19:21 还在改，**dist 落后于源码**；旧包里还打包着 `#374151/#4f46e5`，于是 ui_audit 报了 6 处——其中 5 处其实源码已修、只是没 build。我执行 `npm run build`（2.82s）后旧色值清零、违规降到 1（即 F3 的时序项）。
- **建议（双保险）**：
  1. 约定写进 AGENTS.md / 交付说明门禁：**任何 `web/src` 改动，必须先 `cd web && npm run build`，再跑 ui_audit / mobile_audit / demo_acceptance / 对外演示**；

### 观察项（不算缺陷，答辩/取舍时知道即可）
- **O1：PWA 是"可安装"、不是"可离线"。** 没有 service worker，所以"加到主屏幕 / standalone 全屏"成立，但断网不可用。**答辩时不要说"离线可用"**；业务本身强依赖后端，比赛阶段不需要离线。若想锦上添花，可加一个只缓存 app-shell（index/css/js，不缓存 /api）的极简 SW，约 30 行，非必须。

## 6. 答辩问答库（针对本轮新增面，5 问）

**Q1：你这移动端是不是就是 CSS 缩放一下？怎么证明真机好用？**
A：不是。我们做了一套真机口径的专项审计（iPhone UA、DPR=3、触屏事件、320–844、横竖屏），21 页查 7 类问题。举三个具体的：① iOS 对小于 16px 的输入框聚焦时会整页放大，我们在粗触屏设备统一把输入框设为 16px 根治；② 用 elementFromPoint 真测"滚到最底的内容会不会被固定底栏挡住"；③ 用 100dvh 带 100vh 回退解决 iOS 地址栏伸缩的高度跳变。21 页全部通过，并且我们用真实公网链接在自己手机上验证过。

**Q2：你说是 PWA，那断网能用吗？**
A（诚实）：manifest 让它可以"加到主屏幕、以 standalone 全屏类 App 方式运行"；但业务是强在线的接诉即办，数据必须实时走后端，所以我们**没有做离线缓存，也不宣称离线**——这是刻意的取舍，避免缓存到过期的政策/工单数据。要做离线只缓存界面外壳是可以的，已在路线图。

**Q3：你用公网隧道把系统暴露到互联网，安全吗？**
A：这是**临时演示隧道**，我们对它的边界非常清楚并做了三件事：① 用随机临时域名、不固定、不可枚举；② 脚本和扫码页都明确提示"无访问控制、演示账号免密、演示完一条命令 --stop 立即销毁"，开机自启默认关闭；③ 服务默认只绑本机回环口（指 F1 已改），隧道是本机出站拨号，不对局域网敞开。长期对外是固定域名 + Nginx + 证书 + 真实鉴权的正式部署方案，文档里有。

**Q4：暗色模式会不会花里胡哨反而看不清？**
A：我们把所有语义文字色做成亮/暗成对的设计令牌，暗色下自动换浅色变体，并且有自动化对比度巡检——26 个页面 × 5 种视口，按 WCAG AA（正文 4.5:1、大字 3:1）自动量，不达标就报。过程中确实抓到过几处内联写死颜色在暗色下不达标的问题，全部令牌化修复了。

**Q5：你说 581 个测试全绿，这里面有没有"永远不会失败"的水测试？**
A（这题答好是加分）：我们认真区分过。早期确实有两个测试只返回结构化数据、不做断言——发现后我们没有删数，而是**补了带强断言的独立测试**，结果立刻暴露出人设路由准确率只有 91.67%（一句话被误判成社区观察员），修到 100% 后才绿。现在关键指标都有"必须等于 100% / 必须无缺失"的硬断言，剩下少数返回结构化结果的是给消融实验报告供数的冒烟项，且告警被显式登记、有真断言兜底。
