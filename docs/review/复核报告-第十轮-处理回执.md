## 一、O1（PWA 无 service worker，别说离线）→ 已查实、修了措辞、加了门禁 ✅

### 1. 先查实：仓库里的真相

| 事实 | 证据 |
|---|---|
| **确实没有 service worker** | `web/src/**` 全文无 `serviceWorker` 注册；`web/public`、`web/dist` 下无任何 `sw*.js` |
| **可安装能力是真的** | `web/public/manifest.json` 合法（standalone / 3 图标含 512 maskable / 2 快捷方式）、`icon-192/512.png` 存在、`index.html` 有 manifest 链接 + iOS meta |
| 所以只有一半能讲 | ✅「可添加到手机主屏幕、类 App 全屏」　❌ 任何"脱网也能用"式承诺 |

### 2. 但**材料里确实有一处误导**（报告没指出，我自查发现）

`docs/mobile-deploy.md` §4.3 原文写的是：

> `web/public/manifest.webmanifest` + `pwa-192/512.png` + `sw.js`（缓存优先 `/assets/`），`main.js` 生产注册 SW。

三个问题叠在一起：① 写成"已落地"的方案陈述（**实际没做 SW**）；② 文件名**根本不存在**
（实际是 `manifest.json` / `icon-192.png` / `icon-512.png`，仓库里没有 `manifest.webmanifest` 和 `pwa-192.png`）；
③ 表格里还写着 PWA 用途是「离线壳」。
这正好就是 O1 警告的那类失真——只不过它是"文档比现实更大"，比"嘴上说离线"更隐蔽。

**已改**：§4.3 重写为「**已完成：可安装** / **未做**：service worker 与离线能力」的事实表 +
能做什么/不能做什么 + 一句对外口径；表格行改成「已落地『可安装（类 App 全屏）』；**service worker / 离线未做**」；
`docs/mobile-adaptation-plan.md` 的路线图条目同步改成「**未做**，对外不得宣称离线能力」。

### 3. 加门禁（不再靠"记得别说"）

1. 新增测试 `tests/test_claims_consistency.py::test_pwa_is_installable_but_not_offline`，断言四件事：
   - 源码里**没有** SW 注册代码、`public/dist` 下**没有** sw 文件（"无 SW"是真事实，不是谦虚）；
   - `manifest.json` 存在且合法（含 `name/short_name/start_url/display/icons`，`display==standalone`），
     且**它引用的每个图标文件真实存在**（这条能直接抓住"文档写了不存在的文件名"这类问题）；
   - 禁止短语表里必须登记四个"离线能力"式表述；
   - 当前状态文档里**「可添加到主屏幕」这句诚实表述还在**（只删不立同样失真）。
2. `scripts/check_claims.py` 的过时表述表新增：`离线可用`、`支持离线`、`离线 PWA`、`断网可用`、
   `manifest.webmanifest`、`pwa-192`、`pwa-512` —— `check_claims` 与 pytest 共用这一份，改错材料两处都会红。

### 4. 门禁**当场咬到我自己**（如实记录）

我在 §4.3 写了一句"**不要**说「离线可用 / 支持离线 / 断网可用」"——**注释里引用了被禁的词本身**，
门禁立刻报 `docs/mobile-deploy.md:166 「支持离线」`。改成"任何'脱网也能用'式的能力承诺都不能说"后通过。
这说明门禁是按"字面"判的、确实有效，也说明**该口径的表述方式要避开原词**（已写进文档注释）。

## 二、O2（581 里 6 条供数冒烟有强断言兜底）→ 说法**基本成立，但不是 6 条都有**；已补白名单门禁 ✅

### 1. 逐条查实（这是这轮最该说清楚的一件事）

`tests/test_ablation.py` 里有 **6 个 `test_*` 函数只 `return dict`、不做任何断言**（供消融报告取数）：

| 供数冒烟项 | 有强断言兜底吗 | 说明 |
|---|---|---|
| `test_persona_routing` | ✅ `test_persona_routing_is_accurate` | 断言 `rate == 100.0`、`total >= 5` |
| `test_tool_discovery` | ✅ `test_tool_discovery_covers_expected` | 断言 `missing == []`、`found_expected == expected` |
| `test_ooda_pipeline_latency` | ❌ 无 | 量各阶段耗时（机器相关，天然易 flaky） |
| `test_db_performance` | ❌ 无 | 量查库耗时 |
| `test_reflector_components` | ❌ 无 | 组件可用性数据 |
| `test_memory_operations` | ❌ 无 | 记忆读写数据 |

**所以准确的表述是**："6 条里有 2 条（对外材料真正引用的那两个指标）有硬断言兜底；另外 4 条是
**纯机器相关的性能/组件观测值，只给消融报告用、不进任何对外材料**（已核对：材料里没有引用它们的数字）。"
报告原话"关键指标另有强断言兜底"是这个意思，但容易被读成"6 条都有" —— 这里把它写明。

### 2. 加门禁（把这段解释变成不可漂移的事实）

`tests/test_claims_consistency.py` 新增两条 + 一条自洽检查：

- `test_ablation_smoke_items_are_whitelisted`：用 `ast` 解析出"所有不带 `assert` 的 `test_*`"，
  必须**恰好等于**白名单里的 6 个。**以后谁再加一个不做断言的 `test_*`，CI 直接红** ——
  这正是第八轮抓到"人设路由只有 91.67%"的同一类防线。
- `test_ablation_quoted_metrics_have_asserting_tests`：对外引用的指标 → 必须存在对应的断言测试，
  且断言里要有明确阈值/等值（`== 100.0` 这类），防止"有 assert 但断言很软"。
- `test_current_status_docs_still_reference_ablation_smoke_scope`：材料里只要把消融用例算进测试规模，
  就必须同时写明它们的性质（供数冒烟 + 关键指标另有强断言）。

### 3. 材料口径同步

`docs/competition/最终版交付说明.md` 增加一段主动说明：
`582 = 581 通过 + 1 跳过`（本轮同步后为 `586 = 585 + 1`），其中 6 项是供数冒烟、两个对外指标由
`test_persona_routing_is_accurate` / `test_tool_discovery_covers_expected` 守着，**主动讲，不等评委问**。

## 五、我这轮犯的两个错（如实记录）

1. **用 PowerShell `Add-Content` 往 UTF-8 文档追加了中文** → 写进去的是 GBK 字节，文件被污染，
   第一次"门禁反证"失败的原因其实是 `UnicodeDecodeError` 而不是断言命中（**假证明**）。
   已按字节定位截断修复（18,313 字节 / 298 行，无非法字节），改用 Python 以 UTF-8 注入重做反证，结论才成立。
   教训：**这个仓库的文本文件一律只用 UTF-8 工具链改**（PowerShell 5.1 的 `Add-Content`/`>` 默认 GBK）。
2. **在文档里引用被禁短语做说明** → 触发自己的门禁。已改写成不含原词的表述。
