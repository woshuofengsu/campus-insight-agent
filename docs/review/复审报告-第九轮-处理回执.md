### F3（P3 暗色首帧）采纳改法 ✅，但**根因判断需更正** ⚠️

- **采纳部分**：按建议在 `web/src/main.js` 的 `app.mount()` **之前**按 `localStorage.ci_theme`
  先给 `body` 加 `dark` 类（`App.vue` 的 `theme.apply()` 保留，切换主题仍以它为准）。
  这样首帧即暗色，消除暗色闪烁（FOUC）。
- **更正部分**：报告认为残留的 `处理结束 2.96:1` 是"审计采样时序造成的假问题"，
  并称"稳定后再测同一个字是 #6EE7B7"。**这个判断方向是反的**，实测证据如下：
  - 该元素的颜色在源码里是**写死的字面量** `'#047857'`（`web/src/views/grid/Issues.vue:159`），
    它**根本不读 CSS 变量**，所以 `body` 上的 `--ink-success=#6ee7b7` 对它没有任何影响；
  - 它的**背景**才是走 CSS 补丁的（`#ecfdf5` → 暗色 `#12241B`）。也就是说：
    首帧（补丁未生效）= 深绿字配浅绿底 ≈ 5.5:1 **通过**；补丁生效后的稳定帧 = 深绿字配**深绿底** = **2.96:1 不通过**。
    若真是采样时序问题，被误抓的应该是"通过的那一帧"，而不是稳定帧。
  - 修法：该状态色改为 `var(--ink-success)`（亮色取值与原写死色**完全相同**，暗色自动换 `#6EE7B7`）。
    顺手把同一条绑定里另外三个写死色（`#5B6B80`/`#b91c1c`/`#4f46e5`）也令牌化 ——
    其中"已关闭/已超时"两个分支当前数据没触发（审计量不到），但属同类隐患，一并收掉。
  - **修后实测**：`grid-workorders-dark` 对比度违规 0；全量 54 页/视口连续两轮 **0 违规**（可复现）。
  - 结论：**F3 的一半（FOUC）是真问题、已按建议修；另一半（"2.96:1 是假问题"）是真 bug、已修在源码里。**

## 二、本轮自查新增（报告未覆盖）

### A（工具级漏洞，已修）控制台报错此前**只打印、不计入违规**

- 影响：前端门禁对外宣称"0 JS 报错"，但 `ui_audit` 里 `jsErrors` 只是打印一行，**不影响退出码**。
  也就是说 **F2 那种"打开页面就发 400"的问题，审计本来是抓不到的**（4xx 请求在 Chromium 里会进 console）。
- 改法：`jsErrors` 现在**计入 HIGH**（列出每条报错），与"0 JS 报错"的口径对齐。
- 修后：54 页/视口 **0 JS 报错**（这同时反向验证了 F2 的修复）。

### B（网络级真坑，已修并写进文档）校园 DNS 对新隧道域名返回 NXDOMAIN

- 现象：隧道刚建好，**本机连自己的公网地址都打不开**：`urllib` 报 `getaddrinfo failed [Errno 11001]`，
  看起来像"隧道挂了"。实测对照：
  ```
  nslookup <域名>          → 校园 DNS(59.64.80.110)：Non-existent domain
  nslookup <域名> 8.8.8.8  → 104.16.230.132 / 104.16.231.132   ✅
  ```
  `ipconfig /flushdns` 也救不回来（那是上游的负缓存/拦截，不是本机缓存）。
- 影响判断：**手机若连同一个校园 WiFi，很可能同样打不开这个新域名**（同一解析器）。
- 修法（新增 `scripts/net_probe.py`，纯标准库，被两个脚本复用）：
  1. 用 **UDP/53 直接问公共 DNS**（8.8.8.8 / 114.114.114.114 / 223.5.5.5）拿 A 记录，绕开本机解析器；
  2. 把结果写回**本进程**的 `socket.getaddrinfo`（TLS SNI 仍用原域名，证书校验不受影响），
     此后所有 `urllib` 请求照常工作；
  3. 另提供 `get_via_ip()`：**完全不依赖解析**，直接 IP+SNI 发一次 HTTPS GET 做交叉验证。
- 实测证据：
  ```
  UDP/53 8.8.8.8 → ['104.16.230.132', ...]
  IP+SNI 直连 104.16.230.132：HTTP/1.1 200 OK  service=CommunityInsight Web
  ```
  接进工具后：`serve_public.py --status` 会打印"已用公共 DNS 解析到 …（手机若连同一个 WiFi 也可能打不开，
  建议切 4G/5G）"，`probe_public.py` 自动绕行后仍 **8/8**。
- 已写入 `docs/演示常开-本机方案.md` 的"已知坑"，并给出三条替代：**手机切 4G/5G（最稳）** /
  换手机 DNS / `python scripts/serve_public.py --lan` 后走局域网 IP（需同一 WiFi，且 http 下无语音）。
