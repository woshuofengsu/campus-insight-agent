## 1. 总体评价

**本轮没有发现致命缺陷**，只有 4 个 P2/P3 级一致性与严谨性问题（两套混合排序并存、评测判据偏宽、缓存表裸 ALTER、大屏仍用旧检索）。

## 2. 核心优势（本轮新增/强化，5 点以内）

1. **向量是真的，且能自证**：`kb_embeddings` 59 条全部有 `dense_json`，dim=1024、provider=bailian，抽样 1024 维全非零、L2 norm=1.0（正是 text-embedding-v3 的归一化输出特征）。不是零向量占位、不是随机数、不是"接了 API 但库里没东西"。
2. **增益可量化、可复现、有对照**：`scripts/rag_eval.py` 同一份 27 例金标，混合 27/27=100%，`--no-embedding` 强制关向量纯词法 24/27=88.9%，净增 3 例全是零词法重叠的语义难例；阈值 85% 卡 exit code，已接进 `.github/ci.yml`。这是答辩时"凭什么说语义检索有用"的硬证据。
3. **真接进了线上主链路，不是"建了没接线"**：`/api/web/qa/ask → db_policy.ask_question → search_published_knowledge`（词法分 + `_dense_boost` 语义加分，逐条标 `hybrid/lexical`），弱命中才走 `policy_rag.generate` 真 LLM 且强制闭集引用；每次问答在 `api_routes/policy.py:30` 写 `kb_query_log`（含未命中与检索路线）。
4. **可观测性成闭环**：v43 建 `kb_query_log`（走正规 `_m43_` 迁移注册）+ `data/db_kb_metrics.py`（命中率/零命中 top/检索路线分布/语料规模）+ `GET /agent/kb-health`（双重校验锁 grid）+ 大屏卡片 + `scheduler.py:161` 挂 90 天清理。
5. **降级设计严谨、零重依赖**：`utils/embedding.py` Provider 抽象 none/bailian/zhipu，只用 `requests`；无 key、网络失败、额度耗尽、维度不符全部安全返 `None`；查询向量进程内缓存 512；`_dense_boost` 在 provider 不可用时返 `{}`，等价纯词法，**升级零风险**。

## 3. 致命缺陷与硬伤（按严重程度排序）

## 6. 答辩问答库（本轮 RAG 相关尖锐问题 + 应答思路）

**Q1：你这混合检索比纯关键词到底好在哪？数字怎么来的？**
A：同一份 27 条居民口语金标，纯词法（同义词扩展）top-3 命中 24/27=88.9%，加入语义向量后 27/27=100%。脚本 `scripts/rag_eval.py` 用 `--no-embedding` 一键对照、CI 卡 85% 阈值，现场可复跑。净增的 3 条都是词法无法命中的语义改写。

**Q2：举一个词法一定漏、语义能接住的例子。**
A："老楼上下楼不方便"——整句没有"电梯"两个字，关键词匹配找不到《既有多层住宅增设电梯》；向量按语义相似度能召回。同类还有"家里老人一个人住不放心→独居关爱""穷人租不起房→保障性住房"。这对不会说书面词的老人尤其关键。

**Q3：RRF 是什么？为什么用它而不是直接把分数相加？**
A：RRF（Reciprocal Rank Fusion，k=60）按"两路各自排名的倒数"融合，不需要把词法分和余弦分强行归一化到同一量纲，对分数尺度不敏感、鲁棒。线上自动回答为了不扰动既有词法主序，采用"词法主序+语义加性纠偏"，两路共用同一批向量，取向不同。

**Q4（追 Q3）：那你线上到底用哪个？评测和线上不是一套？**
A：评测与 Agent 上下文用 RRF（`agent/rag.search_hybrid`）；居民自动回答走 `db_policy` 的词法主序+语义加分。原因是自动回答已有成熟词法阈值体系，加性叠加能保证关掉向量后行为与以前完全一致、零回退；RRF 用于需要双路平等召回的 Agent 场景。两者向量底座、结论方向一致，已在代码注释互相标注。（这就是 P2-1，务必按第 5 节先加注释。）

**Q5：向量哪来的？是不是假数据/占位？**
A：阿里云百炼 text-embedding-v3，1024 维，59 条知识全部落库，可现场查：每条向量 1024 维全非零、L2 归一化 norm=1。文档向量离线一次性构建落库，查询向量实时生成并进程内缓存。

**Q6：断网 / embedding 服务挂了 / API key 没配，系统会崩吗？**
A：不会。`utils/embedding.py` 在无 key、网络异常、限流、维度不符时全部安全返 None，检索自动退化为纯词法，`provider=none` 时与升级前行为完全一致；查询向量失败不阻断问答。这是刻意的"语义只做加法、不做单点依赖"。

**Q7：这是不是为了用大模型而用大模型？哪些地方坚持用规则？**
A：恰恰相反，默认全关。意图路由、状态机、匹配阈值、敏感词/医疗法律拦截、仲裁校验全部规则；语义向量只在检索纠偏这一层做加分；只有弱命中且 `POLICY_LLM_RAG=1` 时才调 LLM 生成，且强制引用闭集内知识、引用标题用数据库真实行拼装防幻觉。规则兜底确定性、LLM/向量只补规则的盲区。

**Q8：怎么防止 LLM 一本正经胡说（幻觉）？**
A：三层：①只把检索到的已发布知识片段喂给模型；②模型只能引用给定下标，标题从数据库真实行取，不信任模型复述；③引用下标越界/标题子串对不上直接丢弃生成结果、回退转人工。金标与命中率评测持续度量。

**Q9：27 条金标会不会太少、自己挑对自己有利的？**
A（诚实）：27 条对竞赛验证"语义净增益"足够，其中刻意放了 7 条零词法重叠难例；但我们也明确指标目前是 top-3 关键词命中、样本量有限，生产化会扩到 100+ 并引入 MRR/nDCG 与首位命中率。评测脚本、金标文件、CI 阈值全部公开可复跑，不是手工挑结果。

**Q10：知识库里的政策是真的吗？来源？**
A：40 条新增来自北京市人大、市医保局、住建委、民政局等公开政策，带发布机构、真实文号（如京政办发〔2018〕6号）和来源链接；社区自整理内容显式标注"社区整理"脚注，不冒充官方；过期政策自动到期下架、新版本走审核并自动替换旧版。

**Q11：每次提问都调向量 API，成本和延迟扛得住吗？**
A：文档向量离线一次性构建，不重复花钱；只有查询向量实时调，进程内缓存 512 条热点问题；且降级到纯词法不依赖网络。成本主要是查询嵌入，按调用量线性、单价极低，已在商业测算中列出。

**Q12：知识库健康度是干什么的？谁看？**
A：`kb_query_log` 记录每次检索（**含未命中**），网格员端 `/agent/kb-health` 看近 N 天命中率、零命中问题 top、检索路线分布、语料规模——零命中问题就是"该补哪条知识"的待办清单，让知识库能持续运营而不是建完即烂尾。日志 90 天自动清理。

**Q13：语义检索会不会把不相关的内容硬凑上来误导居民？**
A：两道闸：语义只做有限加分（余弦折算有上限、不改变词法主序），最终仍要过既有匹配阈值，低于阈值不自动答、转人工；金标对照也显示语义只在"该召回却没召回"时纠偏。

**Q14：为什么用 SQLite 存向量？不用向量数据库？**
A：59 条（社区级真实规模也就百条量级）1024 维，全量加载内存算余弦毫秒级，引入 Milvus/pgvector 是过度工程；抽象层已隔离，规模上去可平滑替换为 pgvector，检索接口不变。

**Q15：多 worker / 多社区部署时向量缓存怎么办？**
A（诚实）：查询向量缓存目前是进程内的，多 worker 各自缓存、命中率略降但结果一致；生产化会把缓存与黑板等进程内状态统一迁 Redis。文档向量在 SQLite，多实例共享无一致性问题。

**Q16：怎么证明你说的这些现在就是好的、测试不是凑数？**
A：531 pytest 全绿、ruff 0、前端构建通过；新增 RAG 测试默认 monkeypatch 关闭向量、不依赖外网，保证 CI 离线可跑；rag_eval 作为独立质量门接在 CI。现场可直接跑 `pytest -q` 与 `rag_eval.py` 双模式对照。

**Q17：语义系数为什么是 3.0？**
A：词法分由标题/关键词/正文命中次数累加、典型量级在 0–6，余弦 ∈[0,1]，乘 3 表示"语义高度相近时，最多相当于一次强词法命中的纠偏力"，既足以救回零重叠语义难例、又不至于压过明确关键词命中；该值可用 rag_eval 做敏感性扫描。（答辩前最好真跑一次 1/3/5 对照。）

**Q18：居民提问里有手机号等隐私，进查询日志合规吗？**
A（按第 5 节改完后答）：日志只服务知识库运营、90 天清理，落库前对手机号等做掩码，展示/导出沿用统一脱敏；这是 PIPL 最小必要原则。（**没改就别声称已做，诚实说"已列入清理+脱敏计划"。**）

**Q19：这套 RAG 和你那 9 个智能体什么关系？**
A：RAG 是"政策专员"等角色的能力底座——接待员识别为政策类问题后，由检索增强给出带引用的答案，校验器/合规审计员仍在最外层做拦截与留痕，智能体负责"谁来处理、怎么协作"，RAG 负责"答得准不准"，职责正交。

**Q20：如果只能再做一件事把它变成可上线产品，做什么？**
A：找一个真实街道/社区试点，用 `kb-health` 采集真实零命中问题反哺知识库，把金标从 27 扩到真实分布的 100+——技术闭环已经具备，缺的是真实数据飞轮，这也是当前竞赛版与生产版唯一的本质差距。
