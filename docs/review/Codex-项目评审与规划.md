## 4. 真实短板

严重度按**对现场演示/答辩和真实使用的影响**排序，不等同于漏洞评分。以下“隔离逻辑验证”指直接调用真实函数、替换数据库或依赖为模拟对象；没有向 :8000 发请求，也没有读取或修改真实数据。

### 致命（可能挂演示/答辩，或否定真实试点资格）

**F1｜社区隔离在老人名单与健康记录主路径缺失。〔静态确认 + 隔离逻辑验证〕**

- `api_routes/elderly.py:523` 的老人列表只筛 role/is_active，没有社区条件，返回 id、name、community。
- `:511` 的健康记录只校验 grid 角色，直接用传入 uid 调用 `list_vitals` 与 `vitals_summary`；`data/db_vitals.py:73`、`:92` 按 user_id 查询，无租户条件。
- 这是页面实际使用的接口：`web/src/views/grid/ElderlyCare.vue:26` 拉名单，`:37` 查询选中老人。
- **影响：**A 社区网格员可以沿此链看到其他社区老人和健康记录；不是仅“攻击者知道 id 才可能”的边缘路径。模拟 A 网格员传另一个 uid，路由确实调用底层并返回成功；未做真实数据跨社区读取。
- **建议：**老人名单、uid 解析及健康数据查询共用同一社区授权条件；归属判定前不返回目标是否存在。

**F2｜“同社区”被误当作“有权操作这个人”。〔静态确认 + 隔离逻辑验证〕**

- `api_routes/elderly.py:315` 删除联系人、`:328` 处置 SOS 只有 `_same_tenant`，没有足够的角色/本人/授权家属判定；修改用药 `:231`、暂停恢复 `:344` 同类。
- 底层 `data/db_elderly_care.py:928`、`:1085`、`:1107` 等函数按记录 id 处理，没有补上请求者所有权校验。
- 模拟普通居民、同社区闸门通过时，SOS 关闭（带处理备注）和删除他人联系人都会进入修改函数并返回成功。实际 SOS 还受状态/备注校验、联系人受数量约束；这些业务校验不能替代授权。
- **影响：**同社区其他用户可能干扰求助、联系人或用药提醒。界面不显示按钮并不能保护接口。
- **建议：**明确“本人、已验证家属、所属社区网格员”矩阵，按资源类型收口；尤其不能默认所有居民拥有网格员处置权。

**F3｜人工兜底在关键失败分支只是成功提示。〔静态确认 + 隔离逻辑验证〕**

- `agent/orchestrator.py:515` 建处理包异常后，`:528` 只记录 warning、置 hid=None；`:534` 仍回复“已为您转接工作人员”，status 为 transferred_to_human。
- `:389` 协商超过上限直接返回同一状态，但未调用建处理包流程。
- 隔离探针人为让 create_handoff 失败，观察到 **transferred_to_human / handoff_id=None / 成功承诺**；触发协商上限也证实未调用转人工函数。
- **影响：**居民以为有人接手，工作人员却可能没有待办；“不会编造办理结果”“有人工兜底”会被一个失败案例推翻。
- **建议：**持久化成功后才能宣称“已转接”；建单与通知失败分开表达，前者失败明确告知未接通，后者进入待重试而保留真实编号。

**F4｜当前演示脚本无法按所写的操作直接走通。〔页面与脚本静态核对〕**

- `docs/competition/演示脚本.md:159` 要把工单“待处理→处理中→已解决”；页面真实流转见 `web/src/views/grid/Issues.vue:185`、`:194`、`:201`，包含审核、派单必填姓名电话、开始处理、填写结果。连同展开卡片，操作量明显超过脚本表述。
- `docs/competition/演示脚本.md:164` 要打开独立“Agent 日志 / 留痕”入口；当前 `web/src/router/index.js:44` 的九个网格页没有同名独立页面。执行链和消息功能仍存在，不能把“有后端留痕”说成“已有脚本指定入口”。
- **影响：**一分钟演示段可能卡在找入口、字段校验或状态名称。没有浏览器现场复验，不能断言当前服务必挂。
- **建议：**按当前按钮重排脚本，提前准备合法输入；留痕展示只选择已亲自打开验证的入口。

**I2｜通知收件人选择绕过社区边界。**

`agent/orchestrator.py:520` 将转人工信息发送给所有 grid；`data/db_vitals.py:201` 的异常健康提醒也遍历所有 grid；`data/db_user.py:144` 的 list_users 没有社区参数。后者通知可能含老人姓名与健康读数。即使消息中心只允许用户看自己的消息，敏感内容已被投递给了错误收件人。需在**写通知前**限定职责与社区，不能靠读取接口补救。未实际发送任何通知。

**I3｜协作“通知草稿已生成”没有形成可管理对象。〔隔离逻辑验证〕**

`agent/roles/business_agents.py:465`、`:473` 在天气/安全隐患协商中返回 draft_ready=True 和“已生成草稿”，但函数没有创建通知草稿、返回草稿 id 或写黑板草稿。模拟该协商后黑板仍无共享字段、消息或历史变更。当前证据支持“产生了建议文本”，不支持“通知管理页存在待发布草稿”。应当真正创建可审核对象，或把文案改为“建议生成”；赛前优先后者。

**I4｜网格助手查询人工待办缺租户参数，会被新安全闸门拒绝。**

`agent/roles/auto_agents.py:157` 命中“处理包/人工待办/转人工的”后调用 list_handoffs，却没传 tenant；`data/db_agent.py:254` 使用租户过滤，`utils/tenant.py:156` 对未指定租户采取拒绝策略。该异常由 `agent/orchestrator.py:265` 捕获，用户只得到服务暂不可用。HTTP 管理路由已经传 tenant（`api_routes/agent.py:142`），但对话路径遗漏。这正是“功能存在、主入口没接完整”的例子。

**I5｜双层防线的覆盖范围和执行时机被过度概括。**

- `agent/orchestrator.py:149` 的接待员直答可直接进入 _finish，不经过 _dispatch 中的统一 Verifier。
- `:261` 先执行业务角色，`:278` 才校验结果；如果角色已产生副作用，校验文本不是事务回滚。
- `:318` 后追加协商内容，前面的校验不能自动覆盖最终拼接回复；仲裁也是遇到特定条件才触发。
- `:292` 把被拦截的 retry 交给转人工，而 `:534` 会保留原回复并追加承诺；应审查被拦截内容是否仍被输出。这是控制流风险，本次未以真实高风险内容做端到端验证。
- `agent/verifier.py:159` 的 verify 与文件前面的 verify_facts 是不同函数；不能以文件里“有事实校验函数”推导当前主链一定执行了它。

**建议口径：**“在特定业务路径实施规则校验与条件仲裁，正在补齐最终输出和副作用边界。”不要说“每条输出必过两层且所有幻觉都能拦住”。

**I6｜评测没有充分支撑宣传的 RRF 增益与真实业务效果。**

`scripts/rag_eval.py:64` 调用的是 data.db_policy.search_published_knowledge；命中规则（`:85` 附近）是预期关键词在结果标题/关键词/内容里出现，不是按固定正确文档 id 或回答事实判定。不能把它自动等同于 agent.rag 中另一条混合检索路径的评测。

脚本默认门禁针对 top-k 命中率、按 provider 取 70/85 阈值，而登录页展示 hit@1=100（`web/src/config/meta.js:30`）。因此“CI 绿”不必然等于“当前 48/48、RRF 提升至 100%”。属地优先的四个用例也主要依据预期关键词，不应直接包装成广泛属地准确率。

下一次需固定语料、样本、实现入口与模型配置，保存逐条结果及失败案例；100% 的小样本回归值即使复现，也不是现实泛化准确率。本次没有运行会初始化实际 DB_PATH 的 rag_eval.run。

**I7｜数据导出静默漏项，脱敏异常则继续写原文。**

- `api_routes/auth.py:153` 用统一 user_id 查询 community_issues/proposals，但这两表的关联用户字段是 reporter_id（同文件注销逻辑 `:204`、`:209` 也可交叉印证）。SQL 异常被 `:159` 吞掉，导出仍完成，用户不会知道诉求/提案缺失。
- `data/db_kb_metrics.py:85` 先保留原始问题，脱敏失败后 `:89` pass，再继续落库。这是安全处理失败时放行，应该记录“已省略敏感原文”的占位或跳过记录，而非继续保存原文。
- 本次没有触发实际导出或写日志；结论来自字段与异常分支的静态核对。

**I8｜当前测试与审计存在可解释的盲区。**

`tests/test_tenant_idor_sweep.py:327` 的自动规则只抓路径含“{”的接口，难以发现 ?uid= 查询，也不能证明同社区所有权正确。`tests/e2e/test_web_demo.py:15` 使用 TestClient，能验证 API 状态流，但不是“用户点按钮”的浏览器操作链。移动流程脚本存在，不应说项目没有 UI 检查；但未见其覆盖完整网格审核、字段输入、派单、居民反馈全链。

本次静默异常脚本报“假成功 0”，隔离验证却找到了实际假成功，说明正则检查只能筛嫌疑，不能作为语义正确性证明。781 项测试与这些缺口可以同时成立。

### 如果只能再做三件事，是哪三件？

1. **P0：把演示闭环和说法做实。**按现有 UI 排练、统一数字，删除“每轮必过”“全部隔离”“失败也成功”的过度承诺，并准备标注清楚的预录备用。理由：最近节点是上台，可信的一个闭环胜过十个未经验证的亮点。

## 7. 如果我是评委，我会问的 10 个问题

按最容易暴露当前问题的顺序。每题提供三句话答法；涉及修复效果的句子只能在修复并验证后使用，不能提前当作既成事实。

### 1）你说多社区隔离已经完成，为什么网格员能列出全平台老人？

① 主工单等路径已经做了社区过滤，但本轮审查确认老人名单、健康查询及部分派生路径仍有遗漏，不能把局部覆盖说成全系统完成。  
② 我会把按社区、按本人、按职责的权限矩阵补齐，并将通知和图谱也纳入验证。  
③ 当前展示使用合成数据，未修复并验证前不接真实多社区业务。

### 2）系统说“已转人工”，数据库没写成功怎么办？

① 目前有异常分支会给出不准确的成功提示，这是需要优先修复的缺陷。  
② 正确标准是有真实处理包编号和接单队列记录，建单失败必须明确告知未转接，通知失败则单独重试。  
③ 验收时我会主动注入存储失败，给您看用户提示与后台记录是否一致。

### 3）九个智能体是不是九个 if 或九套提示词，为什么需要这么多？

① 目前核心是可解释的规则路由和事件协作，九个角色对应不同业务职责，并非九个大模型同时自主推理。  
② 黑板和角色间消息确实存在，但某些协作结果尚未形成完整业务对象，我不会把它们全部算成自动闭环。  
③ 是否值得保留某个角色，要用完成率、人工接管和成本对比固定工作流来证明，而不是按角色数量判断先进性。

### 4）48 条检索命中 100% 和 85.7% 基线，原始结果在哪里？

① 这是自建小样本回归口径，不是对现实所有问法的准确率承诺。  
② 现有材料的同批 48 条与 85.7% 分母不一致，而且当前脚本按关键词命中，因此我要先补齐版本一致的逐条结果。  
③ 在结果复核前我只确认有 48 条评测样本，不把“融合提升到 100%”作为已经重新证明的结论。

### 5）781 项测试为什么没发现这些问题？

① 数量代表被收集的测试项，不代表全部业务路径、全部权限组合或百分之百覆盖率。  
② 当前按 id 的结构扫描偏重路径参数，容易漏查询参数与同社区所有权，而 API 测试不能保证按钮操作完整。  
③ 我会增加权限矩阵、失败注入和真实浏览器旅程，并同时报告本次执行结果与未测范围。

### 6）你说每条输出都过校验和仲裁，能画出调用链吗？

① 当前业务分发路径有校验和条件仲裁，但接待员直答和后续拼接内容并不都走同样的检查。  
② 因此“每条必过双层防线”不准确，校验输出也不等于撤销已经发生的业务操作。  
③ 我会把最终回复检查与写操作授权、事务分开设计，并用具体被拦截案例证明各自边界。

### 7）断网、模型失败、老人不会操作，你还能完成什么？

① 规则与本地服务可支撑一部分流程，但 Web 业务仍需要后端可达，不能宣称整套系统浏览器离线可用。  
② 语音失败时提供预置短语和文字输入，模型失败时使用已经验证的规则降级或明确转人工。  
③ SOS 只是辅助联系流程，不等于专业救援服务，真实响应责任必须由合作方明确。

### 8）这会让网格员少干活，还是又多一个系统？

① 当前还没有真实试点数据证明省时，不能用合成工单的大屏推导治理成效。  
② 最小验证应只针对一种诉求，比较补充询问次数、每单处理时间和遗漏率，同时观察是否增加录入负担。  
③ 如果不能减少重复劳动，我会优先改进现有来源接入和流程，而不是继续加智能体。

### 9）你一个人借助 AI 写了这么多，哪些关键部分你真正掌握？

① 我会用一次真实工单解释前端输入、路由鉴权、业务状态迁移、数据库记录和居民反馈之间的完整关系。  
② 我也会拿一个本轮发现的缺陷讲清触发条件、根因、修复取舍和验证方式，并如实说明 AI 辅助的范围。  
③ 我不以提交数或行数证明个人能力，而以能否解释和复现设计决策、故障与改进来证明。

### 10）为什么社区要采用你，后续你毕业了谁维护？

① 目前产品仍是验证原型，采用理由需要建立在一个明确的省时场景和试点证据上。  
② 我会先收敛功能、补齐部署恢复与运营责任，让系统可以由其他人接手，而不是依赖我现场操作。  
③ 如果试点不能证明价值或合作方无法承担运行责任，就不扩张到多社区，也不承诺持续服务能力。
