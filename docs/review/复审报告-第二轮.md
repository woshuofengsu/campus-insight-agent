## 1. 总体评价

这一轮整改是**动了真格的**，不是"改文档糊弄"。首轮点出的三个 P0——**演示端点越权拿 JWT、材料与代码两张皮、主链路几乎纯规则**——都在代码层面被真正闭合：越权做了中间件+路由双硬关并补了 6 个负向安全测试；政策问答从"纯检索"升级为**带引用下标强校验的真 RAG 生成**；健康⇄天气的仲裁从"只留痕、结果丢弃"改成了**仲裁结论真正改写用户可见回复与是否转人工**；自研 HMAC-CTR 也换成了**真 AES-256-GCM 且旧密文参数逐字节对齐、可平滑解密**。测试从 457 增至 495 且全绿，特性开关默认关的策略保护了既有测试，工程纪律在线。

## 2. 核心优势（整改后真正立得住的 5 点）

1. **安全从"口头合规"变成"可证伪"**。`/api/web/auth/demo` 在非 DEMO_MODE 下被中间件直接 403（api_web.py:145 附近），路由内再判一次 `config.DEMO_MODE`（api_routes/auth.py:67），角色入参用 pydantic `pattern` 锁死 resident|grid|elderly；配套 `tests/test_security.py` 16 个测试含 **JWT 篡改、alg=none、居民 token 打 grid 端点越权、导出脱敏、删除匿名化、5 次失败锁定**，全部实测通过。这是评答辩"安全"时最硬的弹药。

2. **真 RAG，且把"幻觉防线"做成了代码而不是 PPT**。`agent/policy_rag.py` 强制 LLM 返回 `{answer,cited_index}`，下标必须落在检索集内、引用标题由数据库真实行回填（防 LLM 编造标题子串），INSUFFICIENT/解析失败/下标越界一律返回 None；`data/db_policy.py` 的 low_score 分支接入后**任何异常都回退原转人工**，零检索结果坚持 no_knowledge（无材料不生成）。前端 QA.vue 在 `result.rag` 时显示"🤖 AI 依据知识库生成 · 已校验引用"，形成"生成—校验—标注"闭环。

3. **多智能体协商第一次"真的咬合上了"**。健康顾问发现非紧急不适且有生效预警时，会主动 `_post("weather_guardian","task_request", health_weather_risk_query)`（business_agents.py:338）；天气守护用**最新预警重新复核**后回执（auto_agents.py:71-91）；健康侧拿到"天气说没事但症状高危"的真实分歧后交 Arbiter，**仲裁结论直接决定用户看到的文案和 need_human**（business_agents.py:396-422），并有 `test_arbitration_real.py` 8 条断言锁定。这不再是写死的顺序调用。

4. **加密升级做到了"换算法不炸存量"**。`utils/crypto.py` 新写入为真 AES-256-GCM（cryptography 库，`g1$` 前缀 + 12B nonce + SHA-256 派生 32B 密钥）；旧 HMAC-CTR 收进 `_LegacyStream`，经 `git show 7707585~1:utils/crypto.py` 逐行比对，**salt（campus-insight-crypto-v1）、scrypt 参数（n=2¹⁴,r=8,p=1,dklen=32）、nonce12B/mac32B、CTR counter 大端 8B、CRYPTO_KEY 与默认密钥全部一致**——存量密文确实解得出，不是"自造密文自测"。

5. **工程自证能力成型**。`scripts/check_claims.py` 一条命令打出用例数/schema/路由/角色/表数的**代码库真值**，从根上杜绝材料数字漂移；混合压测 `scripts/benchmark_business.py` 改为**先登录拿 JWT、按 issues/chat/notices/policy/create 真实比例、输出 p50/p95/p99 与错误率**，回应了首轮"550 并发只压免登录 demo 端点"的质疑；离线金标 `tests/test_eval_golden_rules.py` 用临时库、不触网、以真实 jsonl 条数为分母进 CI。

## 3. 致命缺陷与硬伤（按严重度排序）

**结论先行：首轮的 3 个 P0 已全部解除，本轮没有发现新的"致命级"（可被现场打穿、导致项目不成立）问题。** 以下为"高残留"，按"被评委戳中的概率 × 杀伤力"排序：

### H1（高）招牌生成式能力默认关闭，且没有一键演示档——"真 AI"现场可能跑不出来
- **事实**：`config.py` 中 `POLICY_LLM_RAG`、`RECEPTION_LLM_FALLBACK` 默认 `"0"`（实测 import 后均为 False，设计如此，为降本）；但项目根 `.env` 只配了 `DEEPSEEK_API_KEY`，**没有打开这两个开关，也不存在方案里承诺的 `.env.demo`**。即：现在 `uvicorn` 起起来，政策弱命中仍走转人工、接待员未命中仍走关键词，**真生成路径处于休眠态**。
- **为什么致命**：互联网+ / OPC 现场，评委最想听的就是"你这 AI 在哪"。如果演示机用默认配置，你点一个知识库弱相关问题，系统直接"转人工"，RAG 一次都不触发，前面所有"真 RAG/真仲裁"的代码都无法被看到。这不是代码缺陷，是**演示工程缺陷**，但在赛场上等价于硬伤。
- **补救**：新建 `.env.demo`（内容：`DEMO_MODE=true`、`POLICY_LLM_RAG=1`、`RECEPTION_LLM_FALLBACK=1`、`LLM_NEGOTIATION=1`、`DEMO_AUTO_WORKER=false`），并在 README 写清两档启动：`--env-file .env`（降本/生产口径）与 `--env-file .env.demo`（展示 AI 脑）。**赛前必须用 .env.demo 真机走一遍三条生成链路并截图存档**，防止现场断网/API 限流时无录像兜底。

### H2（高）ruff 静态检查"配置存在但既没清零也没门禁"，工程故事只讲了一半
- **事实**：`ruff.toml` 存在且为合法 UTF-8，但实测 `py -3.12 -m ruff check .` = **700 errors**（I001 未排序 import 190、F401 未用 import 110、RUF100 多余 noqa 60、E702 分号多语句 54、SIM105 51、UP009 50、F541 49……469 项可 `--fix` 自动修）；且 `.github/workflows/ci.yml`、`test.yml` **都没有任何 ruff 步骤**。
- **为什么是硬伤**：你在材料/dev-log 里写了"WS9 静态检查"，评委里只要有一个工程背景的人让你现场 `ruff check .`，700 条红字会直接反证"工程严谨"这个卖点；没接 CI 意味着它以后也不会变干净，属于"声称做了、实际没闭环"。
- **补救**（约 30–60 分钟）：先 `ruff check . --fix`（吃掉 469 项），剩余手工清；确属项目惯例的（BLE001/S110/DTZ005）已在 ruff.toml 全局降级，保留即可；然后在 ci.yml 的 test 步骤前加 `- run: pip install ruff && ruff check api_routes agent utils data scripts`（**先只门禁主链路目录，避开 ui/ legacy**），做到"门禁范围内 0 问题"。

### H3（中高）存量手机号密文重加密"脚本就绪、主库未执行"，"全库 AES-GCM"目前不成立
- **事实**：`scripts/reencrypt_phones.py` 已写，但实测主库 `data/community_insight.db` 中仍是旧算法密文（`g1$` 前缀计数为 0）：user_profile 4 条、community_issues.reporter 185 / assignee 2、health_consults 180、emergency_contacts 3，**合计 374 条全部 legacy**。
- **影响判断**：因为 `_LegacyStream` 能解旧密文、新写入自动是 GCM，**功能上完全正常、不影响演示**；但如果对外讲"敏感数据已全部 AES-256-GCM 加密落库"，这句话与库现状不符，属于可被"请导出一条密文看看前缀"证伪的表述。
- **补救**：备份 db 后执行 `py -3.12 scripts/reencrypt_phones.py`（脚本应先备份、逐行 decrypt→encrypt(g1$)、计数打印、可重入），跑完用本次复审的前缀统计核对 g1=374/legacy=0；若决定演示库不重加密，则**口径统一为"新写入 GCM、历史密文版本化兼容、提供一键轮换脚本"**——这句反而是加分的"密钥轮换能力"，不要硬说"全库已 GCM"。

### H4（中）两处"自己打脸"的小不一致，评委对照材料/界面时会扣分
1. **政策 RAG 布尔条件写反**：`agent/policy_rag.py:61`
   ```python
   if not ans or (not isinstance(idx, int) and str(idx).isdigit()):
       return None
   idx = int(idx)
   ```
   少了一个 `not`——数字字符串下标（如 `"2"`）被误判拒识，第 63 行 `int(idx)` 对该路径成为死分支；而垃圾值（None/"abc"）反而靠第 63 行抛异常、被外层 ask_question 的 try 兜住转人工。**主路径（JSON 返回整数）不受影响、无用户可见故障**，但这是明确的逻辑缺陷。
   正确写法：`if not ans or (not isinstance(idx, int) and not str(idx).isdigit()): return None`，并补一条"cited_index 为数字字符串也能接受"的单测。
2. **SOS 确认弹窗与结果页矛盾**：`web/src/views/elderly/Home.vue:254` 弹窗仍写"将依次呼叫：张三、李四"，但触发成功后（:130）诚实提示"手机无法自动连续呼叫，请手动拨打120"。前后承诺不一致。把弹窗 content 改为"将**通知**紧急联系人：X（手机不能自动连续拨号，需手动点拨打120）"。

### H5（中）"状态更正声明"里的数字又过时了，且低估了自己
- **事实**：`docs/competition/技术实现报告.md` 顶部更正表写"测试 467 项（463 passed）"，实测已是 **495 passed / 499 collected**；同表加密行写"可平滑替换 AES-256-GCM"，但 WS6 **已经是真 GCM** 了，措辞还停在"将来可替换"，反而把已完成的亮点说小了。
- **补救**：测试数不要写死，改成"`python scripts/check_claims.py` 实时输出（当前 495 passed）"；加密行改为"已采用 AES-256-GCM（密文版本前缀 g1$），兼容历史密文并支持脚本轮换"。

## 4. 十维度诊断（每维：核验结论 → 现状 → 残留问题 → 具体建议）

### 维度 1 技术架构合理性 —— 8.5/10（↑0.5）
- **核验结论：通过，且比首轮更干净。**
- 现状：FastAPI 主线 + api_routes 模块化维持；首轮发现的 `/self-resolution` 重复注册已删除（实测 api_routes 内仅 1 处）；统一 LLM 客户端 `agent/llm_client.py` 收口了熔断（连续 3 次失败开 60s）、默认 6s 超时、无 key 快速失败、任何异常不外抛，成功/失败都 `record_usage` 记账。
- 问题：① 双后端（FastAPI 主线 + Streamlit app.py 备线 + api.py 扣子入口）仍在，`ui/` 目录约 1.3 万行遗留未动（ruff 已正确将其排除）；② 全量 ruff 700 项（见 H2）。
- 建议：**竞赛必须**——主线目录 ruff 清零并进 CI；**长远**——把 ui/、app.py、api.py、agent/engine.py(LangChain 旧链) 移到 `legacy/` 子目录并在 README 标注冻结，主线树立刻显得克制。架构本身不过度：黑板+仲裁+校验在本场景是"可演示的治理闭环"，保留。

### 维度 2 LLM 接入的真实性与有效性 —— 8/10（↑2.5，本轮提升最大）
- **核验结论：从"基本是规则"升级为"规则为骨、LLM 为脑、且脑可开关"，真实性成立；扣分在默认关+无演示档。**
- 现状（已逐文件确认）：
  - 政策弱命中 → `policy_rag.generate` 真生成 + 引用下标/标题双校验 + 失败回退（db_policy.py low_score 分支）；
  - 接待员规则未命中 → `intent_llm.llm_intent` 8 意图闭集兜底，闭集外/未识别返回 None，temp0、max_tokens8、timeout3，receptionist 已接线并标 `intent_via=llm`；
  - 健康协商文案可选 LLM 润色，但**升级判定仍用确定性高危词**（business_agents.py:370-374 注释明确），保证不被 LLM 措辞带偏——这个取舍非常成熟；
  - LLM 用量落 `llm_usage` 表带 token 单价，网格员端可查"AI 费用"，把"规则优先降本"做成了可验证数字。
- 问题：① H1：默认关 + .env 未开 + 无 .env.demo；② 金标只在**离线规则层**（intent 24 条/verifier 13 条），**真 LLM 答题质量评测** `scripts/llm_eval.py --provider llm` 需要 key、CI 不跑，因此"LLM 回答质量"目前没有可出示的离线成绩单；③ policy_rag.py:61 反逻辑（H4）。
- 建议：**竞赛必须**——出 `.env.demo` 并录三条"规则搞不定、LLM 兜底成功"的对比 GIF/截图（弱命中政策、口语化意图、健康⇄天气分歧仲裁）；用真 key 跑一次 `llm_eval.py --provider llm` 把准确率/引用命中率存进 docs/review。**长远**——金标扩到每类 ≥30（现 24/13，低于方案自定目标）。

### 维度 3 数据安全与合规 —— 8.5/10（↑2.5）
- **核验结论：从"自研算法冒充 GCM"变为"真 GCM + 真越权防护 + 负向测试"，安全成为强项；剩存量轮换与一个限流粒度问题。**
- 现状：AES-256-GCM 真实落地且旧密文参数逐字节兼容（见核心优势 4）；越权双硬关 + 登录失败锁定（utils/login_guard.py：5 次失败锁 300s、滑动窗口 deque、线程锁）；CORS 从 `*` 改为读 `CORS_ORIGINS`、缺省仅本机 5173；非 DEMO 下 docs/openapi/redoc 置 None；导出脱敏、注销匿名化有测试。
- 问题：① H3 存量 374 条未重加密；② login_guard 以 `username|ip` 为键，**攻击者轮换 IP 即可绕过对单一账号的失败累计**，且缺"按 IP 全局限流"，在线上仍可能被分布式撞库；③ HTTPS 仍停留在文档方案。
- 建议：**竞赛必须**——跑重加密脚本或统一口径；答辩主动讲"锁定键含 IP，已知可被轮换 IP 绕过，下一步加按 IP 全局限流 + 验证码"（主动暴露=掌控力）。**长远**——login_guard 增加 `_ip_fail` 全局计数器（同 IP 任意账号累计 N 次即封），生产前置 HTTPS/反向代理。

### 维度 4 多智能体协作的真实性 —— 8.5/10（↑2）
- **核验结论：协商链端到端真实闭合、仲裁真改变输出，首轮"仲裁是摆设"的批评成立地被推翻。**
- 现状：三条链均可走通——天气⇄健康双向（health 发起 risk_query→weather 用最新预警复核→health 仲裁改文案）、报修安全隐患→通知草稿（仍守"紧急通知必须人工发布"停机点）、LLM 协商演示。Arbiter 五条首匹配规则的 decision 值（safety→human / professional→professional）与消费方分支严格对齐，仲裁每次落 agent_logs 留痕。
- 问题：① 触发面仍偏窄——"真分歧仲裁"目前只在 health⇄weather 一条链上，其他 7 个角色之间仍是确定性事件转发；② 黑板为进程内带锁结构，多 worker（uvicorn --workers N）下各进程黑板不共享，跨进程协商会断（演示单 worker 无影响）。
- 建议：**竞赛必须**——把 health⇄weather 这条链打磨成 30 秒的"对抗式协作"演示脚本（先让天气说"可正常活动"，再输入"头晕"，展示系统如何被仲裁拉回保守并转人工），这是最能区别于"单 Agent 套壳"的镜头。**长远**——黑板后端抽象接口，给出 Redis 实现占位以支撑多 worker。

### 维度 5 适老化与用户体验 —— 8/10（↑1）
- **核验结论：从"形式大字版"向"真实可用"又走了一步，诚实化处理值得肯定。**

## 6. 答辩问答库（20 问，按整改后状态重写；含"诚实且加分"的答法与避坑）

> 用法：每题给【评委真实意图】→【推荐答法要点】→【避坑】。

**Q1 你们 LLM 默认是关的，那这系统到底是不是 AI？**
- 意图：质疑"规则套壳冒充 AI"。
- 答法：这是**刻意的成本与稳定性设计**，不是没有 AI。主链路规则优先保证政务场景 7×24 确定、可控、近乎零成本（可现场看 llm_usage 的 token 费用）；在三个规则搞不定的点接 LLM——政策弱命中 RAG 生成、口语化意图兜底、跨部门协商——用 `.env.demo` 一键切到"AI 增强档"，现在就可以演示。规则为骨、LLM 为脑、关键节点人确认。
- 避坑：不要说"我们全自主 Agent"；也不要被带得去争论"规则不算 AI"。

**Q2 怎么证明政策回答不是大模型瞎编的？**
- 意图：幻觉。
- 答法：现场讲 policy_rag 三重保险——强制 JSON 返回引用下标、下标必须落在本次检索集合内、引用标题用数据库真实行回填而非模型文本；越界/解析失败/模型说"资料不足"一律弃用转人工；零检索结果绝不生成。可现场跑 test_policy_rag。

**Q3 多智能体是不是写死的顺序调用剧本？**
- 意图：质疑 MAS 真实性。
- 答法：演示 health⇄weather 反向协商——健康顾问**主动发问**、天气守护用**最新预警重新复核**（不信任上游缓存）、当"天气说可活动但症状高危"出现真实分歧时由 Arbiter 裁决并**改变最终回复和是否转人工**；仲裁规则是声明的、可审计、每次落 agent_logs。强调触发条件来自运行时数据而非固定脚本。

**Q4 仲裁器凭什么谁说了算？规则谁定的？**
- 意图：仲裁合理性。
- 答法：固定优先级——合规否决 > 人身安全转人工 > 专业领域采专业 Agent > 费用/不可逆转人工 > 数据版本取最新 > 无法裁决默认保守转人工。这是把基层治理"安全兜底、专业归口"的制度显式编码，且默认永远偏向人工，符合政务风险偏好。

**Q5 你说用了 AES-256-GCM，怎么证明不是自己拼的？**
- 意图：加密真实性（首轮这里是硬伤）。
- 答法：现在用的是 cryptography 库的 AESGCM，密文带 `g1$` 版本前缀和随机 nonce，可现场 `from utils.crypto import get_crypto` 加解密看前缀；历史密文用旧算法保留在 LegacyStream、参数对齐保证可解，并提供 reencrypt 脚本做密钥/算法轮换——**版本化加密 + 可轮换本身就是合规加分项**。避坑：别声称"全库已 GCM"，如实说"新写入 GCM、历史兼容、可一键轮换"。

**Q6 演示账号能不能被外人用来登录？**
- 意图：越权（首轮 P0）。
- 答法：非 DEMO_MODE 下 demo 端点在中间件层直接 403、路由内二次校验、角色参数枚举校验，三重关闭；现场可跑 test_demo_login_disabled_in_prod、JWT 篡改/alg=none/越权三个负向测试。

**Q7 JWT 被篡改或用 alg=none 能绕过吗？**
- 答法：不能，有专门负向测试 test_jwt_tampered_rejected / test_jwt_alg_none_rejected，可现场跑红。

**Q8 居民能不能调网格员的接口？**
- 答法：不能，test_role_escalation_resident_to_grid_endpoint 用居民 token 打 grid 端点断言 403；权限在依赖注入层统一校验。

**Q9 登录接口能被暴力破解吗？**
- 答法：有失败锁定（5 次锁 300 秒，滑动窗口+线程锁）。**主动补一句**：当前锁定键含 IP，已知分布式撞库可轮换 IP 绕过，已排上按 IP 全局限流——主动暴露已知边界比被挖出来强。

**Q10 SQLite 撑得住吗？为什么不用 PostgreSQL？**
- 答法：WAL 模式下读写分离、单街道量级（万级居民/千级工单）完全够；schema 走 `_mN_` 迁移注册、当前 v41/44 表，迁移 PG 只需替换连接层，已为此不使用 SQLite 私有方言。现场可用混合压测 p95/p99 数据佐证。

**Q11 你这压测是不是只压了不用登录的静态接口？**（首轮质疑点）
- 答法：现在 benchmark_business 先登录拿真实 JWT，按报修/对话/通知/政策/建工单的业务比例混合，输出 p50/p95/p99 和错误率，脚本和 markdown 结果都在，可当场复跑。

**Q12 你说有 495 个测试，数字怎么保证不和代码脱节？**
- 答法：`scripts/check_claims.py` 实时统计用例数/schema/路由/角色/表数，材料数字以它为准，从流程上杜绝"文档写 328、实际 457"这种漂移。

**Q13 老年人不会说普通话、环境吵，语音能用吗？**
- 答法：如实说——当前用端侧 Web Speech（零成本、隐私不出端），已对不支持/拒麦克风/非 HTTPS/无网络/长时间无声做显式降级和 60 秒上限，不会把老人卡死；服务端 ASR 与方言是明确预留的下一阶段，不夸大现状。适老真正的底座是大字、长按防呆、SOS 倒计时、手动 120 这些不依赖语音的设计。

**Q14 紧急求助真的会自动打 120、联系家属吗？**
- 答法（诚实是关键）：H5/浏览器**无法**自动连续拨号，我们不做虚假承诺：一键发求助留痕并通知审核通过的紧急联系人，同时提供直达 `tel:120` 的大按钮由老人/家属手动拨出。比"假装会呼叫"更负责。

**Q15 DEMO 里工单自己在流转，这效率能算你们的治理成效吗？**
- 答法：不能，也绝不这么算。DEMO_AUTO_WORKER 只是演示用的闭环机器人，材料里明确标注"不代表真实成效"，生产和正式演示会关掉回到人在环；我们只对"机制完整性"负责，不背未经真实社区验证的办结率。

**Q16 这么多 Agent，维护成本和调用成本会不会很高？**
- 答法：正因为规则优先，绝大多数请求零 LLM 调用，llm_usage 表带单价可算出每千居民月成本（给数字）；Agent 是声明式角色（配置驱动），新增角色是加配置而非重写框架。

**Q17 双后端（FastAPI + Streamlit）是不是架构混乱？**
- 答法：主线只有 FastAPI+Vue 一个；Streamlit 是早期原型备线、api.py 是扣子插件入口，三者只共享 data/ 服务层，旧链已计划迁入 legacy 冻结。讲"演进留痕"而不是"三套并行"。

**Q18 数据合规（PIPL）做到哪一步？**
- 答法：敏感字段加密落库、展示/导出脱敏、注销匿名化、activity_log 审计留痕、权限校验、合规审计员角色做输出侧敏感词/引用校验；HTTPS 与三方数据责任边界是部署期事项，已文档化。不声称拿到等保/备案（没有就是没有）。

**Q19 和现有 12345 / 街道系统是什么关系，会不会重复建设？**
- 答法：定位是街道/社区**最后一百米**的协同与适老交互层，不替代 12345，而是通过工单/舆情接口对接（外部源适配位已留）；落地路径是先在一个街道做脱敏试点再谈替换。

**Q20 项目最大的不足是什么？**（必问，答得好是加分题）
- 答法（真诚且有掌控感）：三点——一是生成式能力为控本默认关闭，需要演示档开关和离线质量成绩单，正在补；二是真实协商目前集中在健康⇄天气一条样板链，跨其他角色的自主协商还要扩；三是尚未经过真实街道的长期试点，所有成效数字目前只到"机制可验证"而非"治理有效"。我们选择先把可验证的工程底座做扎实，再谈规模化。
- 避坑：别回答"我觉得我们没什么不足"；也别自曝 H2/H4 这种"没清 lint、条件写反"的工程小辫——那些赛前就该修完。

### 话术红线（避坑清单）
- 不说"9 个全自主 AI""100% 防幻觉""全库 AES-GCM""自动呼叫 120""办结率 X%"（任一被证伪都伤根基）。
- 统一口径："规则为骨、LLM 为脑、关键节点人确认""新写入 GCM、历史版本化兼容可轮换""机制已验证、成效待试点"。
- 任何数字先跑 check_claims / pytest 再出口。
