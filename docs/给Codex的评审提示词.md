# 给 Codex 的评审提示词（复制下面整段给它）

> 用途：让 Codex 通读项目 → 给出评价 → 生成项目报告 → 给出未来建议与规划。
> 设计要点：**只读评审、明确禁止改代码/动库**（避免把上台前的状态改坏）；
> **要求它自己复算而不是相信文档**（本项目所有数字都有脚本可复核）。

---

```
请对我这个项目做一次**完整的通读评审**，然后产出「项目报告 + 未来建议与规划」。

## 一、你的角色
你是资深技术评审 + 创业/竞赛评委。既看工程实现，也看产品价值与可演示性。
请**讲真话、给证据**，不要客套式表扬；不确定的地方明确说"未验证"，不要编造。

## 二、项目位置与背景
- 工作目录：当前仓库根（`campus-insight-agent`）
- 项目：社区先知 CommunityInsight —— 基层治理·网格化多智能体系统（接诉即办平台）
- 三端：居民端 /resident、网格员端 /grid、老年端 /elderly；FastAPI(:8000) + Vue3 + SQLite
- 我是**单人参赛**的大二学生，**马上要现场演示**（这是最近的关键节点）

## 三、⚠️ 硬边界（这次是"评审"，不是"开发"）
1. **不许修改任何源码/文档/配置**（包括不要"顺手修一下格式"）。你只读、只输出报告。
2. **不许动数据库**：不要 seed、不要 DELETE/UPDATE、不要删 `data/community_insight.db`，
   也不要碰 `.env` 与 `.shots/db-backup-*.db`（里面是演示数据的唯一真源与密钥）。
3. **不许杀 :8000 上的服务进程**。如果你要跑 `pytest`，先告诉我"需要你手动停服务"，
   等我确认；`ruff`、`check_claims.py`、读文件随便跑。
4. 报告写到 `docs/review/Codex-项目评审与规划.md`（**只写这一个新文件**）。

## 四、先读什么（按顺序，别跳）
1. `AGENTS.md` —— 项目约定、架构、**踩过的坑**（这份文件是理解项目的钥匙）
2. `docs/给Codex的交接说明.md` —— 硬约束 + 现状 + **已知未修复项**
3. `docs/spec/dev-log.md` 最后 300 行 —— 最近做了什么、为什么
4. `docs/competition/` 下的材料（创意说明书-提交版 / 技术实现报告 / 演示脚本 / 答辩问答手册 / 上台前清单）
5. 代码主干：`api_web.py`、`api_routes/`、`agent/`（含 `roles/`、`orchestrator.py`、`verifier.py`、`arbiter.py`）、
   `data/`（表结构与迁移 `db_core.py`）、`web/src/{views,layouts}`、`scripts/`（自检与审计脚本）

## 五、必须自己复算的数字（**不要相信文档写的**）
跑这些脚本，用**你实测到的值**写报告；如果与文档不一致，这本身就是重要发现：
- `python scripts/check_claims.py` —— 用例数 / 路由数 / 业务表数 / schema 版本
- `python -m ruff check .` —— 代码规范
- `python -m pytest tests/ -q --collect-only | tail -5` —— 可运行用例数（**只收集不执行**，避免长时间占用）
- 目录规模：`git log --oneline | wc -l`、代码行数分布（`cloc` 或按目录统计）
- 关键事实核对：`agent/roles/__init__.py` 的角色数、`data/db_core.py` 的迁移注册条数

## 六、报告结构（请严格按这个写）

### 1. 项目一句话画像
它到底是什么、给谁用、解决什么问题（≤100 字）。

### 2. 我实测到的事实（先给数字，再给结论）
表格：项目 / 我实测的值 / 文档声称的值 / 是否一致。
**任何不一致都要单独列出来并标注严重度**。

### 3. 分维度评分（每项给分 + 一句理由 + 证据 file:line）
按 10 分制：① 创新性与差异化 ② 技术实现深度与工程质量 ③ 完整度（功能闭环）
④ 数据与算法可信度（可复算性）⑤ 安全与隐私 ⑥ 可演示性与表达 ⑦ 可维护性与可扩展性
最后给一个总分与"在同类学生作品里的位次判断（前 10% / 前 30% / 中游）"，并说明依据。

### 4. 真实短板（按严重度排序，每条必须给证据与影响）
分三档：**致命（会挂演示/答辩）** / **重要（会被评委追问且答不好）** / **一般（锦上添花）**。
请特别去查这几类容易被忽略的地方：
- 有没有"文档说做了、代码里其实没接上主路径"的功能（本项目历史上多次出现这种问题）
- 有没有**跨租户/越权**的数据路径（租户=社区名；读取必须显式过滤、按 id 直取必须过闸门）
- 有没有**静默吞异常后返回成功**、或 fail-open 的安全校验
- 有没有**前后端口径不一致**（页面显示 vs 接口返回）
- 有没有**测试覆盖不到的演示路径**（尤其"用户点了按钮会发生什么"）

### 5. 演示当天风险清单
按"发生概率 × 影响"排，给出**现场可执行的兜底动作**。

### 6. 未来建议与规划（这是我最想要的部分）
分三档，每条写清 **做什么 / 为什么值得 / 预估工作量 / 风险 / 怎么验证**：
- **A. 上台前（几天内，只做低风险高收益的事）**
- **B. 赛后打磨（1~3 个月，把项目变成可复用/可开源/可写进简历的东西）**
- **C. 长期想象（6~12 个月：产品化、真实试点、技术演进）**
并在最后回答一个问题：**"如果只能再做三件事，是哪三件？"**（给理由与优先级）

### 7. 如果我是评委，我会问的 10 个问题
从最狠的开始（会把我问住的优先），并为每个问题给"我该怎么答"的三句话要点。

## 七、输出要求
- 报告写到 `docs/review/Codex-项目评审与规划.md`，中文，Markdown，**不要写成流水账**：
  先结论后证据，能上表格就上表格。
- 凡引用代码，给 `文件:行号`；凡给数字，注明是"实测"还是"文档声称"。
- 最后在文件末尾列一节 **「本次评审未验证的部分」**（诚实标注你没能确认的东西）。
```
