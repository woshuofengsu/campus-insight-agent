## 一、多租户（目标：从"仅预留字段"做成真隔离）

### 1.1 已定结论

| 事项 | 结论 |
|---|---|
| 租户键 | **用社区名**（如"海淀小区"），不用行政区。依据：`user_profile.community` 存社区名、`config.REGION_BY_COMMUNITY` 以社区名为键 |
| v41 现状 | 迁移 `_m41_tenant_column`（`data/db_core.py:673`）只给 3 张表加列并**回填**默认值；业务代码**从不写入** tenant_id → 新数据拿不到租户 |
| 请求侧前提 | `api_routes/deps.py` 已有 `_community_of(uid)`（`:103`，带缓存）与 JWT 的 `community`（`:62`）→ 租户参数可**复用现有属地解析**，无需重造身份体系 |
| **不**改 | `notifications`（14099 行，已按 `user_id` 严格过滤）；agent 内部表（`agent_dialogs/logs/sessions`）本次不铺 |

### 1.2 三个"只在数据层加过滤也会漏"的洞（必做）

1. **缓存键不含租户（已在主线路径复核，比初判更严重）**：
   `utils/cache.py` 是 **`st.cache_data`** 包装（`:2-3`），而它**被主线 FastAPI 路由调用**：
   `api_routes/notices.py:82,86` → `cached_notices_with_stats`（键只有 `notice_type/status/publish_scope/keyword/limit`，`utils/cache.py:120-124`）；
   `api_routes/weather.py:91,92` → `cached_active_alerts`；
   （`cached_proposals_full` 只在 Streamlit 备线 `ui/pages_grid/proposals_mgmt.py:40,127` 用。）
   所以只在 SQL 加 `tenant_id=?` 而不管缓存键，**通知列表会在 15s TTL 内把 A 社区结果发给 B 社区**——
   比不过滤更难排查。v47 必须同步把 tenant/community 并进缓存键。
2. **Agent 工具层整段绕过 REST**：`agent/web_agent_service.py:180-183`（待办：工单/咨询/老年用药全库计数）、
   `:193-195`、`:203`（统计）、`:220-221`、`:227`（搜索）。其中 `:220` 先 `get_issues(limit=1000)` 再按关键词过滤，
   会把**其他社区的工单标题念进 Agent 回复**；页面审计抓不到这类泄漏。
3. **天气预警接口无角色校验 + 无租户维度**：`api_routes/weather.py:89-92` 函数体只有一行、`request` 参数未使用、
   无 `_require_role`；而 `weather_alerts` 表既无城市列也无 `tenant_id` → 任何已登录居民可拿全平台预警。

### 1.3 顺带发现的一处"校验恒被跳过"

`data/db_notice.py:487-501` 用 `communities` / `buildings` 两张表做通知发布范围校验，而**这两张表在本库 52 张表里都不存在**
→ 校验永远不生效，写错小区名会静默变成孤儿通知。若租户判定要依赖 `publish_scope`，必须先修它。

### 1.4 教训（写给以后的自己）

本项目的**查询面不止 REST 层**：data 层函数同时被 **agent 工具层**、**Streamlit 备线**（`app.py` / `ui/`）、
**缓存层**三处复用。任何"按接口清单做隔离"的方案都会漏。

## 二、老年端深化

### 2.0 本轮已修：主动关怀的时区去重 bug（附带发现 A）

`data/db_care_proactive.run_followup` 拿**本地日期**比库里的 **UTC 时间列**做"今日已回访"去重，
且插入 `activity_log` 时没写 `created_at`（落到 `CURRENT_TIMESTAMP` = UTC）。两者在本地 0:00–8:00 必然错配。
**准确结论**：错配窗口（本地 0–8 点）与"21:00–8:00 静默"完全重叠，所以**生产上没真发出重复回访**——
但传假 `now` 的测试必然失败（2026-09-24 实测把它跑红），且静默时段一改就会真的重复打扰居民。
已修：新增 `utils/timeutil.local_to_utc_naive` / `utc_stamp_of_local`，去重与时间戳统一按 UTC 写入；
`list_inactive_elderly` 的截止时间也从本地 `datetime.now()` 改成 `utcnow()`。回归见 `tests/test_timeutil_utc.py`。

### 2.0.1 附带发现：感知统计的日界同源问题（下一批修）

同一类"本地日期 vs UTC 列"的错配在统计模块里**成片存在**（约 10 处查询）：
`data/db_perception.py:36,40`（生成本地日期）→ `:101,104,110,115,123,128,151,161,179,189`（拿去比 `date(reported_at)`/`date(resolved_at)`），
`data/db_health.py:58`、`data/db_policy.py:280,837,1472`、`agent/analytics.py:68`、`agent/closed_loop.py:62` 同类。
影响：**治理大屏/统计的"今日"在本地 0:00–8:00 会算错日界**（把前一天的 UTC 归到别的日子），
不影响安全与隔离，属显示正确性问题。修法二选一：① 统一按 UTC 日统计（简单，但"今天"= 08:00–08:00 北京）；
② SQL 侧把 UTC 列转本地日（`date(col, '+8 hours')`，需把时区偏移做成配置）。**留到 B3/B6 处理。**

### 2.1 四个"做了但没生效"

| # | 问题 | 证据 |

| 2 | **无人应答检测没有定时触发**：`_check_elderly_safety()` 不在 `scripts/scheduler.py:105-144` 的调度里，只在 Agent 聊天观察阶段（`agent/engine.py:256`）顺带跑 → 是"文案 + 偶发"，不是闭环 | 同上 |
| 3 | **网格员"重点关注老人"是孤儿**：`get_elderly_overview()`（`db_elderly.py:281-302`）无 API；`/manage/inactive` 虽存在（`api_routes/elderly.py:399`）但前端 `web/src/api/index.js` 没有对应方法 → Vue 端调不到 | 同上 |

### 2.2 隐私口径缺口

`elderly_profile.emergency_contact` 是 JSON，里面**存明文手机号**；而 `scripts/audit_phone_encryption.py:37`
只扫"列名含 phone 的列"，**永远查不到 JSON 里的号码**。P3 要做"通知子女"就必须先把这处口径定下来，
否则通知链本身就是在扩散明文。
