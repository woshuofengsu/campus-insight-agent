# 社区服务智能体 · 改造方案（蓝图）

> 依据：`docs/spec/` 下的 7 个模块需求 + 跨模块联动修正报告。
> 本文档定义改造的总体原则、数据模型、分阶段计划与关键技术决策。

## 一、总体原则

1. **在现有基础上演进**，保留 Agent 内核（OODA 循环 / LLM 语义路由 / 反幻觉 enforce+reflection / 三层回退），这是项目的核心竞争力。
2. **重构数据层与业务层**，把"演示 demo"升级为文档要求的完整生产级系统。
3. **角色映射**（已确认）：网格员 = 负责人（含各专项负责人权限）；维修人员仅记录姓名电话、无系统账号；家属作为居民端可选身份（代报）。
4. **演示模式开关**（已确认）：保留 `DEMO_AUTO_WORKER`，默认演示自动办结保证流畅；切到真实人工流程时按文档状态机逐级手动推进。
5. **留痕统一**：全局留痕统一走 `activity_log`，扩展 `before_value` / `after_value` / `module` 字段。

## 二、数据模型设计（schema v11+）

### 通用
- `activity_log` 扩展：`module`（模块来源）、`before_value`、`after_value` 字段，满足跨模块追溯与前值/后值留痕。

### 报修（工单）
- `community_issues` 扩展字段：
  - `issue_type`（室内/室外）、`reporter_name`、`reporter_phone`
  - `audit_status`（待审核/已审核待派单/退回补充/已撤回/已关闭/待协商/已转出）
  - `approved_at`（审核通过时间=计时起点）、`assignee_name`、`assignee_phone`
  - `resolve_note`（处理结果）、`photo_before`（现场照片 JSON）、`photo_after`（维修后照片 JSON）、`no_photo_reason`
  - `is_agent_report`、`agent_name`、`agent_phone`、`agent_relation`（代报）
  - `is_violation`（违规搭建标记）、`non_community_responsibility`（非社区责任）
  - `supplement_count`（补充次数）、`supplemented_at`
- 新表：
  - `issue_drafts`（报修草稿，7 天）
  - `safety_reminders`（安全隐患提醒记录，不进入工单状态机）
  - `issue_supplements`（居民补充信息历史）

### 提案
- `proposals` 扩展字段：
  - `is_public`（公开/私有）、`audit_status`、`audit_opinion`
  - `visibility_confirmed`、`published_at`、`voting_started_at`、`voting_ended_at`
  - `reopen_count`（重新执行次数）、`executor_dept`、`execution_result`、`decision_reason`
  - `attachment_public`（附件是否公开）
- 新表：
  - `proposal_votes`（匿名投票：proposal_id、score、created_at，**不存 user_id**）
  - `proposal_vote_dedup`（防重复：proposal_id、user_id，仅系统内部，不记分数）
  - `proposal_drafts`（提案草稿）

### 天气
- 新表：
  - `weather_cache`（缓存降级）
  - `weather_alerts`（极端天气预警）
  - `weather_check_tasks`（负责人检查任务 + 检查清单）

### 疾病预防
- 新表：
  - `health_contents`（内容发布：草稿/待审核/审核通过/已发布/已下架）
  - `health_consults`（居民健康咨询：待回复/已回复/继续回复/已结束/已关闭）

### 通知发布
- 新表（区别于现有"私信" `notifications`）：
  - `notices`（广播通知：6 类型、发布范围、定时、紧急、附件、草稿/待发布/已发布/已下架）
  - `notice_reads`（已读记录：notice_id、端类型、user_id）

### 老年端
- 新表：
  - `medication_reminders`（用药提醒：待审核/审核通过/审核不通过/已暂停/已结束）
  - `emergency_contacts`（紧急联系人：待审核/审核通过）
  - `emergency_calls`（紧急求助 + 联系拨打记录）

### 政策问答
- `knowledge_base` 扩展：`audit_status`、`audit_opinion`、`source`、`effective_date`、`expire_date`、`version`、`cite_count`、`plain_interpretation`、`summary`
- 新表：
  - `knowledge_versions`（版本历史）
  - `policy_questions`（提问记录：已自动回答/已转人工/已回复/已结束/需线下沟通）

## 四、关键技术决策

1. **状态用字符串**（保持现有风格，如 `待审核` / `已派单`），不用枚举表。
2. **留痕前值/后值**：在业务函数里更新前先读旧值，写 activity_log 时带上。
3. **投票匿名**：`proposal_votes` 只存分数+时间；`proposal_vote_dedup` 只存 user_id 防重复；两表物理隔离，任何查询不 JOIN。
4. **通知区分**：`notices`（广播）+ `notice_reads`（已读）；现有 `notifications`（私信）保留用于系统定向通知。
5. **数据诚实声明**保持不变：seed 演示数据，上云重置。
6. **现有 328 测试**：旧测试随重构同步改写（用户已授权可删改增加）。
