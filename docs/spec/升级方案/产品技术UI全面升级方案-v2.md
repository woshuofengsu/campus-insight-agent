## 从功能堆叠的原型，升级为清楚、可信、可验证的社区服务产品

**方案版本：v2.0｜制定日期：2026-09-27｜适用对象：单人大二参赛者**

> **核心决策：未来四个月不继续横向堆功能。以“模糊诉求的可靠办理”为唯一主线，做实授权、信息补齐、状态迁移、真实转人工和可复算对照实验。**
>
> 上台前追求稳定和可信；赛后证明技术贡献；真实试点后才讨论数据、流程经验和交付能力形成的壁垒。复制代码仍然可能，不能承诺四个月内建立不可复制的护城河。

>

## 本版先做的取舍

**v2 替代 v1 作为后续执行依据。它不是给旧方案再加一堆功能，而是把产品、可靠性、UI、实验和交付重新排序。**

| 维度 | v1 的不足或需要补强处 | v2 的调整 |
|---|---|---|
| 产品定位 | 技术方案完整，但首次使用者未必一眼理解价值 | 每端围绕下一步任务组织页面；报修闭环成为统一产品主线 |
| UI | 只有原则，没有逐页规格和预算 | 补截图诊断、设计令牌、三端线框、组件、状态与验收 |
| 排期 | 12 周方案没有计入完整 UI 工作量 | 默认 16 周；原 200h 主线＋64h UI＋56h 缓冲=320h |
| 技术贡献 | 容易被理解成“更多角色＋更多机制” | 安全机制作为工程底线；协作收益用独立公平实验判断 |
| 数据可信度 | 算法指标之外，前端业务数字也可能误导 | 增加统计总数、预览、时间窗、加载失败的契约 |
| 交付方式 | 一次完成全部功能会产生大规模回归 | 按单条用户旅程纵向交付，先一页/一条链验证，再复制到其他页 |
| 比赛表达 | 功能与数字偏多 | 一个问题、一个闭环、一个失败恢复、一个真实实验结果 |
| 长期价值 | 容易把开源框架组合说成壁垒 | 分别积累评测质量、可靠性经验和真实交付能力 |

## 1. 升级目标：你最终要证明什么

### 1.1 面向用户的一句话

**居民不必一次把问题说完整，网格员仍能收到信息清楚、责任明确、状态可追踪的待办；系统处理不了时，能如实、完整地交接。**

首个主场景限定为：**单社区、非紧急公共设施报修**。例如楼道灯、电梯一般故障、公共设施损坏；涉及即时人身危险时，系统提供明确的人工/既有紧急联系入口，不让模型自行承担救援调度责任。

主场景选择理由：

- 你已有居民提交、网格办理、居民反馈的业务骨架，不需要重做产品。
- “信息不完整、反复补问、重复报修、交接丢上下文”可以被测量。
- 对照方案容易搭建，能够检验多角色协作是否真的有增益。
- 能把权限、状态机、幂等、失败反馈集中在一条可演示链路里。

### 1.2 分层目标

| 时间尺度 | 应达到的结果 | 不能据此宣称 |
|---|---|---|
| 几天内，上台前 | 一条真实可演示闭环；口径统一；已知缺陷边界明确 | 全系统生产可用、所有租户已彻底隔离 |
| 16 周 | 可复现的可靠办理原型、授权与故障验收、与合理基线的实验报告 | 行业领先、现实场景 100% 成功、已经形成商业壁垒 |
| 6～12 个月 | 经授权的小范围试点、真实流程改进证据、他人可部署维护 | 在没有合作或付费证据时宣称商业化成功 |

### 1.3 建议放弃的“伪壁垒”表述

| 原表述 | 更准确的升级表述 |
|---|---|
| 我有九个智能体，所以技术复杂 | 我比较了不同编排方式在特定任务上的效果，保留确实有收益的协作 |
| 我有很多代码和测试，别人做不了 | 关键权限、状态和故障行为有明确契约，并可复现验证 |
| RAG 命中率 100%，能解决政策问答 | 在固定样本和语料版本上测量检索与引用效果，并公开无答案和失败样本 |
| 加密了手机号，所以隐私安全 | 加密、访问授权、通知范围、日志脱敏和数据保留分别验证 |
| 有人工兜底，所以系统可靠 | 只有真实处理包持久化后才显示已转交，失败可见且可恢复 |

## 2. 技术贡献与壁垒：分别建设，不混为一谈

### 2.1 建议的技术课题

**“面向不完整社区诉求的约束式协作与可验证办理”**

这是一项待验证的工程技术方向，不是本方案确认的新算法。论文或专利级新颖性仍需独立文献检索和论证，不能因为给方法命名就视为原创。

建议拆成三个可解释的技术点：

1. **约束式信息补齐。**把居民原话转换成带来源、缺失项和冲突项的任务对象；只有缺少影响办理的字段时才追问。
2. **受控业务执行。**角色可以提出建议，但所有写操作统一经过权限、状态、确认与幂等检查；自然语言不能直接成为办理事实。
3. **基于事实的回复与交接。**面向居民的状态由已提交的业务记录生成，人工处理包可追溯到原话、补充信息和失败原因。

这三个技术点共同解决“看起来答对了，实际没办成或办错了”的问题。

### 2.2 逐步积累的优势

| 积累项 | 形成方式 | 为什么复制代码不等于得到相同效果 | 当前状态 |
|---|---|---|---|
| 场景评测资产 | 真实需求访谈、经授权的脱敏表达、独立标注和失败分类 | 对方仍需理解任务边界、维护数据质量和形成代表性案例 | 现有 RAG 小样本可作起点，办理评测需新建 |
| 可靠性经验 | 记录权限缺口、超时、重复请求、错投通知等故障及回归 | 有价值的是完整故障模型和恢复经验，不只是某个函数 | 已有缺陷证据，可转成测试契约 |
| 流程适配与交付 | 与真实接单方对齐责任、字段、反馈和现有工作流 | 社区协作关系、运营规则和接入经验不能由复制 UI 直接获得 | 尚未验证试点 |
| 实验结果与复现质量 | 固定基线、样本和配置，公开失败与成本 | 形成可信技术履历，但公开结果本身不是排他性壁垒 | 需要升级评测方法 |

**区分：**开源不等于放弃竞争力；也不能一边完全公开数据和方法，一边声称这些内容不可复制。学生阶段更应优先积累可信成果与专业能力。

D3、D4 可能超过赛前剩余时间；它们不是“顺手改几行必然安全”。上台前只做确认能够完成验证的部分。**本方案不会自动执行这些修复。**

### 建议五分钟演示

1. 30 秒：说明用户与一个具体痛点。
2. 60 秒：居民给出不完整报修，系统只追问必要信息。
3. 60 秒：用户纠正一个字段，系统展示最终摘要，确认后生成真实编号。
4. 90 秒：网格员按页面真实流程处理，居民端看到更新。
5. 40 秒：展示一个受控失败或重复提交案例，说明不会假成功/重复建单。
6. 20 秒：说清实验范围与未完成边界。

**步骤 2、3、5 的升级行为只有实现并验收后才能演。**否则演示当前已实现行为，用设计图明确标注“下一阶段方案”。

## 6. 目标架构：建议与业务事实分开

### 6.1 保留现有技术栈，改进关键边界

继续使用 FastAPI、Vue3 和 SQLite 完成首轮升级。当前问题主要不是数据库品牌或框架能力，而是业务约束没有集中承载。

建议主链：

**居民输入 → 可信身份上下文 → 任务提取/补齐 → 草稿与确认 → 受控命令执行 → 业务记录与事件 → 事实回执 → 居民/网格员界面**

角色协作可参与“理解与建议”，不能自行绕过命令执行层写库。安全校验、授权和状态规则必须是代码约束，不能依靠提示词要求模型自觉遵守。

### 6.2 最小数据契约

| 对象 | 建议字段 | 关键约束 |
|---|---|---|
| ActorContext | user_id、role、tenant_id、授权关系/职责范围、session 信息 | 来自可信服务端认证与授权，不采信模型或请求体自行声明 |
| TaskDraft | draft_id、业务类型、字段、缺失项、冲突项、field_sources、version、status | 每个关键字段能对应原话/用户确认；版本避免旧草稿覆盖 |
| Command | command_id、actor、resource_id、action、expected_version、idempotency_key、payload | 参数由白名单校验，授权和状态合法后才能执行 |
| ExecutionReceipt | command_id、resource_id、结果状态、实际提交时间、可恢复原因码 | 有真实提交事实才出现“已提交/已转交”等用户表述 |
| DomainEvent | event_id、tenant_id、资源、事件类型、时间、最小必要摘要 | 与业务状态在事务内一致写入，敏感信息最小化 |
| HandoffPackage | handoff_id、原始诉求、已确认字段、未决问题、尝试结果、交接原因、状态 | 不等同于工作人员已接单；处理包可查询和领取 |
| DeliveryRecord | event_id、recipient_id、channel、delivery_status、attempts | 收件人先授权，重试去重，不把通知失败误称业务失败 |

这些是逻辑对象，不意味着必须新建七张表。实施时先复用现有字段和表；只有确实缺失的能力才增加迁移，继续遵守现有版本化迁移约定。

### 6.3 草稿、命令和工单状态分开

- **草稿状态：**收集中 → 待用户确认 → 已消费 / 已取消 / 已过期。
- **命令结果：**成功 / 拒绝 / 待确认结果 / 失败。
- **业务工单状态：**沿用现有审核、派单、处理、反馈等状态，不在同一次升级中重新命名全部状态。
- **人工交接状态：**待领取 → 已领取 → 处理中 → 已回复/关闭。
- **通知状态：**待投递 → 已投递 / 待重试 / 放弃并告警。

网络超时可能意味着“结果未知”，而不是确定失败。客户端应查询原请求结果，不能立刻换一个 id 无限制再提交。

### 6.4 必须守住的六条不变量

1. tenant、角色与所有权不匹配的命令不能产生业务副作用。
2. 同一幂等键、相同语义请求重复发送，返回同一业务结果；同键不同内容拒绝。
3. 任何“已创建/已转交”提示都能找到对应持久化对象。
4. 已取消或旧版本草稿不能覆盖新版本。
5. 通知接收者必须拥有对应信息的读取权限。
6. 失败不会自动升级权限、绕过确认或保存未脱敏原文。

幂等键要限定用户、社区和操作范围，保存请求摘要及执行结果；不能只用“文本相同”判断重复，因为两次相同描述可能是两次合法业务。可参考 AWS 对调用方请求标识和重试安全的工程说明。[AWS Builders’ Library：Making retries safe with idempotent APIs](https://aws.amazon.com/builders-library/making-retries-safe-with-idempotent-APIs/)

### 6.5 SQLite 阶段的可靠写入

首轮建议使用业务事务与简单 outbox：

- 同一事务写入业务状态、执行结果和待通知事件。
- 事务提交后再投递通知；投递失败保留待处理记录。
- 领取事件和更新结果需要原子条件，事件与收件人组合去重。
- 定义重试次数、退避和人工检查入口，不无限重试。
- 单实例可先用简单任务循环；不要把进程内队列当持久化交接保障。
- 不宣称端到端 exactly-once；目标是可重试、可去重、结果可核对。

数据库迁移、并发策略与锁等待需在独立环境验证，不能用唯一演示数据库试错。

## 7. 核心技术升级一：约束式诉求理解与补齐

### 7.1 从“猜意图”升级到“可解释的任务对象”

以报修为例，先确定最小必填项：设施/问题、位置、故障描述；联系人和联系方式是否必要由业务规则决定，能从授权资料获得时不重复采集。

每个字段记录：

- 原始文本证据或合法结构化来源。
- 当前值与用户是否确认。
- 缺失、歧义或相互冲突的状态。
- 来源与更新时间，避免把后来的纠正当成额外并列信息。

若使用模型置信度，只把它当辅助信号。未经校准的“模型自报 0.9”不应成为安全放行依据。

### 7.2 追问策略

| 情况 | 系统应做的事 | 不应做的事 |
|---|---|---|
| 缺少影响派单的位置 | 一次询问一个必要问题，并提供已有可选位置 | 编造楼号或追问一长串无关字段 |
| “3 号楼，不对，是 5 号楼” | 明确新值，保留修正来源，展示最终摘要 | 两个楼号都提交或恢复旧草稿 |
| 用户只想咨询 | 解释可办理范围，征求提交确认 | 未确认就创建工单 |
| 同一描述可能已提交 | 展示可能重复项，确认是查看进度还是新问题 | 凭文本相似度直接删除或合并用户诉求 |
| 缺少权限 | 拒绝该操作并解释合法入口 | 通过继续追问获取更多私人信息 |
| 多轮仍无法确定 | 生成真实交接包，说明未决问题 | 用“系统已处理”掩盖理解失败 |

优先用简单的必填项、冲突规则和固定追问模板建立强基线；模型只用于规则难覆盖的表达提取与解释。

### 7.3 对话中止与恢复

设计显式的新建、继续、取消与过期行为。取消应使旧草稿失效；新问题不得自动继承旧位置或联系方式；恢复时先显示摘要供用户确认。

验收用例至少包括：中途刷新、换端、用户纠正、取消重开、两个标签页同时编辑、提交后再次发送旧确认。

## 8. 核心技术升级二：有边界的协作机制

### 8.1 九角色注册可以保留，但不要求每次全部参与

建议主线最小角色：

- 接待/提取角色：识别业务类型，整理原话。
- 业务角色：提出补问或办理建议。
- 校验组件：检查结构、来源、权限及状态；不是让另一个模型替代授权代码。
- 人工交接模块：将失败或不确定任务交给真实队列。

通知、健康、天气等角色仅在明确事件触发且有证据需求时参与。

### 8.2 协作触发策略

先定义容易解释的规则：

- 正常报修字段齐全：走固定办理链，不协商。
- 信息冲突：补问用户，而不是让多个角色替用户猜测。
- 权限冲突：直接拒绝，不由角色投票放行。
- 跨业务问题：只有输出需要另一个专业模块时才请求一次协作。
- 连续无法确认：进入人工处理包，不用无限协商增加延迟。

限制每次协作调用数、耗时和预算；数值先通过小规模测量决定。模型调用结束后才判“超时并重做”可能重复副作用，因此模型建议和业务提交需要解耦。

### 8.3 技术实验应回答的假设

- H1：字段来源与冲突管理能否减少错误字段提交？
- H2：按需协作相对固定流程，是否在复杂任务上提高成功率？
- H3：新增机制是否增加了不必要追问、延迟或成本？
- H4：结构化交接是否减少工作人员再次询问信息？
- H5：安全约束是否在故障和提示注入下仍能阻止越权副作用？

假设可能不成立。负结果也有价值：它帮助你删掉没有收益的角色和调用。

## 9. 核心技术升级三：真正可办理的人工交接

### 9.1 处理包内容

保留最少必要信息：原始诉求、已确认字段、用户纠正、已尝试步骤、失败原因、待工作人员确认事项、关联业务编号、合法联系渠道。

不得将模型推断写成“用户已确认”，不得携带与处理无关的健康或其他个人信息。对话记录可按权限展开，而不是无差别复制给所有网格员。

### 9.2 负责人界面

网格工作台提供真实的“待领取/我处理中”列表，包含时间、原因、优先级依据与处理状态；支持领取、退回补充、回复、关闭，关闭必须填写结果。

“已交接”与“有人已接单”分开显示。社区未定义值守和响应时限时，不承诺一定几分钟内联系。

### 9.3 故障场景验收

| 故障点 | 预期结果 |
|---|---|
| 建包前数据库失败 | 明确未转交；不生成虚假编号或成功承诺 |
| 建包已提交、响应丢失 | 用原幂等键查询/重试，返回同一包 |
| 建包成功、通知失败 | 包仍可从队列找到，通知待重试；用户文案反映实际状态 |
| 两名网格员同时领取 | 一个领取成功，另一个看到已被领取 |
| 工作人员未处理 | 到达约定阈值提醒或人工检查，不偷偷标记完成 |
| 协商次数达到上限 | 真建包或明确建包失败，不只修改回复状态 |

## 10. 对照实验：让“有技术贡献”成为可验证结论

### 10.1 对比四种方案

| 组别 | 实现 | 目的 |
|---|---|---|
| A：固定规则/表单流程 | 必填项校验、固定追问、相同业务工具 | 强而合理的低成本基线 |
| B：单角色模型 | 一个模型完成提取与补问，使用相同受控工具 | 检验多个角色是否必要 |
| C：现有多角色方案 | 冻结本次改造前的编排逻辑，在隔离环境运行 | 建立项目自己的旧版本对照 |
| D：升级方案 | 字段来源、按需协作、受控执行、事实回执 | 验证升级后的净收益 |

不能故意把 A 做成不会追问的弱基线；不能给 D 更多知识或更好的工具而把收益全部归因于协作。

授权和副作用实验独立报告。用于比较编排收益时，A/B/C/D 尽可能共用同一安全业务执行层；旧版本未修复行为只在独立安全回归实验里测，不能在真实数据上运行。否则实验无法分辨收益来自“更聪明”还是“补了漏洞”。

### 10.2 数据集：先 120 条，再扩到 240 条

**16 周最小版本：**

| 子集 | 数量 | 用途 |
|---|---:|---|
| 开发集 | 40 | 设计字段和追问规则，允许迭代 |
| 冻结测试集 | 60 | 最终方案比较，调试时不查看逐条答案 |
| 安全与故障集 | 20 | 越权、重复提交、存储失败、草稿冲突等专项验收 |
| 合计 | 120 | 不把 20 个安全场景混入普通任务成功率分母 |

60 条测试集可初步覆盖简单完整、缺信息、纠正冲突、多步交接、边界/无法办理五组，每组 12 条。这个分组是便于排错的工程设计，不代表真实用户分布。

若时间充足，扩展为开发 80、冻结测试 120、安全故障 40，共 240 条。不得把从同一模板换几个词的题目随机分到训练与测试两侧；按任务来源、模板族和表达来源分组隔离。

### 10.3 每条案例必须带什么

case_id、版本、来源类型、初始角色/社区、对话输入、任务约束、可用业务数据、期望关键字段、合法最终状态、禁止副作用、允许的人工交接条件、评分规则。

真实语料必须获得使用授权并脱敏；没有真实来源时明确标注合成案例。建议请老师或同学盲审至少 20% 样本的答案与评分，记录分歧，不能编造“双人一致”。

### 10.4 指标与分母

| 指标 | 定义 | 说明 |
|---|---|---|
| 任务完成率 | 达到正确终态且无违规副作用的任务数 / 适用任务数 | “返回一句合理话”不算完成 |
| 字段正确率 | 正确的必填字段数 / 应填写字段数 | 与任务成功率分开报 |
| 不必要追问 | 已有充分信息仍追问的次数 / 任务数 | 避免只靠多问提高准确率 |
| 人工交接质量 | 按预设清单评分；另记录接单者再次询问次数 | 应由实际阅读处理包的人评价 |
| 假成功数 | 声称已办理但缺业务事实的次数 | 安全质量门禁要求测试中为 0 |
| 越权副作用数 | 未授权读/写/投递成功的次数 | 任一出现即阻断真实试点 |
| 重复业务对象数 | 同一幂等请求重复执行产生的额外有效对象数 | 测试中要求为 0 |
| 延迟 | 从输入到用户可见结果的 P50/P95 | 区分含模型、纯规则和人工等待 |
| 成本 | 每次任务实际模型调用/token/费用 | 价格随供应商变化，实施时按账单配置，不写死宣传值 |

人工介入率不能越低越好：对于本应拒绝或升级的任务，正确转人工本身就是成功行为。普通任务、风险拒绝、人工交接分别统计。

### 10.5 执行与统计

1. 用约 20 个开发任务作预实验，估算单轮时间、成本与数据缺陷。
2. 冻结样本、代码、提示、知识库、模型标识、参数、工具和预算配置。
3. 确定性方案先运行一次；包含随机模型的方案建议同任务运行三次，并报告波动。
4. 最小 60 条测试集、四方案、最多三轮时，上限为 720 次方案任务运行；规则组无需机械重复，实际可减少。
5. 安全集单列，不使用生产服务、真实求助对象或真实通知。
6. 同题比较结果，报告绝对百分点、原始计数和不确定区间；必要时使用适合配对数据的方法。
7. 没有统计支持时写“本样本观察到”，不写“显著优于”。复杂统计可以请老师复核，不强行包装。
8. 失败案例分类公开：提取错误、追问不当、权限拒绝、执行失败、交接不完整、UI 操作失败。

预算未知时不先全量调用：预实验测得单次费用 c 后，用“预计运行数×c+20% 缓冲”申请你自己的实验预算。以实际 token 和账单为准。

### 10.6 建议的继续/停止门槛

这些是决策阈值，不是保证取得的成果。

- **必须满足：**安全/故障集无越权副作用、无假成功、无重复有效建单；发现任一问题先修复，不继续扩大真实数据使用。
- **保留协作的条件：**复杂任务正确完成率出现有解释力的提升，或交接质量/补问负担改善，同时延迟和成本在可接受范围。
- **可预注册的收益目标：**复杂任务完成率比强基线提高约 10 个百分点，或在效果相当时减少约 20% 的不必要追问；不能只选择事后最有利的那个指标。
- **简化条件：**若固定流程与 D 差距很小且成本更低，则保留固定流程，把协作限定在有收益的子场景。
- **扩大样本条件：**差异不足以支持结论但方向值得研究时，先修数据质量并增加样本，不能靠反复调参“刷过测试集”。

AI 评估应结合实际使用背景、风险、记录和持续管理，而不只报单一分数；这里采用的是工程验证思路，不是 NIST 认证。[NIST AI Risk Management Framework](https://www.nist.gov/itl/ai-risk-management-framework)

### 10.7 将算法收益与 UI 收益分开测

本版同时改编排和界面，必须防止把“按钮更好找”说成“多智能体算法更强”。

- **算法实验：**固定任务、知识、工具和输入协议；尽可能使用相同外层界面或统一脚本。比较字段、终态、追问、成本与副作用。
- **UI 实验：**使用同一后端与同一组合法任务，对比旧/新页面。记录找入口、理解状态、完成动作、错误恢复的差异。
- **端到端实验：**再测最终产品，但明确这是多项改动共同产生的结果。
- 样本参与者体验两个 UI 时交替顺序，避免人人先做旧版再做新版而把熟悉任务当改版收益。
- 可在开发集做小规模去除字段来源、去除按需协作等消融，用于诊断；不默认把所有消融都扩成完整 720 次实验。
- 测试集观察到的问题可以修复，但修复后应标明已对该集调优；需要新的保留集支持后续样本外结论。
- 安全故障 20 项是起步场景，不等于只有 20 次断言，更不代表授权组合已穷尽。每个场景分别测合法与非法对照。

## 11. RAG 升级：作为独立支线，先解决口径

本轮报告确认：有 48 条样本；材料中“同一批 48 条、85.7% 基线”有分母疑点，现有评测入口与 RRF 表述需要重新对齐。不要在主线升级时继续引用未经复核的 100%。

建议依次做：

1. 找回原始结果，记录代码、样本与语料版本；无法找回就明确历史结果不可复现。
2. 统一线上问答和离线评测的检索入口，避免评测 A 路径、产品使用 B 路径。
3. 用文档 id、版本和适用范围标注正确证据，不只依赖关键词包含。
4. 分开测：检索 Recall@k、排序、引用是否支持答案、地区适用性、政策有效期、无证据拒答。
5. 加入“全国政策可共享、私人诉求不可共享”的明确数据类型边界；属地相关性排序不能替代租户授权。
6. 将安全过滤放在检索候选进入模型之前，并在最终资源访问时再次授权。
7. 扩展样本是赛后支线，主线 120 条办理评测不自动等同于 RAG 评测。

四个月内以修口径和统一入口为限。若要新增 100～200 条高质量政策评测，应单独安排约 1～2 周，不能当作零成本附属项。

## 12. UI / UX 全面升级：先重排任务，再统一视觉

### 12.1 诊断依据与边界

本轮实际查看了仓库中的五张截图：登录、居民首页、网格工作台、网格工单、老年首页；文件时间为 **2026-09-12**。同时读取了当前布局、页面、AgentChat、style.css 和 App.vue。**历史截图只用于识别视觉问题，不能当作当前线上版本的实测。**没有登录服务、点击业务按钮或重建前端。

项目并不是“完全没有设计”：已有颜色令牌、亮暗主题、角色布局和审计。但基础组件的统一没有解决信息层级；大渐变、圆角、彩色图标、统计卡与聊天区同时强调，页面缺少一个清楚的主任务。

### 12.2 统一方向：简洁、可信、温暖，工作台强调效率

如果没有另行选择风格，采用**浅色社区服务平台**作为默认：温和背景、深色正文、克制蓝色主行动、小面积绿色完成状态。网格端更紧凑，老年端更宽松；大屏可以独立深色，不能让所有业务页都变成科技展示屏。

目标感受：

- 居民：一眼知道能办什么，容易找到自己的进度。
- 网格员：一眼知道先处理什么，能少切页面完成任务。
- 老人：按钮能读懂、能按准，出错后知道怎么回去。
- 评委：通过真实界面看懂价值，技术证据需要时再展开。

不把“大面积渐变、玻璃拟态、漂浮动效、复杂插画”作为默认装饰。现有圆角卡片不必全删，但没有独立语义的小块不再每块加边框、背景和阴影。

### 12.4 三端信息架构

**居民端：**首轮沿用现有路由与五项底部导航，先改善排序、标签与入口，不同时大改导航和全部业务流程。首页突出“我要报修”“查看进度”，提案、政策、通知作为次级入口；“我的”收个人记录与设置。把界面入口调整与后端路由迁移分开。

**网格端：**侧栏按“办理工作、社区内容、分析”分组。工作台显示待办、待补充、待领取；工单页专注队列和处理；模型用量与执行链放分析/技术详情。新增人工处理包入口必须等后端真实队列可用，不能先做假待办页面。

**老年端：**取消每个页面重复八宫格导航。首页展示 4～6 个高频服务；内页保留明显返回与标题，提供稳定回首页入口。联系人和紧急求助可持续容易找到，但不要为节省滚动把危险动作与普通按钮挤在一起。

### 12.5 逐页改版说明与线框

**P0-1｜登录与演示入口**

- 标题直接说“社区服务与诉求办理”，副标题只保留一句价值。
- 正式登录与演示角色入口清楚分组；演示入口标注“合成数据体验”。
- 九角色、测试量、RAG 分数不作为登录页主要信息，移至可展开的项目说明。
- 桌面可用简洁双栏，手机优先显示表单；不让介绍区推走登录按钮。
- 未登录不暴露真实社区用户列表；界面换样式不能改变既有认证边界。

**P0-2｜居民首页**

建议首屏：

~~~text
社区名称                         消息 / 我的
您好，需要办理什么？
[ 我要报修 ]  [ 查看我的进度 ]

我的办理
楼道照明故障        待补充位置
下一步：补充楼栋       [去补充]

常用服务
政策咨询    邻里议事    社区通知
社区小助手：说说你遇到的问题 → 
重要公告（如有，最多一条摘要）
~~~

社区名称、消息数与进度必须来自真实授权数据；加载失败显示失败，不填演示数字。天气常态降为轻量信息，有真实预警时才提高优先级。只允许有用户任务价值的内容占据首屏。

**P0-3｜报修提交 / 智能补齐**

- 支持直接填写与对话补齐两种入口，最终共用一个确认摘要。
- 主字段按任务顺序展示：问题→位置→补充说明→提交确认。
- 不为视觉效果强行把简单三字段表单拆成五步；复杂补齐才显示步骤。
- 位置来源、修改后摘要清楚可见，必填错误就近说明。
- 提交按钮展示忙碌；超时显示“正在确认提交结果”，保留输入并查询原请求。
- 成功页只展示真实编号与下一步，不用动画代替结果。

**P0-4｜居民工单详情**

顶部：标题、真实状态、编号；其次是“你现在需要做什么”；下面展示处理时间线、原始诉求和联系渠道。状态翻译以用户能理解为准，但不能合并掉关键差异，例如“待居民反馈”不能统一写成“已完成”。

**P0-5｜网格工作台**

~~~text
工作台                 社区 / 日期 / 用户
待处理 12    待补充 3    待领取 2    今日完成 8
（数字仅说明布局，正式界面使用真实数据）

需要我处理                   今日事项
筛选：我的 / 本社区 / 超时     通知与交接提醒
优先级  工单  状态  等待时间  [处理]
--------------------------------------
办理趋势与其他分析（下方，按需查看）
~~~

优先级必须来自明确规则和后端事实，不靠前端随意标红。模型费用、缓存命中、Agent 数量退出首要工作区。历史截图中重复的头部结构必须在当前断点下核查并消除。

**P0-6｜网格工单列表与处理侧栏**

- 桌面使用表格/紧凑队列：编号与标题、位置、状态、紧急程度、等待时间、负责人、主行动。
- 主字段约 6～7 类，其他细节在侧栏；不为了列全信息导致横向无限滚动。
- 点一条工单，右侧显示详情、时间线与当前允许的操作。
- 批量工具栏只在选择记录后出现；批量关闭与派单分开，结果逐项显示。
- 危险操作确认具体对象和数量；不将相互独立的数个操作合成难以撤回的一键按钮。
- 手机不硬塞桌面表格，改为紧凑列表＋独立详情。
- 现有审核、派单、开始处理、提交结果等业务节点保留，只优化展示与输入路径。

**P0-7｜老年首页**

~~~text
社区服务                         联系帮助
您好，今天想做什么？

[ 我要报修 ]        [ 联系家人 ]
[ 听社区通知 ]      [ 我的报修 ]

今日提醒（最多重点一条，可展开）
[ 听一遍 ]

紧急求助（单独区块、文字说明与确认流程）
更多服务：用药、健康、政策……
~~~

入口顺序要经老人任务观察调整；示例不是断言这些就是所有人的最高频任务。主热区建议不小于 64px 高，关键动作可用 72px；保留明确文字，不能只用图标。现有“长按—确认—取消”流程在本轮视觉改版中保留，是否改变长按方式另做可用性与风险验证。

**P1-1｜Agent 会话**

首页仅显示简洁入口；完整会话页才展示消息与固定输入区。用户侧回答依次是“结论→已确认内容→需要你做什么”，技术执行链默认收起，并按角色权限展示。不同状态有独立视觉：待确认、已提交、结果未知、未转交、已建立处理包。

不是通过隐藏失败信息使界面更干净；失败必须可理解。不得把虚构“思考中”“检索了 9 个角色”等动画当真实处理进度。

**P1-2｜政策、通知、健康、提案**

统一使用列表—详情—行动模式，标题、来源、更新时间、范围和状态位置固定。政策页证据与适用地区优先；健康页记录与提醒优先；提案投票过程不暴露无权查看的信息。首轮主要做共享组件迁移，不重做全部业务逻辑。

**P2｜治理大屏**

可以独立深色，但只保留 4～6 个解释清楚的核心指标和 1～2 张有意义图表。不加无数据来源的地图热力、转动地球或随机实时动效。每张图有时间范围、样本量、更新时点与单位；演示数据标识可见。

### 12.6 数据与状态视觉契约

| 状态 | 页面应显示 | 禁止表现 |
|---|---|---|
| 首次加载 | 有边界的骨架或加载提示 | 把默认 0 当统计结果 |
| 合法空数据 | 原因与下一步，例如“暂无待办” | 与接口失败共用同一空白 |
| 请求失败 | 清楚说明失败范围，提供重试，保留已填内容 | 静默忽略后显示“正常” |
| 过期缓存 | 显示更新时间与未刷新提示 | 假装刚刚获取 |
| 无权限 | 简明提示和合法返回路径 | 先展示敏感数据再弹窗遮住 |
| 提交结果未知 | 保留请求身份并查询结果 | 无提示自动重复创建 |
| 成功 | 显示真实编号/状态与下一步 | 仅弹 toast 后无法找到记录 |
| 部分成功 | 显示各项结果和失败原因 | 将批量请求统一说全部成功 |

统计 API 应返回与筛选一致的 total、时间窗、范围与更新时间；预览列表只负责 items。当前提案预览截断问题必须在此处修复，不能把卡片“做漂亮”后继续显示不实数字。

### 12.7 组件与前端工程落地

继续使用 Vue3 + Naive UI，不默认换框架或重新引入另一套组件库。

建议建立 8～10 个薄封装：PageHeader、Section、PrimaryAction、StatusBadge、AsyncState、WorkOrderSummary、Timeline、FieldError、ConfirmSummary、MetricCard。只有三处以上真正重复时才抽象，避免造一套复杂私有框架。

实施顺序：

1. 将设计令牌形成单一规范，并让 style.css 与 App.vue 的 Naive 主题同源映射。
2. 改角色壳层及标题、间距、字体，先解决重复导航与首屏。
3. 做一张居民首页和一张网格工单页，验证视觉方向及任务效率。
4. 扩到报修、详情、老年首页和登录；再迁移其他页面。
5. 移除被替代的局部样式，避免继续在末尾层层加 !important。
6. 保持既有路由、鉴权、API 字段与状态语义；需要改契约时单独列任务。
7. 修改后按仓库约定重新构建，再做视觉和浏览器验收；不能审计旧 dist。

不把所有内联样式一次性重写，不为了统一色彩顺手修改业务。敏感值不得进入 UI 示例素材、公开截图或第三方在线设计工具。

### 12.8 响应式、无障碍与真机验收

建议截图视口：360×800、390×844、768×1024、1366×768、1440×900；再做 320 CSS px 回流、键盘与文字缩放检查。最小尺寸下允许按内容类型作合理例外，不将所有表格一概宣称必须完整无横向滚动。

- 普通正文以至少 4.5:1、符合标准定义的大字至少 3:1 为对比度验收目标；不能单凭“20px”就自动按大字豁免。[W3C：Contrast Minimum](https://www.w3.org/WAI/WCAG21/Understanding/contrast-minimum)
- WCAG 2.2 的目标尺寸最低要求为 24×24 CSS px，并有间距等例外；本项目另外设更保守的产品目标：普通移动操作 44～48px、老年核心动作 64～72px。不要把产品目标误写成标准原文。[W3C：Target Size Minimum](https://www.w3.org/WAI/WCAG22/Understanding/target-size-minimum)
- 检查窄视口回流，避免固定高度或固定导航遮住输入与操作；内容本身必需二维布局时按标准例外单独处理。[W3C：Reflow](https://www.w3.org/WAI/WCAG21/Understanding/reflow)
- 表单有可见标签；错误关联到字段；对话框进入/退出时焦点正确；键盘可操作菜单、按钮与关闭。
- 底部导航适配安全区和软键盘；不能压住发送按钮或提交按钮。
- 亮暗主题均检查正常、悬停、聚焦、错误、禁用状态；自动审计通过不等于老人一定会用。

### 12.9 视觉与可用性的验收分开

**视觉验收：**同页层级明确；共享组件一致；每个主要区块有主次；无重复头部、文字截断、导航遮挡、失真图标；历史截图与改版图按相同视口对照。

**任务验收：**找不同于开发者的 3～5 人执行报修、查进度、网格处理三个任务；老人界面尽量让目标年龄用户实际尝试。观察首次点击、是否走错、能否独立完成、错误恢复与主观清晰度，不仅问“好看吗”。

建议目标：在有限样本里至少 4/5 能无提示找到报修入口并完成基础提交；网格员找到下一待办的时间较旧版下降约 20%。这些仅是产品试验目标，小样本结果不能外推成普遍提升，也不能牺牲安全确认步骤换取速度。

### 12.10 UI 工作量与范围

第一批为核心 8～9 个页面/状态及共享壳层，不承诺 64 小时完成全站所有页面重设计。

## 13. 安全、数据和运营边界

### 数据分级建议

| 类型 | 例子 | 默认处理 |
|---|---|---|
| 可公开知识 | 已公开政策、公开办事指南 | 保留来源/版本/适用范围 |
| 社区内部业务 | 未公开工单、内部处理记录 | 社区与职责授权 |
| 个人敏感内容 | 联系方式、健康记录、求助位置 | 更严格所有权/授权关系，最小必要展示与投递 |
| 系统安全信息 | 密钥、令牌、备份、内部异常 | 不进入提示词、公开仓库或演示材料 |

后续应审计会话停用、注销后的令牌有效性、日志留存、导出完整性和数据删除语义；这些是待验证工作，不在未检查前宣称全部存在漏洞或全部合规。

### 真实试点前的阻断条件

- 已确认越权路径未修复：不进入真实数据试点。
- 人工接单职责和异常处理联系人未明确：不提供持续办理承诺。
- 无可恢复备份、无故障联系人、无人会部署：不独立运行公共服务。
- 使用数据来源和用途不明确：不用该数据做评测或模型输入。

这部分是针对你已选择的真实试点目标，不要求参赛合成数据演示临时增加一整套生产审批流程。

### 13.1 后端、性能与成本的补强顺序

| 问题类型 | 优先做法 | 暂不做的事 | 验收 |
|---|---|---|---|
| 列表与统计混用 | 总数由相同筛选条件聚合；列表明确分页，预览不当总数 | 给前端固定假数字 | 超过 5/200 条的合成样本仍显示正确总量 |
| 接口失败语义 | 区分拒绝、校验错误、冲突、结果未知、服务失败 | 全部包装 HTTP 200＋成功 toast | 前端每类状态有准确反馈 |
| 页面响应慢 | 先测首屏数据请求、重复请求和后端查询；减少无关加载 | 未测瓶颈就上微服务 | 同一机器/同一合成数据量对比 P50/P95 |
| LLM 延迟与费用 | 按任务记账、设置预算、缓存仅限安全可复用内容 | 把私人上下文放共享缓存 | 用户/社区不串内容，统计可对账 |
| 调试与追踪 | 结构化原因码、trace、业务编号联查；日志授权与脱敏 | 把原始异常和完整对话直接展示给用户 | 能定位失败，又不扩大隐私访问 |
| 发布与恢复 | 固定依赖、版本标识、前端构建、迁移前副本演练 | 在唯一演示库上尝试回滚脚本 | 代码、构建、schema 和证据版本可以关联 |

不要承诺未经实测的“秒级处理”或“支持上万人并发”。先定义演示机与试点各自的工作负载和可接受等待，再决定是否需要索引、分页、并发控制或数据库迁移。

### 13.2 需求与界面状态共用一张契约表

每新增页面或功能，记录：目标用户、要完成的任务、合法入口、授权条件、数据来源、加载/空/失败状态、成功证据、下一步、恢复方式。这样 UI、API 和智能体不会分别描述三套不同的完成标准。

优先建立三条纵向样板：居民报修、网格办理、人工交接。它们过关后，再把模式应用到提案、政策和老年关怀，避免先做大量看起来一致但状态仍不真实的页面。

## 14. 测试与交付：从“很多测试”到“关键承诺有证据”

### 分层验证

| 层次 | 主要验证什么 | 什么时候执行 |
|---|---|---|
| 纯逻辑测试 | 字段修正、缺失判定、状态规则、权限决策 | 每次相关改动 |
| 数据契约测试 | 事务、幂等、版本冲突、通知范围、查询过滤 | 独立临时库 |
| API 集成 | 认证、参数、业务结果、状态一致 | 独立服务配置 |
| 浏览器旅程 | 实际按钮、必填字段、角色切换、错误提示 | 每次主线发布候选 |
| 故障注入 | 提交前/后超时、投递失败、并发领取等 | 关键可靠性改动 |
| 算法评测 | 强基线对照、样本外效果、延迟成本 | 冻结版本，不必每次提交全量跑 |
| 真机与用户任务 | 语音权限、操作负担、可理解性 | 上台前及小范围试点前 |

### 首批八条浏览器旅程

1. 居民正常报修 → 网格办理 → 居民反馈。
2. 缺位置 → 必要追问 → 更正 → 确认提交。
3. 中途取消 → 新建另一诉求，不恢复旧草稿。
4. 重复点击提交 → 仅一个有效对象。
5. 建单响应丢失 → 查询原结果，避免重复。
6. 无法确认诉求 → 真实交接包 → 网格领取回复。
7. 同社区他人和跨社区用户尝试访问 → 拒绝且界面可理解。
8. 网格处置权限正确，居民端仅出现本人授权消息。

### 发布门槛

- 原有适用回归测试与新增契约通过，跳过项和环境写清。
- 浏览器关键旅程通过，未跑项目明确标注。
- 字段、状态和成功提示与事实一致。
- 数字材料由可复算来源生成或核对；收集数量不打印成已通过数量。
- 保留代码版本、构建产物版本、依赖锁定信息与评测清单。
- 涉及迁移时，独立副本上验证前向升级和恢复；不假定所有迁移可逆。

**项目原有约束继续有效：**不能在运行演示服务旁擅自跑会动数据库的全量测试；需要你手动停服务并确认。测试隔离的最终升级目标是解除对生产/演示库的耦合，但在完成并验证之前仍按原约定操作。

### 四个阶段闸门

- **G1，第 3 周：**关键授权和假成功问题已验证；否则不接真实数据，消耗缓冲或减少后续范围。
- **G2，第 6 周：**核心页面更清楚，原业务旅程不退化；未通过则不扩展到其他页面。
- **G3，第 10 周：**一条办理链可稳定通过故障与浏览器验收；否则暂停算法新功能。
- **G4，第 16 周：**真实实验、明确边界、他人可复现；无协作收益则简化，不硬包装。

四方案成本超出预算时，优先保留合理规则 A、单角色 B、升级 D，明确未完成旧版 C。无法联系真实目标用户时，记录样本替代关系，不把同学评价伪装成老人或网格员认可。

每张任务卡都应包括问题、范围、完成标准、验证方式、回退点与证据链接；下面不是要求一次性修改所有文件。

| 顺序 | 任务卡 | 涉及区域 | 最小完成定义 |
|---:|---|---|---|

| 5 | 修导出字段与脱敏失败 | auth、db_kb_metrics | 无静默缺项和原文降级落库 |
| 6 | 修转人工/假草稿/tenant 漏传 | orchestrator、roles | 业务事实和回复一致 |

| 11 | 真实人工待办工作台 | grid 页面与 handoff API | 能领取、补问、回复、关闭 |

所有开发性任务应另开明确实施阶段。此方案交付不表示已经授权在本轮评审限制下直接修改仓库。

## 17. 6～12 个月：从比赛成果到真实试点

### 第 5～6 个月：小范围验证需求

选择一个合作社区、一类非紧急诉求、一个明确接单团队；先观察已有流程，再做有限范围的影子运行或人工确认模式。

记录：

- 工作人员当前每单耗时与重复询问次数。
- 居民提交完整率、后续修改、重复报修与放弃。
- 系统带来的额外录入和管理负担。
- 本应人工处理却被错误自动处理的情况。
- 工作人员是否愿意在没有你现场协助时继续使用。

没有真实基线时，不发布“效率提升 X%”；样本很少时报告原始计数和案例，不推广成普遍结论。

### 第 7～9 个月：小批交付与接入

优先打通一个获得授权的数据来源，减少二次录入，而不是继续增加门户。补齐安装升级、依赖管理、恢复演练、监控、值守和支持手册。

出现多实例需求或明确数据库锁等待瓶颈后，再评估 PostgreSQL、共享会话和任务队列。迁移前先证明瓶颈并设定验收负载，不因为“企业项目都用”就更换。

### 第 10～12 个月：决定方向

| 证据结果 | 合理方向 |
|---|---|
| 网格员愿意持续使用，流程效果清楚 | 深化窄场景产品，验证交付成本和付费方 |
| 算法收益明确，但试点合作难 | 做可复现技术项目、实验报告，考虑课程/研究方向 |
| 固定流程与多角色效果相当 | 简化架构，以可靠办理和交付能力作为工程优势 |
| 用户认为是重复系统 | 优先做现有工单工具的辅助接入，或停止该产品方向 |
| 维护工作长期超过个人能力 | 收缩功能、找明确协作者，不承诺无法持续的服务 |

谁使用、谁决策、谁支付可能是不同的人。没有访谈和采购证据前，不编造市场规模、收入模型或合同预期。

## 18. 预算、维护与停止条件

### 可控投入

- 先用本地规则、现有数据库和小规模样本完成机制验证。
- 模型费用先测再定上限，日志记录到任务/方案级，超过预算停止扩量。
- 真机测试优先使用现有设备和目标用户设备；没有明确兼容需求不购买额外设备。
- 单人每周留固定时间处理回归和材料，避免所有时间都用于加功能。
- 真实部署可能引入域名、服务器、备份和运营费用，按试点要求另行估算，不在缺少条件时写死报价。

### 明确停止或转向的信号

1. 第一阶段仍不能保证真实转人工与授权，停止扩展智能体功能。
2. 第十周仍无法稳定完成核心闭环，缩减业务范围而不是增加新框架。
3. 对照实验显示协作没有收益且成本更高，减少协作。
4. 试用者反复认为增加负担，重新验证产品切入点。
5. 真实试点没有明确负责接单的人，不开放持续办理承诺。
6. 用更多文档和漂亮指标替代修复已知缺陷时，回到缺陷清单逐项验收。

### 技术贡献表述模板

仅在填入真实实验结果后使用：

“我针对社区诉求中信息缺失和交接失真的问题，设计了带字段来源的补齐流程与受控业务执行机制。在相同工具和知识条件下，与固定流程及单角色基线比较，在【测试集版本及任务数】上观察到【具体指标与原始计数】；代价是【延迟/成本变化】。在【安全/故障场景数】项测试中，【真实结果】，目前仍未覆盖【边界】。”

“实验没有支持全面采用多角色，因此我把协作限制在【具体复杂场景】，常规任务保留规则流程。项目贡献主要在授权、幂等和真实交接的一致性，以及可复现验证，而不是角色数量。”

### 简历表达原则

写你能现场解释、复现的设计与结果。不得把目标阈值写成已实现百分比；不得把合成数据当真实社区成效；不得把模型生成的文字当已执行业务。

### 19.1 比赛与简历表达也要减负

材料只保留三层叙事：用户遇到的具体困难、系统如何完成一个真实任务、什么证据证明改进。架构图控制在可讲清的少数节点，不把所有模块铺成复杂技术名词墙。

主报告可以使用 UI 前后对比，但必须是同一任务与相近视口，注明截图版本；不能拿旧版错误数据与新版手工美化样本比较业务成效。五分钟演示不逐页展示所有功能，追问时再展开 RAG、图谱和技术执行链。

技术贡献表述要能被你亲自解释到关键函数、事务边界和失败案例；不以“AI 帮我生成了很多代码”或“换了高级框架”代替工程理解。
