# v3 方案复核：目前还没做好什么

**复核基线：当前 HEAD 9004659（2026-09-28）**  
本轮只读复核，没有修改项目。

## 结论

上一轮提出的部分权限问题已经修补：当前老年路由增加了资源所有权判断，联系人、用药修改、暂停/恢复等不再只依赖“同社区”。但老年主线仍有四个阻断缺口：

1. 老人缺少位置时，后端会用社区名代替位置并直接提交。
2. 联系人/社区“拨打”接口当前主要是写拨号留痕，不能证明电话真的发起或接通。
3. 语音交互的文案、事件和真实设备行为不一致。
4. 老年端仍然是八个顶层入口，v3 的功能收敛还没有落到界面。

所以现在可以说“有老年端特色原型”，不能说“老人已经可以可靠完成社区办事闭环”。

## 一、阻断级问题

### 1. 缺位置仍然会被伪装成完整工单

位置在 api_routes/elderly.py:198 附近通过 extract_location 提取；失败时使用 profile.community 或“社区”，然后直接调用 submit_issue。老人说“楼道灯坏了”时，系统可能成功写入一张 location=社区 的工单。

这违背“只补问必要信息”，也会让网格员收到无法派单的事项。

应改为：缺位置返回待补充草稿；让老人补充楼栋/楼层；展示结构化摘要；确认后才提交。验收中“楼道灯坏了”不能直接建可办理工单；“五号楼二层楼道灯坏了”才允许提交；“不是三号楼，是五号楼”只能留下五号楼。

### 2. “正在呼叫”与实际行为可能不一致

api_routes/elderly.py:449 的 web_elderly_contact 调用 log_emergency_call 后返回；Contacts.vue:41 的 confirmCall 只请求接口并显示“正在呼叫”。当前代码没有看到联系人按钮执行 tel 导航、系统电话 API 或可信呼叫服务。

如果产品只是打开拨号盘，应明确显示“打开拨号”；如果要记录接通，必须有真实电话能力或用户反馈。API 不能在按钮点击后直接写“已结束”并让老人以为已经接通。

应分别记录：准备拨打、已发起、用户取消、失败、已接通（只有真的有证据才允许）。安卓、iOS Safari、微信要分开验收。

### 3. 语音文案和代码不一致

Report.vue:68 文案是“按住说话”，但事件是 click，没有按下/松开/取消；实际是点击开始、最多 60 秒结束。Report.vue:27 和 Home.vue 还有挂载期 speak 调用，而 useSpeech.js 的注释已经承认 iOS Safari 的 TTS 需要用户手势。

应二选一：真正实现 pointerdown/pointerup 的按住说话，或统一文案为“点击开始录音”并提供停止按钮。播报统一改成用户点击“听一遍”，显示播放失败和再次播放，不能把挂载期调用当成老人听到了。

### 4. 老年导航仍未收敛

ElderlyLayout.vue:20 仍有首页、小助手、报修、我的报修、用药、联系人、通知、政策八个顶层按钮；首页又有天气、通知、报修、联系社区、用药、健康等入口。

首版应收敛为：我要报修、看看办理进度、联系家人或社区、今日提醒、独立紧急求助、更多服务。路由可以保留，展示入口先收敛；内页保留大返回和回首页，不再每页重复八个入口。

## 二、重要问题

### 5. 提交成功没有“结果未知”状态

Report.vue:48 请求成功就显示“已上报成功”，请求异常只显示错误。没有按原请求身份查询“可能已提交但响应丢失”的路径。

应增加幂等请求身份、超时查询和真实编号。网络断开时显示“正在确认是否提交”，而不是鼓励老人再次点提交。

### 6. 当前确认的是转写文本，不是结构化办理摘要

Report.vue 只显示“您说的是：转写文本，对吗”；后端随后自行分类、提取位置并提交。老人确认了文字，不等于确认了楼栋、楼层、类别。

应先返回草稿：问题、位置、补充说明、缺失项、来源；用户确认字段摘要后再调用写入接口。

### 7. corrected 是提交后的文字说明

api_routes/elderly.py 先执行 submit_issue，再返回 corrected；页面在提交成功后才显示纠正内容。它没有改变已经写入的 title、location、description。

必须分开原始话语、系统建议、用户确认值和最终入库值；未确认的纠正不能成为业务事实。

### 8. 联系接口接受前端传入的姓名和号码

ContactCall 接受 target_name、target_phone；后端没有在这条接口中确认目标是不是已审核联系人、系统社区号码或合法服务号码。

建议前端只传 contact_id 或明确系统目标类型，后端自己取号码。自由号码只能标成“手动拨号”，不能写成可信联系人事件。

### 9. 老人订单仍缺少可理解的完整进度

Orders.vue 主要显示状态、人话状态、维修人员和处理备注，没有形成稳定的“当前状态、下一步、更新时间、真实编号、是否已建立处理包”结构。

每项只保留一个主行动：补充信息、等待处理、查看结果或联系帮助。只有真实处理包持久化后，才显示“已交给工作人员”。

### 10. 草稿恢复与防丢失还没有同时解决

交接说明仍列出旧草稿覆盖新报修的问题。当前语音页面的文本主要放在组件状态中，刷新或离开也可能丢失。

正确方案不是简单“永远自动恢复”或“完全不保存”，而是 draft_id、user、tenant、version、updated_at；恢复时让用户选择继续/新建，取消后失效，换账号不能恢复上一个人的草稿。

## 三、v3 方案还需要补的设计

### 1. 把“保留”拆成保稳定或继续开发

首轮深做：报修输入、补齐、确认、我的报修、网格待办、真实人工交接。

只保稳定：SOS、联系人、用药、通知。

只保入口：政策、天气、健康记录。

降级为技术详情：图谱、复杂协商、治理大屏、模型费用。

如果“保留”仍需要修 bug，必须从 192 小时预算中单独扣除，否则方案会再次变成多条并行产品线。

### 2. 把目标用户观察提前到 UI 开发之前

至少先让 3 人完成旧版的三个任务：找到报修、改正楼栋、查看进度。记录停顿、误点、需要提示的地方，再定新版线框。

找不到真实老人时，必须标记为替代样本，不能把家人或同学测试写成老人研究。

### 3. 固定一条可演示失败路线

要真实准备：语音不可用转文字、缺位置进入补充、用户改口生成新摘要、提交结果未知可查询、无法判断进入处理包、无人领取显示等待。不能只做一张失败提示图。

### 4. 明确最小代码接入边界

第一批只改老年 voice-report 为“返回结构化草稿”，复用居民最终提交服务；复用同一 issues 状态和网格处理包；暂不重写提案、健康、天气和图谱。

### 5. 给数据库契约留预算

草稿版本、幂等键和处理包状态可能需要迁移。所有加列/加表必须走 db_core.py 版本迁移；先在独立库验证前向升级、兼容旧数据和回退策略，不能在唯一演示库试错。

## 四、排期判断

v3 的 12 周、192 小时仍偏乐观。建议改成两个闸门：

**前 4 周必须完成：**缺位置不提交、真实摘要确认、权限正反例、拨号语义、旧草稿不覆盖新输入、老年导航收敛。

**后 8 周有余力再做：**真实处理包领取/回告、结果未知查询、用户观察、A/B/C 对照和其他页面统一。

只有 6 周时，优先做好“老人报修”一条链，不要展示八个半成品功能。

## 五、最优先十项

1. 缺位置改成补充状态，禁止社区名兜底。
2. voice-report 改为结构化草稿，确认后提交。
3. 拨打接口区分留痕、发起和接通。
4. 统一“点击录音”或真正实现按住说话。
5. 移除挂载期自动播报。
6. 收敛老年首页和顶层导航。
7. 增加幂等与结果未知查询。
8. 让订单显示下一步、更新时间和处理包状态。
9. 只传联系人 id/系统目标类型。
10. 先做三人旧版任务观察，再锁定新版线框。
