# 授权矩阵（任务卡 1 交付物）

> 来源：v2 升级方案 §5「授权矩阵示例」，本文件把示例**变成可执行的工程约定**：
> 每个单元格都要能在代码里指出"谁在校验、校验什么"。
> **原则**：授权**逐请求、逐资源**判定，**默认拒绝**未明确定义的访问；**前端隐藏按钮不是授权**。

## 一、角色定义

| 角色 | 说明 | 代码里的来源 |

| **本人** | 这条记录的归属用户自己（老人/居民） | `uid == 记录.user_id / reporter_id` |

| **同社区其他居民** | 同社区但与这条记录无关的用户 | 同社区但既非本人也非绑定家属 |
| **其他社区网格员** | 不同社区的 grid | 租户不匹配 |

## 三、实现约定（怎么落到代码里）

1. **三道校验，顺序固定**：`角色/身份` → `租户（社区）` → `资源所有权`。前一道不过就不要执行后一道的查库（避免用错误码探测存在性）。
2. **同社区 ≠ 有权操作**：`_same_tenant()` 只解决第 2 道；涉及个人资源的**写操作**必须再过 `_owns_resource()`（本人/绑定家属）或 `_grid_with_duty()`（职责网格员）。
3. **对外一律 fail-closed**：租户为空、绑定关系查询失败、状态不明确 → **拒绝**（记 warning，不静默放行）。
4. **拒绝文案不透露存在性**：跨社区/无权的返回统一 1003，不区分"不存在"与"无权限"。
5. **前端隐藏只是体验**：任何按钮的可见性都不作为安全依据；接口必须独立可拒。

## 四、待你确认的产品决定（这几行会直接写进代码）

| # | 问题 | 我建议的默认 | 影响 |
|---:|---|---|---|
| D1 | 绑定家属能不能**修改**老人的用药提醒与联系人？ | 可以（已审核绑定关系）；但**打卡**只能老人自己做 | 影响家属协助场景的便利性 |
| D2 | 本社区网格员能不能**代老人**新增/修改联系人与用药？ | **不能**（只审核，不代改）——避免"网格员替居民改个人配置"的授权争议 | 现场演示不受影响（演示走老人本人操作） |
| D3 | 网格员能否查看本社区老人的**健康记录**？ | 可以（关怀用途，仅本社区、仅列表与详情，不做导出） | 与"重点关注老人"功能配套 |
| D4 | 家属能不能**代录**健康数据？ | 不能（避免造数据）；只能查看 | 影响家属远程协助 |
| D5 | 公开提案，其他社区居民能不能看？ | 默认**不能**（当前实现按社区隔离）；若将来要跨社区公示，需显式标记 | 与方案 §5"仅确实跨社区公开时允许"一致 |

> 以上 5 条不改也能按"我建议的默认"实施；你若改，我按你的决定写，并在矩阵里注明日期与理由。
