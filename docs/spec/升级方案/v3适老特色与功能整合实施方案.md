# 社区先知 v3：以老年人为核心的产品收敛与升级方案

**日期：2026-09-28｜性质：产品决策与实施计划｜对象：单人参赛与赛后迭代**

> **最终建议：把项目主定位收敛为“面向老年人的社区办事助手”，以非紧急公共设施报修作为首个完整场景，以网格员接单和结果回告组成闭环。**
>
> 老年端是主入口，网格端是服务承接端，居民端保留为通用入口。技术价值体现在老人表达不完整、听错说错、操作中断和需要人工帮助时，系统仍能正确推进事情。
>
> 不继续扩展为覆盖养老生活的一站式超级应用；不把所有功能装进一个聊天框；不因为缩减入口就删除已稳定的业务。
>
> **版本关系：本版替代 v1/v2 的产品定位、功能优先级和主线排期。**v2 的安全修复依据、设计令牌、状态规范和测试方法仍可作为实施参考；v2 的通用居民优先安排、全站 UI 预算及静态预览不再是本阶段的最终目标。以本版的适老主线和验收为准，不把三版工作量叠加。
>
> 本次只编写方案，未改项目源码、数据库、配置或服务。已有能力及缺陷沿用 2026-09-27 评审，未重新运行全部功能。本文的新增交互、数据契约、实验及排期均为拟实施内容，不是已完成成果。

## 1. 为什么这样调整

### 1.1 项目目前的问题不是功能不够，而是核心对象不清楚

当前系统同时面向居民、网格员和老人，展示报修、提案、政策、健康、天气、通知、图谱和治理大屏。每个模块都能解释用途，但很难在五分钟内证明所有模块都不可替代。

“功能多”只有在减少用户负担时才有价值。对老人而言，入口越多不一定越方便；对网格员而言，新增一个系统也可能增加录入负担。现阶段最需要的是一条可观察、可验证的用户任务。

### 1.2 老年端为什么值得成为特色

项目已具备大字、语音/播报、预置短语、联系人、报修与关怀相关能力，可以复用已有投入。但真正值得深化的是：

- 不熟悉手机操作的人能否找到办事入口。
- 表达不完整时，系统是否只补问必要内容。
- 语音听错、用户改口时，是否容易纠正。
- 提交后是否知道有没有成功、谁在处理、接下来做什么。
- 系统解决不了时，是否真正进入工作人员待办。

**特色来自对这些困难的完整处理，不来自“老人端”这个标签，也不只来自字号。**

W3C 的老年用户研究将年龄相关的视觉、听觉、运动与认知需求纳入可访问性设计，但不能因此假设所有老人能力相同；设计仍需结合具体任务与用户验证。[W3C：Older Users and Web Accessibility](https://www.w3.org/WAI/older-users/)

### 1.3 不把“关怀”扩大成另一套庞大产品

本阶段的关怀首先意味着：愿意听、容易改、能解释、事情有人跟进。不是新增情感陪伴大模型、自动医疗判断、跌倒检测、智能硬件或全天候监护。

对外主名称继续使用“社区先知”；建议描述为：

**社区先知——面向老年人的社区办事与协同服务助手。**

“基层治理、多智能体、RAG”等放在技术说明中，用户入口不需要先理解这些概念。

## 2. 第一批用户、场景和成功定义

### 2.1 不按年龄划定单一能力模型

首批目标是：能基本使用智能手机，但在输入、阅读、理解流程或恢复错误时需要支持的人。可同时观察：

| 用户情况 | 主要困难 | 设计应对 |
|---|---|---|
| 愿意说，不愿打字 | 打字慢、表单难找 | 语音增强＋预置短语＋简短输入 |
| 看得见但不理解状态 | 不明白“待审核”“待反馈” | 明白的话解释状态与下一步 |
| 容易误触或中断 | 返回后丢内容、担心重复提交 | 草稿恢复、确认、可查询结果 |
| 熟练使用手机 | 不希望被迫听播报或一步步慢操作 | 可直接填写、关闭声音、跳过非必要引导 |
| 需要他人代办 | 他人帮助时容易混淆身份和授权 | 后续明确代办身份与范围，不能共享无限权限 |

不要求所有老人都使用“简化模式”。提供适老入口与普通入口，不用年龄强制降低功能或替用户作决定。

### 2.2 首个场景

**非紧急公共设施报修：老人发现楼道照明、公共扶手、公共座椅等问题，能提交清楚的诉求，并获得办理进展和结果。**

选择这个场景是因为已有业务骨架、状态明确、容易观测补问和交接，而不是断言它一定是所有老人最高频的需求。前期访谈若显示需求不成立，可以换成另一个同样有真实承接人的窄场景。

涉及即时人身危险的求助不进入普通报修队列等待算法处理。已有紧急联系入口应保持明确边界和可达性，但不将其作为首轮无人值守能力承诺。

### 2.3 成功不等于“模型回复了”

一个任务的成功至少包括：

1. 老人知道自己正在办理什么。
2. 关键字段准确，修改后的内容生效。
3. 提交前获得适当确认。
4. 提交后存在真实业务记录，重复请求不会建多个有效对象。
5. 工作人员能看到并按职责处理。
6. 老人能理解当前进度、待补充项或最终结果。

真实维修完成依赖线下人员，不是软件可以单独保证的结果。技术验收衡量记录与流程一致性，试点再衡量实际服务成效。

## 3. 功能收敛：明确“合并什么、不合并什么”

### 3.1 四个层次不要混淆

- **入口整合：**减少首页按钮和重复导航。
- **信息整合：**把同一事项的消息、进度和结果放在一起。
- **流程整合：**语音、文字和预置短语进入同一办理流程。
- **技术复用：**共用授权、草稿、状态、通知和结果查询。

这四项不要求立即合并数据库表、删除现有路由或重写所有模块。紧急求助、普通报修、用药提醒即使在同一应用中，也应保留不同业务规则。

### 3.2 现有模块的去向

| 模块 | 决策 | 老人侧呈现 | 网格侧/技术侧处理 |
|---|---|---|---|
| 普通报修、语音报修、报修类 Agent | **重点整合** | 同一个“我要报修”，可说、可选、可填 | 共用草稿、确认和提交入口 |
| 我的报修、处理通知、结果 | **重点整合** | “看看办理进度”，从事项进入详情 | 一个业务编号关联状态和消息 |
| 政策问答、办事指南 | **保留、降为辅助** | “问一问”或办事中的咨询入口 | 保留来源、适用范围、无依据转接 |
| 普通天气、生活建议 | **降级展示** | 今日提醒中的轻量摘要 | 不单独占据主演示 |
| 重要通知 | **整合信息，不弱化重要性** | 今日提醒，必要时置顶 | 保留真实发布范围、有效期与已读语义 |
| 用药提醒 | **保留既有能力，不扩医学功能** | 提醒区入口；详情仍独立 | 不与工单状态混用，不自动改用药安排 |
| 健康记录 | **二级入口、先修授权** | 本人查看与已有记录能力 | 严格社区/本人/授权关系 |
| 联系人、联系社区 | **合并入口** | “联系家人或社区”，先选对象 | 记录与权限清楚；发起拨号不等于已经接通 |
| 人工转接 | **深做闭环** | 从当前事项进入“请工作人员帮忙” | 有真实处理包、领取与反馈 |
| SOS/紧急求助 | **独立保留** | 稳定可见的专门区域 | 单独确认、取消、处置，不混入普通队列 |
| 提案投票、社区议事 | **普通居民侧保留，暂缓扩展** | “更多服务”，不挤占老人首屏 | 稳定维护 |
| 图谱、复杂分析、模型费用 | **退出主用户路径与主演示** | 不显示给老人 | 需要时作为技术/管理详情 |
| 治理大屏 | **保留一页辅助展示** | 无需入口 | 只用真实定义与合成数据标识 |
| 多智能体执行链 | **按需查看** | 默认不显示角色技术名 | 技术答辩和授权诊断入口 |
| 独立家属端 | **本阶段不新建** | 保留已授权联系能力 | 后续在居民端承载有限代办 |
| 新养老硬件、陪伴、自动诊断 | **不做** | 不加入导航 | 不占首轮预算 |

### 3.3 合并展示时必须保留的语义

- “已读通知”不是“已完成事项”。
- “已记录求助”不是“工作人员已接单”。
- “已发起拨号”不是“电话已接通”。
- “已提交工单”不是“维修已完成”。
- “今日没有提醒”必须来自成功读取，不能由请求失败推导。
- “未打卡”不能直接解释为“老人没有吃药”。
- “没有打开应用”不能直接推断“老人发生危险”。

这些不是文案细节，而是关怀功能是否可信的基础。

## 4. 三端重新分工

| 端 | 核心角色 | 本阶段重点 | 不承担什么 |
|---|---|---|---|
| 老年端 | 表达、确认、查看、求助 | 简洁首页、补齐纠错、播报结果、错误恢复 | 不承载技术演示和复杂管理 |
| 网格端 | 接单、补问、办理、回告 | 统一待办视图、真实交接、具体行动 | 不用统计大屏替代日常办理 |
| 居民端 | 通用办事入口 | 复用后端能力，保留已有稳定功能 | 不同期全面重做，也不新增完整家属门户 |

**一条业务，多种表达界面。**老年端可把状态说得更明白，居民端可更紧凑，网格端可显示内部处理细节，但它们必须指向同一真实状态。

不要为了老人端又复制一套提交、草稿和消息逻辑。已有老年报修路径应逐步接入共用业务服务；外观可以不同，权限和事实不能不同。

## 5. 老年端首页：具体、少选、稳定

### 5.1 收敛后的首页

~~~text
社区服务                         帮助
当前：示例社区

[ 我要报修 ]
  可以说一句，也可以选择问题

[ 看看办理进度 ]      [ 联系家人或社区 ]

今天要注意
一条最值得关注的提醒         [听一遍]
[查看其他提醒]

紧急求助
独立区域，清楚的确认与取消方式

更多服务：政策咨询 / 用药提醒 / 健康记录……
~~~

首版优先使用具体名称“我要报修”，而不是宽泛的“我有事要办”。后者听起来范围很广，如果实际只支持报修和咨询，可能制造错误预期。未来支持更多有承接方的业务后，再调整入口。

### 5.2 首页原则

- 首屏首先看到能做的事情，而不是大段欢迎、天气和技术介绍。
- 不在每个页面重复八个导航；首页负责找服务，内页负责完成当前任务。
- 保留明显返回和回首页；不要依赖手机浏览器的返回操作。
- 字号、播报、语速等设置集中到容易找到的位置，不常驻占用首屏。
- 不使用过度幼稚的插画和称呼；尊重成年人身份，不默认称用户“爷爷奶奶”。
- 紧急入口稳定可找，但不使用持续闪烁、跳动制造焦虑。
- 首页顺序稳定；个性化不能让常用按钮每天换位置。

### 5.3 今日提醒的整合规则

用一个提醒区承载不同来源，**后台不必合成同一种业务对象**。每项带来源类型、标题、有效期、是否需要行动和详情入口。

优先显示有效的重要社区通知，其次才是相关日常提醒。去重同一通知，不把天气、健康知识和用药提醒连续自动播报。具体优先级需结合社区责任规则，而不是任由模型给所有内容打“紧急”。

读过、稍后提醒、完成操作应分别记录。提醒失败需可见，不能声称手机关闭或网页后台时仍保证准时送达；提醒渠道和后台能力需要单独验证。

## 6. 核心办事旅程：从表达，到真正收到结果

以“楼道灯坏了”为样例，不使用真实个人数据。

| 步骤 | 老人看到/做什么 | 系统必须做到 | 常见失败与恢复 |
|---|---|---|---|
| 1. 开始 | 点“我要报修” | 显示可说、可选、可填的入口 | 不支持语音时仍能继续 |
| 2. 表达 | “楼道那个灯又不亮了” | 保留原话，提取问题，但不猜具体楼层 | 听不清则明确说出缺失部分 |
| 3. 补齐 | “是在几号楼、哪一层？” | 只问影响办理的必要字段 | 不一次列出十个问题 |
| 4. 纠正 | “不是三号楼，是五号楼” | 替换旧值，显示修正后的摘要 | 不把两处位置同时提交 |
| 5. 确认 | 听/看“5 号楼 2 层楼道灯不亮” | 摘要含关键字段，提供修改与确认 | 返回修改不丢输入 |
| 6. 提交 | 点“确认提交” | 授权校验、幂等写入、返回真实编号 | 超时查询原请求，避免重复建单 |
| 7. 等待 | 看“已收到，等待工作人员处理” | 真实记录对应真实状态 | 不虚构接单人或响应时限 |
| 8. 处理 | 必要时补充信息 | 网格员看到原话、摘要、未决项 | 老人不必从头讲一遍 |
| 9. 回告 | 听/看实际处理结果 | 区分工作人员已处理和居民待反馈 | 不把“待反馈”自动标为老人满意 |
| 10. 结束 | 确认结果或说明未解决 | 保留真实反馈与后续路径 | 不因一次点击误关闭所有事项 |

**设计要求：**能直接填写的人应走短路径；需要帮助的人才使用逐步补齐。不要强迫所有人多轮聊天，也不要为了“流程完整”给简单任务增加不必要页面。

W3C 的认知可访问性建议强调使当前步骤、完成任务所需信息和当前位置清楚可理解；此处采用该设计原则，不把具体页面方案宣称为标准认证。[W3C：Make Each Step Clear](https://www.w3.org/WAI/WCAG2/supplemental/patterns/o1p04-clear-steps/)

## 7. 五项适老交互深化

### 7.1 语音是可替代的输入方式

默认点击开始、明确显示正在听、允许停止和取消；不持续后台监听。转写后把关键字段展示给用户确认，不能把识别结果直接当事实。

支持预置短语、点击选项和文字输入作为同等有效的替代途径。设备或权限失败时解释原因，保留当前内容。原始录音默认不因调试而长期保存；是否保留、用途和授权需另定。

不要承诺已经解决方言和噪声问题。只有测试过的设备、语言和环境才能对外报结果。

### 7.2 纠错是一等功能

为“说错了”“不是这个位置”“重新说”“先不提交”设计明确入口。保存字段来源与版本，让后一条确认覆盖前值。

系统自动提取的地址与用户明确确认的地址分开标识；存在冲突时不要静默选择其一。尽量不在每次确认中重复播报无关敏感信息。

### 7.3 播报围绕任务而非阅读整页

播报当前问题、摘要、结果和下一步；允许重听、暂停与停止。不要页面一打开就自动播放全部内容。

“听一遍”不等于“同意提交”；播报结束也不能自动触发危险操作。新消息到来时避免多个音频互相叠加。

### 7.4 中断可恢复，但不能恢复错的人、错的事情

刷新或返回后可找到未完成草稿；恢复时先显示摘要，让用户选择继续或新建。退出账号、换用户或切社区后不能带入上一个人的草稿。

已取消草稿失效，旧确认不能再次提交；两个标签页编辑时检测版本冲突。为了避免数据丢失，服务端草稿和本地临时内容都要明确权限与清理规则。

### 7.5 适老不等于不断弹确认框

只在提交、更改关键事项、联系/求助等有实际后果的节点确认。查看信息、返回首页等低风险动作不必多次确认。

目前 SOS 存在长按和限时确认设计。**赛前不贸然更改其业务行为；赛后应专门观察长按是否难以完成、10 秒确认是否造成不必要压力。**不能未经评估就把这个时间限制当作适老最佳实践，也不能为了更好点按而改成一次误触即发送。

## 8. 网格端：要接得住，而不只是看得到

### 8.1 统一待办视图，不统一所有业务状态

工单、人工交接、待补充信息可以出现在同一工作台，但每项显示业务类型、责任人、当前状态和下一步。底层仍采用各自合法状态机。

日常优先看“需要我做什么”，将 AI 自解率、模型费用、缓存命中等移至分析详情。列表预览与总量分开，不用前五条的长度代表全部待办。

### 8.2 人工处理包最小内容

- 用户原始表达及合法可见的联系渠道。
- 已确认的位置和问题。
- 系统已问过什么、用户怎样修正。
- 当前无法解决的具体问题。
- 关联工单、提交/交接时间与真实状态。

不在每条待办突出“老人不会操作”等标签；只提供完成任务所需信息。相关健康记录不能因为“方便工作人员”而无差别附加。

### 8.3 领取、处理、回告

处理包有真实编号，工作人员能领取、补问、回复和关闭；两个工作人员同时领取只能一个成功。建立处理包、发送通知、工作人员接单是不同事件，页面要分开表达。

没有明确值守和响应规则时，不向老人承诺“马上会有人联系”。通知投递失败不能丢掉待办，建包失败不能显示已转接。

### 8.4 避免给网格员新增负担

本阶段不要求工作人员在旧系统和本项目反复维护同一信息。先做模拟任务观察，再决定是否需要导入/导出或接入；不要在没有合作方流程的情况下建设复杂集成。

衡量的不只有老人提交速度，还包括工作人员是否需要重复询问、是否容易找到关键信息、是否增加无效待办。

## 9. 家属协助与紧急求助：保留价值，控制范围

### 9.1 暂不新增家属端

第一阶段做好老人联系合法联系人。后续可在居民端增加有限协助：查看被授权事项进度、补充指定字段、接收被授权通知。

需要明确本人同意、绑定验证、授权范围、期限、撤销和操作留痕；不能用“知道手机号”“同一社区”“同一家庭名称”直接授权。本人提交与代办提交要区分。

这项能力依赖授权体系成熟，不列入首个比赛版本的必做项。

### 9.2 紧急求助独立处理

保持专门入口、确认、取消和真实工作人员处置。不能将普通模型问答当作急救调度；没有接单能力时如实说明，保留既有联系途径。

演示使用合成联系人或只展示确认界面，避免向无关真实人员发求助。界面设计验证不需要真实触发紧急通知。

### 9.3 健康功能保持记录和提醒边界

保留已实现且经过授权检查的记录和提醒，不扩展自动诊断、调药、风险预测。系统提醒可靠性、来源与实际投递能力应独立说明；不把新首页上的一张卡片当作持续健康监护能力。

## 10. 技术升级：围绕这条主线复用现有系统

### 10.1 目标调用链

**多种输入 → 字段提取与缺失判断 → 草稿/纠错 → 用户确认 → 受控业务命令 → 真实结果 → 进度/播报/人工承接**

建议保持 FastAPI、Vue3、Naive UI、SQLite，先修调用边界。无需为重定位立即更换技术栈或训练模型。

| 层 | 责任 | 不能承担 |
|---|---|---|
| 语音/页面 | 收集输入、展示任务和结果 | 决定用户权限、编造业务状态 |
| 提取与协作 | 提出结构化字段和必要补问 | 直接绕过确认写库 |
| 业务执行 | 授权、状态约束、幂等、事务 | 用自然语言“看起来成功”替代提交 |
| 结果展示 | 根据事实产生短文案和播报 | 将失败统一包装成成功 |
| 人工队列 | 交接、领取、处理、回告 | 将通知发送等同于已接单 |

### 10.2 最小契约

- **身份上下文：**服务端可信 user_id、role、tenant、职责与授权关系。
- **草稿：**业务类型、字段值、来源、确认状态、冲突、版本、取消/过期状态。
- **命令：**操作者、业务动作、目标资源、预期版本、幂等键。
- **执行回执：**真实业务编号、结果、提交时间、下一步和可恢复原因。
- **交接包：**真实 id、已确认信息、未决问题、领取与处理状态。
- **通知事件：**合法收件人、投递结果、重试与去重信息。

这些是逻辑契约，先复用已有表和函数；只有缺失能力才新增版本化迁移。不为了架构图好看一次创建许多抽象层。

### 10.3 必须守住的事实

1. 不因老人需要帮助而降低授权要求。
2. 同一有效请求重复发送，不创建多张有效工单。
3. 没有真实记录，不说“已提交”或“已转交”。
4. 用户最新确认覆盖旧草稿，跨账号不恢复他人内容。
5. 通知只发给有权知道的人。
6. 被拒绝的内容不能在转人工提示中重新原样输出。
7. 脱敏或安全校验失败，不继续保存未处理原文。
8. 响应超时是结果待确认，不能自动判定一定失败。

### 10.4 九个角色如何处理

不以“全部角色都参与”作为完成标准。注册可以保留，日常报修只经过必要路径；天气、健康、通知等按真实事件触发。

普通流程先采用可解释规则。只有在缺失表达、复杂修正或跨业务判断中显示收益时，才引入相应模型协作。四五个清楚的责任边界比每轮展示九个节点更有说服力。

下面沿用评审证据，实施前应核对当前版本，不代表已修复。

| 优先级 | 已知问题 | 为什么影响适老主线 | 首轮验收 |

## 12. UI 设计与可用性验收

### 12.1 视觉方向

延续 v2 的浅色、克制蓝色、清楚层级。老人页面更宽松，工作人员页面更紧凑。颜色表达行动和状态，不给每个功能都配一种强烈颜色。

建议候选：正文 20～22px、主要动作 22～24px、关键热区 64～72px；这是项目设计目标，不是声称所有老人只需要这一组尺寸。关键内容允许放大和换行。

减少彩色 emoji、连续渐变、重复卡片和常驻动态；使用统一图标＋明确文字。普通老人无需看到 API、模型费用、执行链等实现细节。

### 12.2 第一批只深改六类页面

1. 老年首页。
2. 报修输入与补齐/确认。
3. 本人事项列表与详情/反馈。
4. 联系帮助及必要的错误恢复界面。
5. 网格待办列表与办理详情。
6. 人工交接包详情与回告。

“今日提醒”首轮复用现有安全可用的来源，主要做摘要聚合，不新建复杂推荐引擎。其余页面采用基础样式统一和稳定维护，居民端不全面重做。

### 12.3 所有页面都要设计的状态

正常、加载、空数据、无权限、请求失败、结果待确认、部分成功、已完成。错误信息说明影响范围和可采取的动作，不只显示“发生错误”。

关注键盘和屏幕阅读器、焦点可见、读序、输入标签、模态框返回焦点、亮暗主题、软键盘遮挡、窄屏与文字放大。自动审计和视口截图不能替代老人实际操作观察。

### 12.4 用户验证的任务

让用户在不被提前教会按钮位置的情况下完成：

- 找到报修入口。
- 说出或选出问题并补齐位置。
- 改正一个故意设置的错误。
- 确认提交并指出真实结果。
- 找到后续进度或待补充信息。
- 在语音不可用时换一种方式。
- 遇到问题时找到合法帮助入口。

不要问“这个界面是不是比以前好看”；观察用户在哪里停下、误点、犹豫和需要提醒。因设备或听力差异无法完成时记录具体原因，不能归因于“老人学不会”。

## 13. 怎样证明特色与技术贡献

### 13.1 分开回答三个问题

| 问题 | 实验设计 | 避免混淆 |
|---|---|---|
| 新 UI 是否更容易使用 | 相同后端/任务，对比旧页与新页 | 不把后端改进算作视觉收益 |
| 结构化补齐是否更可靠 | 相同输入、工具和授权，对比固定流程与升级机制 | 不用弱基线制造优势 |
| 语音是否带来帮助 | 记录识别错误、修改与不同输入方式完成情况 | 不把理解模块错误全部归给语音识别 |

### 13.2 比前版更小、更贴题的首轮评测

首轮采用 **90 个场景：开发 30、冻结业务测试 40、安全故障 20**。与前版 120 条相比减少数量，是为了聚焦适老交互并留出真实观察时间，不是宣称更小样本更有统计力。

40 个业务测试可按完整描述、缺信息、改口纠错、中断恢复、需要人工帮助五类各 8 个。20 个安全故障场景另报，不混进普通办理成功率。

案例按表达模板和任务来源分组，避免换词后分到开发与测试两侧。每条注明期望字段、合法终态、允许交接条件和禁止副作用。

### 13.3 三组对照足够起步

- **A：简洁表单/固定规则追问。**同样支持必要确认与纠错，是合理强基线。
- **B：规则驱动的适老引导流程。**逐步补齐、结构化摘要、明确恢复，不依赖复杂模型协作。
- **C：在 B 基础上加入有约束的模型理解/必要协作。**工具、数据、权限和提交机制一致。

先比较 A/B 的交互负担，再比较 B/C 在复杂表达上的实际收益。若 C 没有改善，就保留 B。多角色与单角色的额外消融可放赛后，不要求单人在首轮完成一套庞大实验矩阵。

### 13.4 指标

| 指标 | 具体记录 |
|---|---|
| 独立任务完成 | 无主持人引导能否达到正确终态 |
| 关键字段正确 | 最终问题/位置是否与用户确认一致 |
| 纠错成功 | 更正后是否真实替换旧值 |
| 用户负担 | 不必要补问次数、误点、求助主持人的次数 |
| 结果理解 | 用户能否说清当前状态和下一步 |
| 交接质量 | 工作人员还需重新问几项已经问过的信息 |
| 系统可靠性 | 假成功、重复有效建单、越权副作用 |
| 时间与成本 | UI 操作时间与系统等待分开；记录模型成本和延迟 |

语音相关测试另记设备、浏览器、环境和支持范围。不能仅凭“语音识别字数准确”推导整个任务可靠。

### 13.5 小范围用户观察

目标是邀请 **5～8 名实际目标用户**，另加 1～2 名了解网格工作的人。人数是可行性建议，不是显著性保证；无法找到真实网格员时要注明替代者身份。

使用合成资料和不涉及真实求助的任务，提前说明测试目的，不评价参与者能力。记录时间和行为需获得同意；录音录像非必须，避免为做展示多收个人信息。

同一个人测试旧/新页面时调整顺序和任务，减少熟悉效应。报告原始人数和任务结果，不把 5 人观察写成适用于所有老人。

### 13.6 继续与停止条件

- 测试出现越权副作用、虚假成功或重复有效建单：先修复，不扩真实使用。
- 新 UI 仍反复需要主持人指路：重排入口和文案，不先加语音模型。
- 规则引导已解决大部分任务：保留简单方案，把模型限制在有收益的表达。
- 用户不理解“已提交/待处理”：先修状态解释，不只增加颜色。
- 网格员接到更多无效任务：检查信息补齐与业务范围，不单独追求老人提交速度。
- 无明确承接方：可以继续做实验原型，不宣称已提供持续办理服务。

## 14. 分阶段实施与预算

### 14.1 赛前只有几天时

只做已验证的小范围改动：首屏顺序、减少重复导航、入口文案、明确错误状态，以及能完成回归的关键缺陷修复。

不要赛前同时改语音引擎、状态机、数据库结构、所有导航和全部 CSS。准备合成数据的完整演示与标注清楚的预录备份。若缺陷无法及时验证，保持受控演示并明确边界。

### 14.2 首轮 12 周最小版本

假设每周 20h，共 **240h**。计划工作 **192h**，缓冲 **48h**。这是较 v2 主动缩小范围后的 MVP，不是把 v2 的 320h 压缩完成。

| 工作包 | 预算 | 范围 |
|---|---:|---|
| 需求、范围、状态和授权契约 | 16h | 一个报修场景，三端分工与成功定义 |
| 关键安全缺陷 | 36h | 已知高风险路径与正反例；不足则占缓冲并暂停扩功能 |
| 办理可靠性与人工交接 | 44h | 纠错/草稿、确认、幂等、真实回执、真实队列 |
| 核心适老 UI 与网格承接 | 40h | 六类页面/状态，不是全部页面重做 |
| 场景评测与结果分析 | 24h | 90 场景起步，A/B/C 对照 |
| 目标用户观察与必要修正 | 16h | 预约等待可能需要额外日历时间 |
| 文档、复现和演示 | 16h | 原始证据、边界、录屏和复现说明 |
| **计划合计** | **192h** | **另留 48h 缓冲** |

预算为规划估计，安全层、历史代码耦合或数据标注可能超时。每周按结果调整，不把“第几周”作为跳过验证的理由。

| 周 | 建议主任务 | 可检查的交付 |
|---:|---|---|
| 1 | 明确用户、场景和授权，归档当前操作基线 | 范围清单、任务样例、状态/权限表 |
| 2 | 老人资源与同社区所有权修复 | 合法/非法操作验证 |
| 3 | 通知边界、假成功、必要旁路收口 | 失败与真实交接证据 |
| 4 | 首页、导航、核心组件与状态线框 | 三类目标用户能理解的入口 |
| 5 | 报修补齐、确认和纠错页面 | 更正字段后摘要正确 |
| 6 | 草稿恢复、幂等与结果查询 | 中断/重复提交不失真 |
| 7 | 网格待办、人工领取与回告 | 老人—工作人员闭环 |
| 8 | 浏览器旅程、语音替代与真机检查 | 关键任务实际点击可完成 |
| 9 | 完成开发集与故障集，冻结测试集 | 30/40/20 划分及评分规则 |
| 10 | 运行 A/B/C 对照，记录失败与成本 | 原始结果，不调参刷测试集 |
| 11 | 目标用户观察、必要修正 | 卡点、纠错、结果理解记录 |
| 12 | 复现、答辩、视频及后续取舍 | 可解释的成果包 |

这不是保证每周任务恰好 16h。时间不足优先砍掉政策评测扩展、全站重做和额外协作实验，不砍关键授权、真实性或回归。

### 14.3 明确不在首轮预算里的内容

完整家属协助系统、全部旧页面重设计、政策 RAG 大样本研究、新硬件、长期运营监控、真实机构系统接入、数据库平台迁移、医疗决策、全天候应急响应。

12 周最小版本完成后，才能根据实际需求选择其中一项；不再全部并行。

| 7 | 网格待办与处理包承接 | 3、5 | 能领取、补问、回复与关闭 |
| 8 | 语音、文字、短语替代与错误恢复 | 6 | 不支持语音仍可完成核心任务 |
| 9 | 浏览器/故障验收 | 5～8 | 端到端行为与副作用符合契约 |
| 10 | A/B/C 场景对照与用户观察 | 9 | 技术与 UI 收益分开，失败记录完整 |
| 11 | 材料、视频、复现与试点决策 | 10 | 每项对外结论有当前版本证据 |

实施时先读取当前 AGENTS 与交接约定。已有要求仍有效：不在未获确认时执行会与演示服务冲突的全量测试；需要你手动停服务并确认。长期应把测试与演示数据隔离，但完成之前不能假定隔离已成立。

## 16. 比赛怎么讲，特色才会被记住

### 16.1 一个故事比十个模块更有效

**故事：**老人想反映楼道灯坏了，表达不完整且中途改口；系统帮助确认并提交，工作人员接到清楚的事项，老人收到能听懂的结果。

演示建议：

| 段落 | 建议时间 | 展示重点 |
|---|---:|---|
| 用户困难 | 30 秒 | 不熟悉表单、表达不完整、提交后不知道结果 |
| 老人表达与纠错 | 90 秒 | 只补问必要内容，更正实际生效 |
| 确认与真实提交 | 40 秒 | 真实编号与下一步 |
| 网格处理与回告 | 80 秒 | 当前页面真实状态流，不能省略必要步骤 |
| 一个失败/交接案例 | 40 秒 | 无法理解或提交失败时不会假成功 |
| 证据与边界 | 20 秒 | 测试范围、用户样本、仍未完成的能力 |

时间只是演练预算。功能未实现时用明确的设计说明，不能用静态原型冒充运行结果。

### 16.2 可以成立的技术贡献

“我针对老年用户表达不完整和操作易中断的问题，建立了字段来源与纠错确认机制，并让多种输入方式进入统一受控办理链。通过真实回执和人工处理包，避免对话承诺与业务事实脱节。效果用规则基线、模型增强对照和目标用户任务观察分别验证。”

若实验没有证明模型增益，就说工程贡献在可靠性与适老交互。不要为了回应“技术壁垒”强行声称算法原创。

### 16.3 回应老师“容易复制”

可以答：

“界面和技术栈可以复制，我不把它们当壁垒。我要积累的是老人真实表达与错误恢复的场景集，以及工作人员承接后的流程证据。现阶段我先证明特定任务做得更清楚、更可靠，是否能形成产品壁垒还要看试点。”

### 16.4 三个需要当场答得清的问题

- 为什么不用普通表单？——普通表单本身是强基线，需要证据说明哪些用户、哪些任务确实从补齐和纠错中受益。
- 为什么不用一个通用聊天机器人？——因为业务权限、真实提交、进度与人工责任不能靠一段自然语言完成。
- 老人不用手机怎么办？——当前 Web 原型不能覆盖所有人；后续可研究经授权的工作人员代录，而不是宣称人人可用。

## 17. 首轮验收与真实试点条件

### 17.1 可以认为完成升级的证据

| 方面 | 必须看到什么 |
|---|---|
| 产品 | 老人能找到主要任务；没有再次增加大量首屏入口 |
| UI | 核心任务在目标设备可完成，失败和取消可理解 |
| 办理 | 输入更正、确认、提交、进度、反馈一致 |
| 权限 | 本人/他人、社区、角色、授权关系正反例 |
| 可靠性 | 故障场景无假成功、无重复有效建单、无错投 |
| 人工 | 有真实待办与领取/回告，不只发一条聊天提示 |
| 评测 | 原始案例、配置、版本、计数与失败报告 |
| 表达 | 不把计划、历史结果或合成数据说成当前真实成果 |

测试样本通过不是“系统绝对安全”。报告适用范围和未测组合，继续维护回归。

### 17.2 真实试点之前

先找一个愿意承担接单和反馈的合作方，选一个非紧急场景，明确服务时间、责任与异常处理。确保已有高风险授权问题关闭，备份恢复和部署可由他人完成。

首次试点不以模型完全自主办理为目标，可采用工作人员确认模式。先观察是否减少重复询问和遗漏，是否增加录入负担，再谈扩大范围。

### 17.3 下一阶段的选择规则

- 老人任务完成改善、网格负担没有增加：深化当前场景。
- 老人容易用，但工作人员重复录入严重：优先接入已有工作流。
- 家属协助需求明确且授权体系成熟：增加有限代办，不先建新门户。
- 规则引导与模型效果相当：减少模型调用。
- 目标用户对报修场景需求不强：重新选择场景，不继续堆模块掩盖定位问题。

## 18. 本周就能开始的五件事

1. **写一张功能去向表。**按本方案标记主线、二级保留、暂停扩展，不先删代码。
2. **画三张线框。**老年首页、报修确认、网格待办；明确每页用户下一步。
3. **准备十个任务。**包括缺位置、改口、取消、刷新、重复点击、语音不可用、需要人工。
4. **把严重缺陷变成可复现任务卡。**先授权和真实交接，不能用新皮肤覆盖。
5. **找目标用户看任务，不看宣传。**观察入口、纠错和结果理解，记录反例再调整。

**最重要的三个交付：老人能办成一件事、工作人员接得住、你能用证据解释为什么这样设计。**
