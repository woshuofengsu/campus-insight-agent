## 2. 地区模型

- 层级：`NATIONAL(L0) > 省(L1) > 市(L2) > 区/县(L3) > 街道/社区(L4)`；
- 用户属地链（具体→宽泛）：`[社区, 街道, 区, 市, 省]`，外加 NATIONAL 兜底；
- **归一化必须处理复合串**：库里真实值有 `北京市`（39 条）与 `北京市海淀区`（1 条）→
  `normalize_area("北京市海淀区") -> {"北京市","海淀区"}`，匹配取**最具体**层级（区 > 市 > 省）；
- 空值 / `全国` / `通用` / `不限` → `NATIONAL`（覆盖所有人，**永不过滤**）；
- 归一不了的具体文本 → 保留原词 + 视作 `other`（**软降权、不过滤**，保留可发现性）。

## 3. 关键设计：属地只改"选谁"，不改"能不能答"（比 v1 更严）

v1 的"阈值改看 base_score"有个漏洞：如果本地条目 base=1.9 被属地抬成第 1，而一条全国条目 base=2.5 排第 2，
阈值只看 `results[0]["score"]=1.9 < 2.0` → **本来能自动答的，反而转人工了**（比现状更差）。

本版规则（**更安全，且 region=None 时与现状完全一致**）：

```
排序：final = base + region_boost        # 属地分只影响顺序
选答：answer_entry = final 排序里第一条 base >= 阈值 的条目
      · 有 → 用它自动回答（可能不是 final 第 1，但保证"答得准"）
      · 没有 → 走原有 RAG / 转人工分支（用 final 第 1 作为 RAG 的候选首条）
```

- 语义：**"都能回答时，本地优先；答不了时，绝不因为属地而降低门槛"**；
- `region=None` → `final == base` → `answer_entry == results[0]` → **逐字节等价于现状**。

加分表（两套检索共用同一份常量）：

| 级别 | 线上加性分 | RRF 重排分 |
|---|---|---|
| `local_street` / `local_district` | +1.5 | +0.30 |
| `local_city` | +1.0 | +0.20 |
| `local_province` | +0.5 | +0.10 |
| `national`（含空/全国/通用/解析失败） | 0.0 | 0.0 |
| `other`（明确外地） | −0.5 | −0.10 |

**加权只在 `base > 0`（主题已相关）时生效** —— 防止"属地很近但与问题无关"的条目被抬进结果。

## 4. 实施步骤（本版按此顺序落地，每步跑一次全量 pytest）

### WS1 · `utils/region.py`（纯函数，零 IO）
- `Region(community, province, city, city_id, district, street)` + `chain()` + `label()`；
- `normalize_area(text) -> set[str]`（别名：北京/北京市/京、海淀/海淀区、全国/通用/不限/空）；
- `resolve_region(community) -> Region`：命中 `config.REGION_BY_COMMUNITY`；**未命中回落 config 全局城市并 `warning`**（不允许静默无效）；
- `policy_region_boost(applicable_area, region) -> (boost, level)`；`region=None` → `(0.0, "national")`；
- 常量：`REGION_BOOST_*` / `RRF_REGION_*`（两套检索共用）。

### WS2 · 政策线上检索（`data/db_policy.py`）
- `search_published_knowledge(query, top_k=5, category=None, region=None)`：
  双分（`base_score` / `final_score`）、`region_level`、只在 `base>0` 时加权；`region=None` 顺序不变；
- `ask_question(..., region=None)`：按第 3 节规则选 `answer_entry`；`region` 透传到两次检索调用；
- 返回体带 `region_level` / `final_score`（可解释展示："已按海淀区属地优先"）。

### WS3 · Agent RAG（`agent/rag.py`）
- `search_hybrid` 的 select 增加 `k.applicable_area`；RRF 融合后按 `RRF_REGION` 小幅重排**再截断 top_k**；
- `get_rag_context` / `rag_search` 增加 `region=None` 透传；
- `region=None` 时顺序不变（回归断言）。

### WS4 · 天气三端属地化（`tools/query_weather.py` + `data/db_weather.py` + 3 个入口）
- `get_today_weather(city="", city_id="")` → 透传 `fetch_real_weather_days(api_key, city_id or 默认, city or 默认)`；
- `_fetch_days(city="", city_id="")` **真的把参数用起来**；`refresh_weather(city, city_id)`、`get_weather_for_display(city, city_id)`、
  `get_simplified_weather(city, city_id)`、`get_daily_advice(force, city, city_id)` 全链路透传；
- **缓存键统一为 `city_id or city`**（`weather_cache.city` 存这个键）；
- **每日建议缓存修复**：`action` 改为 `生成穿衣出行建议[<key>]`，避免"A 社区生成后 B 社区拿到同一份"；
- 入口：`/weather/current`、`/weather/forecast` 解析 `_user(request).community` 传入；**`/elderly/home` 同样传入**；
  `agent/web_agent_service._exec_weather` 接受可选 region（由会话上下文提供）；
- 响应里带 `region_label`（如"北京市海淀区"）供前端展示。
