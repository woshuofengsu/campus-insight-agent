# 地区识别（属地化）落地方案 —— 天气按城市、政策按行政区划的"属地自适应"

> 状态：可执行设计（未动代码） · 日期：2026-09-14
> 设计原则：**地区来自"用户所属社区"，不做设备 GPS/IP 自动定位**；最小改动、默认行为不变（region=None 时与现状逐字节一致，保证 581 测试不破）；不新增数据库迁移。
> 适用范围：竞赛必须项（WS1–WS4，约 2–3 人日）+ 生产化可选项（第 8 节，比赛期不做）。

## 0. 结论先行（TL;DR）

1. **要加，但加的是"属地解析 + 检索属地加权"，不是定位授权。** 天气、政策确实随地区变化，评委会问；但正确解法是用账号里已有的 `community` 推断属地（真实政务系统也是"人属于哪个街道看哪个街道的数据"），GPS/IP 定位对单社区 Demo 零收益、还带来授权弹窗和隐私口径，属于过度设计，明确不做。
2. **地基已经有了，只差"接线"**：
   - 政策表 `knowledge_base.applicable_area`（适用地区）字段、增删改、导入**全都有**，但**检索时完全没用**（`data/db_policy.py` 的 `_score_entry/search_published_knowledge` 不读它）——本方案核心就是把它接进排序。
   - 天气已有全局城市配置 `config.COMMUNITY_CITY/COMMUNITY_CITY_ID(adcode)/COMMUNITY_DISTRICT`，天气缓存本就按 city 分键——只需把"全局常量"换成"按社区解析"。
3. **不需要 v47 迁移**：政策地区字段已存在、天气缓存已按城市分键。`community→region` 映射放配置即可；只有未来做多租户时才需要 `community_regions` 表（第 8 节）。

## 2. 地区模型设计

### 2.1 行政层级与属地链
- 五级：`全国(L0) > 省/直辖市(L1) > 市(L2) > 区/县(L3) > 街道/社区(L4)`。
- 一个用户解析出一条**属地链**（由具体到宽泛）：`[社区, 区, 市, 省]`，外加"全国"作为通用兜底。
- 一条政策的 `applicable_area` 归一到若干层级 token；空值/"全国"/"通用"视为 **L0 通用，适用所有人**。

### 2.2 别名归一（解决脏数据/口语）
`normalize_area(text) -> set[token]`，内置别名表：
- `北京/北京市/京` → `北京市`；`海淀/海淀区` → `海淀区`；同理朝阳等；
- `全国/通用/不限/''` → `NATIONAL`；
- 归一不了的具体文本 → 保留原词但标记 `unknown`，**按"全国"处理（安全默认：解析不了不惩罚、不误排）**。

### 2.3 属地匹配关系
对用户属地链 `chain` 与政策地区 token 集 `area`：
- `area ∈ {NATIONAL}` → **覆盖所有人**（永远可被召回，绝不过滤）；
- `area ∩ chain ≠ ∅` → 命中，取交集里**最具体的层级**（社区/区 > 市 > 省）；
- `area` 是具体外地、且与 chain 无交集 → "外地政策"，**软降权、不过滤**（用户可能确实在问外地，保留可发现性）。

### 3.3 政策线上检索：`data/db_policy.py`（核心）
**关键安全设计：属地只改"排序"，不改"能不能自动回答"的阈值判定。** 因此保留两个分：
- `base_score` = 词法+语义（现有 `s`，用于和 `_match_threshold` 比较，决定自动答/转人工）；
- `final_score` = `base_score + region_boost`（仅用于排序/取 top1）。

修改 `search_published_knowledge`（290 行）签名加 `region=None`，打分循环（318–326）改为：
```python
def search_published_knowledge(query, top_k=5, category=None, region=None):
    ...
    for e in candidates:
        base, _ = _score_entry(query, e)
        d = dense.get(e.get("id"))
        if d is not None: base += _DENSE_WEIGHT * max(0.0, d)
        rb, lvl = policy_region_boost(e.get("applicable_area", ""), region)
        if base > 0:                       # 属地加权只在"主题已相关"时生效
            final = base + rb
        else:
            final = base                   # 主题不相关，属地再近也不抬（防本地无关条目误自动答）
        if final > 0:
            e["base_score"] = round(base, 4)
            e["region_level"] = lvl
            scored.append((e, final))
    scored.sort(key=lambda x: -x[1])       # 稳定排序：同分时本地自动在前
    ... e["score"] = round(final,4)        # 展示分=最终分
```
> 自动答阈值处（`ask_question` 内比较 `_match_threshold` 的地方）改用 `base_score` 判断；`score/region_level` 仅用于排序与可解释展示（回答里可显示"已按海淀区属地优先"）。
> `region=None` 时 `rb≡0`、`final==base`，输出顺序与现状完全一致 → 现有测试零改动。

## 4. 测试方案（新增 `tests/test_region.py` + 扩展，改后必须全绿）

### 4.1 纯函数单测（utils/region.py）
- 别名归一："北京""北京市""海淀""海淀区"→标准 token；"全国"/空/乱码→NATIONAL/安全兜底。
- `resolve_region`：命中映射；未知 community 回落到 config 默认；None 不报错。
- 覆盖判定：全国覆盖任意 chain；区级命中同时算命中市级链；外地不命中。

### 4.2 政策排序（db_policy）
1. 主题同等相关时，"海淀区"条目排在"全国"前；
2. 只有"全国"时仍能召回（**绝不因属地过滤导致空结果**）；
3. 外地条目被软降权但仍在结果中（可发现性）；
4. **安全门槛**：主题不相关(base=0)的本地条目不会被属地分抬进结果/不会触发自动答；
5. **自动答阈值用 base_score**：构造"本地弱命中 base<2.0、加 boost 后≥2.0"的用例，断言仍转人工（属地不改安全阈值）；
6. `region=None` 回归：随机 20 条 query 的返回顺序与改动前完全一致（快照/排序断言）——保证 581 不破。

### 4.3 RAG（agent/rag.py）
- RRF 后近同分时本地在前；region=None 顺序不变；外地小幅后置但不丢失。

### 4.4 天气
- `get_daily_advice(city_id=X)` 请求用 X、缓存按 X 分键；city_id 缺省用全局默认；未知社区回落默认且 location 标签正确。

### 4.5 端到端（用现有 TestClient 模式）
- 构造 community=演示社区 的登录态调 `/api/web/.../qa/ask`，返回里 `region_level=local_district` 且本地条目 top1；
- 天气 current 接口返回的 `location` 与解析属地一致。

### 4.6 评测门禁
- `rag_eval.py` 属地金标 hit@1=100%，总体 hit@1 不下降（现 100%）。

## 8. 明确不做（防止过度设计）与生产化路线

**比赛期不做（评委问起就说"有意留到生产"）：**
- ❌ 浏览器 GPS / 蓝牙信标 / IP 地理库自动定位：授权弹窗损害老年体验、IP 定位常错到别的区、新增 PIPL 采集面，单社区 Demo 无收益。
- ❌ 完整国标行政区划表与级联选择器、`community_regions` 表与 v47 迁移：当前一个社区，配置映射足够。
- ❌ 按社区拆分的天气守护定时任务矩阵：现单社区用默认城市即可。

**生产化/多租户阶段再做（与既有 roadmap 的 tenant_id、SQLite→PG 同批）：**
- 新增 `community_regions(community PK, province, city, city_id, district, street, tenant_id)`，`resolve_region` 优先查表、回落 config（接口不变，只换数据源）——这才需要一次 `_m47_` 迁移，遵守"改数据层走迁移注册、不裸 ALTER"。
- 天气守护/预警任务按启用社区遍历；政策按 tenant+属地隔离；地区维度纳入红黑榜/满意度下钻统计。

## 9. 风险与边界（提前规避）

| 风险 | 对策 |
|---|---|
| 属地加权把弱相关本地政策抬成"自动回答" | base/final 双分，阈值只认 base_score；加权仅在 base>0 生效（4.2 第 4/5 条测试固化） |
| 本地无政策时查空 | 全国条目永不过滤、永远兜底（4.2 第 2 条） |
| applicable_area 脏数据/口语 | 别名归一 + 解析不了按全国，不惩罚不误排 |

| 两套检索口径不一致 | db_policy 与 rag 必须同批改，共用 utils/region 的等级与权重常量 |
| 隐私合规 | 地区来自账号归属、不采集设备位置，反而可作为 PIPL 数据最小化的正面论据 |
| 前端忘 build | F4 dist 新鲜度闸已会拦截，按提示 build 即可 |
