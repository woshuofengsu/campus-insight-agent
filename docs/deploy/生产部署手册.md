# 生产/试点部署手册（阶段 1A）

> 目标：把"能演示"变成"能在真实社区服务"，且**每一步都可验证、可回滚**。
>
> **当前状态**：编排与脚本已就绪（`deploy/` + `scripts/backup_db.py` + `scripts/restore_drill.py`
> + `scripts/empty_db_drill.py` + `scripts/bootstrap_admin.py`），**但本机没有 Docker / PostgreSQL**，所以：
> - **备份与恢复演练已在 SQLite 上真跑通过**（见 §5，含真实耗时）；
> - **空库初始化演练已在本机真跑通过**（见 §4，含"演练抓到一个生产安全洞"的记录）；
> - **Docker 编排与 PostgreSQL 路径尚未真实执行** —— 第一次上服务器时按本手册逐项走完再宣布可用。

## 1. 开始之前（只能由人做）

| 项 | 说明 | 备注 |
|---|---|---|
| 云服务器 | 1 台即可（2C4G 起） | 单社区试点规模不需要集群 |
| 域名 | 一个子域即可，如 `insight.example.org` | |
| **ICP 备案** | 国内服务器**必须** | ⚠️ **唯一不受你控制的长周期项**，先提交、与写代码并行 |
| 服务器安全组 | 只开 80/443；SSH 限来源 IP | 不要开 8000 到公网 |
| 密钥 | `WEB_JWT_SECRET` / `CRYPTO_KEY` 各生成一份 | 见 `.env.production.example` |

## 2. 环境分层（三套，**库与密钥都必须分开**）

| 环境 | 用途 | 数据库 | 演示数据 | 谁能进 |
|---|---|---|---|---|
| dev | 开发/单测 | 本地 SQLite 临时库 | 随便造 | 你 |
| **staging** | 内部试运行、迁移演练、服务台平板演练、真实流程彩排 | 独立库 | 必须带 `is_demo=1` | 你 + 社区工作人员 |
| **production** | 试点 | **空库初始化** | **一条都不许有** | 真实居民/网格员 |

> **硬边界**：`is_demo=1` 的工单**不得进入生产统计**。v53 已加该字段，
> 网格端「人工修正对照清单」会把"已标记演示 / 未标记"分开报，并固定显示四条免责。
> 上生产前先跑 `python scripts/check_claims.py` 与网格端面板核对一次。

## 3. 首次部署（服务器上执行）

```bash
git clone <仓库地址> && cd campus-insight-agent
cp deploy/.env.production.example deploy/.env.production
# 逐项填写（尤其两个密钥、SITE_ADDRESS、DEMO_MODE=false）
chmod 600 deploy/.env.production

cd web && npm ci && npm run build && cd ..     # 本地构建（镜像内也会再构建一次，双保险）

docker compose -f deploy/docker-compose.yml --env-file deploy/.env.production up -d
docker compose -f deploy/docker-compose.yml ps        # 三个容器应为 healthy/running
```

首次部署的**验收（缺一不可）**：

| # | 检查 | 命令 / 方式 | 期望 |
|---|---|---|---|
| 1 | 应用起来且迁移到最新 schema | `docker compose logs app` | 无异常；`schema v54` |
| 2 | 登录页可达 | 浏览器打开 `https://<域名>/login` | 200，证书有效 |
| 3 | **生产姿态拒绝弱密钥** | 临时把 `CRYPTO_KEY` 改成占位值再起 | **拒绝启动**（这是有意的 fail-closed） |
| 4 | 演示登录在 production 不可用 | 打开 `https://<域名>/login` | 无"免密进入"入口 |
| 5 | 安全响应头 | `curl -I https://<域名>/login` | 有 HSTS / nosniff / X-Frame-Options |

| 7 | 备份任务在跑 | `docker compose logs backup` | 打印"定时任务启动" |
| 8 | **生产库里没有演示账号/演示数据** | `python scripts/empty_db_drill.py` 或 §4 ③ | 演示账号 0 · 工单 0（**这一条曾经不成立，见 §4**） |
| 9 | **首个负责人账号能登进去** | 用 §4 ② 建的账号登录 | 能进 `/grid/dashboard`（登记完记进本手册末尾） |

## 4. 生产库初始化（**红线：绝不迁移演示库**）

```bash
# ① 空库初始化：只建表 + 跑迁移，**不灌任何演示数据/账号**
#    应用首次启动会自动建表；确认 schema 版本：
docker compose exec app python -c "import config; from data.db_core import init_db; init_db(config.DB_PATH); print('ok')"

# ② 建**第一个社区负责人账号**（空库里一个账号都没有，不建就登不进去）
docker compose exec app python scripts/bootstrap_admin.py \
    --username zhuren01 --name 王主任 --community 幸福里社区 --generate-password
#    · 强制 ≥12 位密码（`authenticate()` 对**空密码的居民账号**是放行的 —— 生产库里不能留这种账号）
#    · 拒绝 `demo` 开头的用户名（那是演示账号的命名前缀）
#    · 社区名必填：它是**租户键**，缺了 = 这个账号的数据谁都看不见
#    · 生成的一次性密码只打印一次，立刻记下来并在登录后改掉

# ③ 校验：生产库里演示数据/演示账号必须为 0
docker compose exec app python -c "
import sqlite3, config
c = sqlite3.connect(config.DB_PATH)
print('演示账号 =', c.execute(\"SELECT COUNT(*) FROM user_profile WHERE username LIKE 'demo%'\").fetchone()[0])
print('工单总数 =', c.execute('SELECT COUNT(*) FROM community_issues').fetchone()[0])
print('其中 is_demo=1 的 =', c.execute('SELECT COUNT(*) FROM community_issues WHERE COALESCE(is_demo,0)=1').fetchone()[0])
"
```

**为什么这么严**：本机演示库里的工单**全部**是演示/验证脚本产生的（当前 `350` 条工单里，
已标记演示 6 条，其余同样来自 `journey_check` / `demo_flow_check` 等脚本）。
把整库复制到生产 = 第一天就在真实社区里跑假数据，而且**试点指标全废**。

### 4.1 空库初始化演练（**已真跑通过，2026-10-06**）

```bash
python scripts/empty_db_drill.py          # 临时目录跑三种姿态，绝不碰演示库
```

| 检查 | 结果 |
|---|---|
| 演示姿态（`DEMO_MODE=true`）| 照旧灌演示账号与演示数据（演示/比赛不受影响）|
| 生产姿态（`DEMO_MODE=false`）空库 | **演示账号 0 · 工单 0 · 提案 0 · 知识库 0**，54 张表 + schema v54 齐全 |
| 生产姿态 + 缺密钥 | **拒绝启动**（fail-closed 没被绕过）|
| 演示库文件 | 大小/修改时间**前后一致**（证明"不迁移生产库"不是句空话）|

> ### ⚠️ 这个演练第一次跑就抓到一个**真的生产安全洞**（已修，见 dev-log 六十八）
>
> 原来服务启动路径 `api_web._ensure_db()` **无条件**调 `data.seed.seed_all()`，而 `seed_all`
> 对**空库**会灌整套比赛演示数据。也就是说：一套 `DEMO_MODE=false` 的生产空库，
> 第一次启动后会自动长出 **6 个演示账号（其中 2 个密码是 `demo123`）+ 38 条虚构工单 +
> 19 条提案 + 17 条知识库** —— 而**本手册写的是"一条都不许有"**。
> 文档与代码当时是矛盾的，而且只有**真跑一遍**才看得见（这正是"红线不能只写在文档里"的意思）。
>
> 修法三件：① `config.SEED_DEMO_DATA`（默认跟随 `DEMO_MODE`）让生产姿态不灌种子；
> ② `DEMO_AUTO_WORKER` 的默认值同样改为跟随 `DEMO_MODE`（原来恒 true，"忘了写"就会在生产
> 自动替网格员推进工单）；③ 补 `scripts/bootstrap_admin.py` 解决"空库没有账号怎么登进去"。
> 现在这几条由 `tests/test_prod_empty_init.py`（7 例）和本演练脚本共同守着。

### 4.2 staging 与生产的库必须分开

同一台机器上跑两套环境时用 `COMMUNITY_DB_PATH` 区分库文件（模板里已注释掉示例）：
预发**不许**指向生产库 —— 空库演练能做到"不碰演示库"，靠的就是这个变量。

## 5. 备份与恢复演练（**已在 SQLite 上真跑通过**）

```bash
# 手动备份（定时任务每天 03:10 也会自己跑）
python scripts/backup_db.py --keep 14 --include-uploads

# 恢复演练：还原到临时目录 + 六项校验 + 记录耗时
python scripts/restore_drill.py
```

**本次实测结果（2026-09-29，SQLite）**：

| 检查 | 结果 |
|---|---|
| 恢复耗时 | **0.02 秒**（含六项校验共 0.6 秒） |
| 完整性检查 | ok |
| schema 版本 | 53（与清单一致） |
| 关键表行数 | 全部一致 |
| 手机号明文残留 | 0 行 |
| 密文不可解密 | 0 行 |
| 租户字段为空 | 0 行 |

> 这个 `0.02 秒` 就是试点指标里"**备份恢复耗时**"的第一个真实数字（备份 22.72 MB）。
> ⚠️ 它有两个前提：① 演练是在**同一台机器**上做的，真实故障要加上"找到备份 + 传文件"的时间；
> ② 迁移到 PostgreSQL 后必须**重跑一次**（`pg_dump` 路径不同）。
> 演练脚本按纪律设计：**任一项不通过就退出码非 0**，不允许"看起来成功"。

## 6. 回滚流程（**跑过一次才算数**）

```bash
# 1) 停应用（数据库容器不动）
docker compose -f deploy/docker-compose.yml stop app

# 2) 回滚代码到上一个已知可用镜像
sed -i 's/^APP_TAG=.*/APP_TAG=<上一个可用tag>/' deploy/.env.production
docker compose -f deploy/docker-compose.yml up -d app

# 3) 若涉及数据结构变更：恢复备份（用演练脚本复位到备份快照）
python scripts/restore_drill.py            # 先确认备份可用
python scripts/restore_db.py --from <备份文件>   # 真正覆盖前**先人工确认**
```

> 纪律：**没真跑过回滚，就只能写"已编写回滚脚本，回滚演练尚未完成"**，
> 不许写"具备可靠回滚能力"。回滚演练记录（日期 / 耗时 / 遇到的问题）贴到本手册末尾。

## 7. 日常运维

| 项 | 做法 |
|---|---|
| 看服务状态 | `docker compose ps`（app 应为 healthy） |
| 看日志 | `docker compose logs -f app`；访问日志在 `proxy_logs` 卷（Caddy JSON） |
| 证书 | Caddy 自动续期；到期前 30 天可在日志里看到自动重签记录 |
| 备份检查 | 每天看 `backup` 容器日志；**每周做一次 `restore_drill.py`** |
| 磁盘 | `backups` 卷按 `BACKUP_KEEP` 自动清理；附件目录`uploads`需要人工盯 |
| 升级 | 改 `APP_TAG` → `up -d`；升级前后各跑一次恢复演练 |
| **观察期界面冻结** | `python scripts/freeze_check.py`（对着冻结点标签逐字比对老年端界面）。**真实老人观察期间每周跑一次**——中途改了界面，前后面向的就不是同一个东西，试点数据当场作废 |
