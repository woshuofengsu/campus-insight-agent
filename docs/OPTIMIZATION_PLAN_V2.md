# 社区先知 CommunityInsight — 二次优化方案（V2，面面俱到）

> 依据：第二轮锐评（优化+老年关怀版后）+ 第三轮锐评（完整审查后）的全部发现，存档见 `docs/REVIEW.md`。
> 目标：把「看起来专业」变成「经得起 CI、评委、真实使用三重抽查」。
> 原则：先修「会翻车/会丢脸」的，再深化「竞争力」，最后做产品一致性；全程 `pytest` 全绿（且**无 key 也绿**）。

## 一、工程与 CI（P0，半天～1 天）

### 1.1 修复 CI（`.github/workflows/test.yml`）
- **pytest 路径补全**：纳入全部 `test_*.py`（`tests/` 目录整体收集即可），确保 `test_semantics.py` / `test_elderly.py` / `test_ablation.py` 进 CI。
- **名称更新**：`name: 309 Tests` → `name: CI (328+ Tests)`。
- **不依赖真实 key**：`test_deepseek_compat.py` 改 `@pytest.mark.integration`（默认 `-m "not integration"` 跳过），或 mock 掉 OpenAI client；CI 不再需要 `DEEPSEEK_API_KEY` secret 也能绿。
- **验收**：PR 后 CI 全绿；`git clean` 环境下 `pytest -q` 无外部调用也全绿。

### 1.2 锁依赖版本
- 生成 `requirements.lock`（`pip freeze`）或用 `requirements.in + pip-tools` 两级管理；CI 与本地都装 lock 版本。
- 运行时依赖（streamlit/langchain）锁小版本（`>=x,<y`），避免大版本漂移。
- **验收**：两次不同日期的 CI 构建装到同一依赖版本；升级依赖是显式操作而非隐式漂移。

### 1.3 清理 dist 旧安装包
- 删除 `dist/CampusInsight_校园先知_一键安装包.zip`（名字过时 + 内容旧），按需用 `scripts/make_installer.py` 重建 `CommunityInsight_社区先知_一键安装包.zip`（脚本已排除 `.env`/`.db`）。
- **验收**：`dist/` 无「校园先知」旧包；新包解压后无 `.env`/`.db`。

### 1.4 测试分层与标记（P2 顺带）
- `pytest.ini` 定义 `markers = unit, integration, e2e, smoke, integration_api`；`test_ablation.py` 标 `smoke` 并从默认断言语义中逐步脱离（本轮只标标记，不重构其返回 dict 的设计）。

### 1.5 配置键弃用点（P2）
- `config.py` 保留 fallback 但加注释与文档：`CAMPUS_*` 为「v2 前旧键，v3 移除」；`.env.example` 只用 `COMMUNITY_*`。
- **验收**：文档写明弃用计划；代码搜索 CAMPUS_* 仅剩 fallback 与迁移。

- **验收**：README 有明确数据声明；若选 B，本地/线上两环境测试通过。

## 三、Agent 竞争力深化（P1 核心）

### 3.1 评测 v2：去自证（P1，半天）
- **加泛化场景**：10 个**关键词表里绝对没有**的新说法（如"家门口地砖翘起来了""楼道里老有股味"），只靠 LLM 语义层判断。
- **LLM 版评测**：`eval_suite.py` 支持 `--mode llm`（有 key 时跑），输出真实泛化命中率 + 每场景的 LLM 判定。
- **指标拆分**：关键词命中率 / LLM 兜底命中率 / 综合命中率，分开展示——诚实面对"关键词表 100%"与"LLM 泛化 X%"。
- **验收**：报告展示两套数字；答辩可引用真实泛化率（哪怕 70%）。

### 3.2 语义路由反转：把决策权交还给 LLM（P1，1 天）
- 现状：关键词表优先，LLM 只在 miss 时替补。
- 改：`route_intent()` 改为 **LLM 优先**（明确工具 + 置信度），关键词表降级为：
  1. LLM 不可用/超时时的兜底；
  2. 高置信关键词（"社区脉搏"等）可跳过 LLM 直判。
- 引擎 `_orient` 注入「建议工具」保留；同时把 LLM 路由结果写进 `intermediate_steps` 供评测统计。
- **验收**：泛化场景命中率显著提升；无 key 时自动回退关键词（三层回退不变）。

### 3.3 事实校验升级：数字核对（P1，半天）
- `verifier.py` 除了 `#编号` 存在性，增加**数值核对**：提取回复中的「X 件 / Y% / Z 天」等，与 `get_issues_stats`/`get_sla_summary` 实际值对比，偏差超阈值（如 20%）追加更正提示。
- **验收**：构造"解决率 95%"但实际 70% 的回复，校验器能提示。

### 3.4 Plan-and-Execute 真循环（P2，2 天）
- `planner.py` 从「注入建议步骤」升级为**执行循环**：`plan → 逐步 execute（调真实工具）→ 校验 → 结果汇入回复`；失败自动 replan（最多 2 次）。
- 保留三层回退：planner 异常 → 现有 AgentExecutor 直接执行。
- **验收**：复合查询（统计+提案）走规划循环，步骤数/结果可观测。

### 3.5 多 Agent 真协作（P2，2 天）
- `workers.py` 升级为带**共享事件上下文**的协作：Observer 产出的事件（新热点/异常）→ Dispatcher 触发派单 → Auditor 复核，主 Agent 引用汇总结论；用 `activity_log`/`perception_log` 作为既有的通信载体，不引入消息队列。
- **验收**：一次感知周期内，Observer→Dispatcher 链在日志中可追踪。

## 四、居民体验（P1）

### 4.1 「办」字闭环：演示网格员机器人（P1，1 天）
- 新增 `data/db_demo_worker.py`：演示模式下，新工单进入自动处理流程（定时/感知触发：待处理→处理中（附处理备注）→已解决→通知居民），模拟"有人办"。
- 开关：`DEMO_AUTO_WORKER`（`.env`，默认开=演示闭环；关=真实人工流程）。
- **验收**：上报后 1 分钟内工单走完闭环并通知居民；关闭开关则恢复人工。

### 4.2 处理时间线可视化（P1，顺带）
- `issue_card`/详情加「上报→处理中→已解决」节点时间（复用 `activity_log` 已有记录）。
- **验收**：居民端可见工单生命周期节点。

### 4.3 信息架构收敛（P2，1 天）
- 居民 9 页 → 按"我要做什么"重组为 5 个主入口（对话 / 上报 / 我的 / 消息 / 社区动态），次级内容（治理看板/大屏/健康）收入二级导航或独立入口。
- **验收**：导航深度 ≤2 层；常用操作 ≤3 次点击。

## 八、风险与取舍

1. **语义路由反转**：LLM 优先有延迟与不确定性 → 必须保留关键词兜底 + 置信度阈值 + 评测验证，不允许"去掉保底层"。
2. **Postgres 迁移**：数据持久化是大工程 → 比赛期选「诚实声明演示重置」，Postgres 列为赛后。
3. **演示机器人**：自动处理可能让评委误以为真实 → 页面标注「演示流程」徽标，可开关。
4. **页面收敛**：删页面有评审风险 → 先合并入口（不删功能），保留深链接。
5. **多 Agent**：成本与复杂度 → Observer/Dispatcher 走规则，仅 Auditor 深度解读走 LLM（沿用现有原则）。
