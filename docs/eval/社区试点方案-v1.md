# 社区试点方案 v1（未开展）

> **状态：尚未开展。** 本文件是**可执行方案与空表**，不含任何试点数据。
> 在试点真实开始前，材料里只能写"尚无真实社区试点数据"。
>
> 定位：这是**一个社区、一个小范围、四周**的验证计划，目的是回答三个问题：
> ① 老人能不能自己把事办完；② 网格员愿不愿意真的用；③ 闭环是否比微信群更清楚。
> **不是**"上线一个平台"。

---

## 1. 试点范围（刻意做小）

| 项 | 取值 | 为什么这么定 |
|---|---|---|
| 社区数 | **1 个** | 两个社区并行会把运维与口径复杂度翻倍，过早了 |
| 网格员 | 2–3 名 | 太少覆盖不了轮班；太多观察不过来 |
| 社区管理员 | 1 名 | 负责看统计与兜底 |
| 服务站平板 | 1 台 | 老年端主要入口（不依赖老人自己装应用）|
| 居民规模 | 30–50 人 | 够形成队列，又不至于压垮单机 |
| 老人重点观察 | 5–8 位 | 与 `elderly-user-study-v1.md` 同一批人，不重复组织 |
| 周期 | **4 周** | 少于 3 周看不到"重复报修/超时"这类慢变量 |

**只开放四项业务**（其余先作为扩展模块，试点期不推广）：

1. 老人/居民反映问题（报修类）
2. 查看处理进度
3. 网格员接单与处理（含转人工）
4. 社区通知 + 人工帮助入口

**明确不在试点范围**：健康诊断、复杂政策判断、提案协商、多社区对比。
（不是这些功能不好，而是**高风险 + 高解释成本**，不该混进第一次试点。）

> ⚠️ 一条硬纪律：**试点期间不改老年端界面**。发现问题先登记，按"观察 → 登记 → 局部修复 → 重冻结"
> 走（见 `elderly-user-study-v1.md` §2）。否则第四周的数据和第一周不可比。

## 2. 老人端的三条入口（不依赖扫码）

| 入口 | 谁用 | 落地方式 |
|---|---|---|
| **服务站平板** | 主要入口 | 桌面上只有一个图标，打开即老年端；由工作人员协助确认身份 |
| 老人自己的手机 | 常用者 | 第一次由工作人员/家人把图标加到桌面；之后日常使用不依赖扫码 |
| 电话 / 人工代录 | 没有智能机的老人 | 社区服务电话、网格员代录、物业前台登记——**同一条工单闭环** |

提交时要记录**提交方式**（老人自助 / 家属代办 / 网格员代录 / 服务站平板），
否则统计口径会把"工作人员代录的成功率"算成"老人的成功率"。

## 3. 试点要收集的指标（三类，都是服务指标不是测试数）

| 指标 | 口径 | 目标值（**待验证**，不得写成已达成） | 实测 |
|---|---|---|---|
| 首次完成率 | 无需协助完成人数 ÷ 参与人数 | ≥ 80% | — |
| 完成时间中位数 | T1 从念完题到提交成功（秒） | ≤ 60 s | — |
| 操作步数中位数 | T1 实际点击数 | ≤ 4 步 | — |

| 需要代操作的比例 | 完全无法完成、需工作人员代录 | 只记录 | — |

### 3.2 网格员使用

| 指标 | 口径 | 数据来源 | 实测 |
|---|---|---|---|

### 3.3 系统可靠性

| 指标 | 口径 | 数据来源 | 实测 |
|---|---|---|---|
| 重复提交率 | 同一人同一分类跨天再报 | 已有 `/agent/governance-metrics` | — |
| 通知失败率 | 补发队列失败数 ÷ 通知数 | 已有 | — |
| 跨社区数据泄露数 | 必须为 **0** | `tests/test_tenant_idor_sweep.py` + 抽查 | — |
| "结果未知"后重复建单数 | 必须为 **0** | 幂等门禁 + 抽查 | — |
| **备份恢复耗时** | 从备份还原到可用（分钟） | **恢复演练实测** | — |
| 服务异常后的人工兜底率 | 异常期间走电话/代录的比例 | 人工记录 | — |

> 「备份恢复耗时」必须**演练过**才有数字。没演练过的备份等于没有备份。

## 4. 试点前必须就位的东西（部署清单）

这份清单是"从演示到能用"的门槛，与业务功能无关：

| 项 | 说明 | 状态 |
|---|---|---|
| 云主机（1 台即可） | 不要把唯一数据库放在个人电脑上 | ☐ |
| 域名 + HTTPS | 语音等浏览器能力依赖安全上下文 | ☐ |
| **每日自动备份** | 库文件 + 附件目录 | ☐ |
| **一次真实恢复演练** | 记录耗时，写进 §3.3 | ☐ |
| 正式密钥 | `WEB_JWT_SECRET` / `CRYPTO_KEY`（生产姿态缺失会拒绝启动） | ☐ |
| 管理员二次认证 | 生产必配 | ☐ |
| 访问日志与错误监控 | 至少能回答"昨天谁在什么时候调了什么" | ☐ |
| 数据保存期限与清理策略 | 与社区约定 | ☐ |
| 测试数据与真实数据分开 | 演示库**不准**接真实居民 | ☐ |

> 说明：**SQLite（WAL）在单社区 30–50 人量级够用**，试点期不必换 PostgreSQL。
> 真正的风险是"单点 + 没演练过备份"，不是"用的什么库"。换库的时机是量真的压上来之后，
> 那时换才有依据（见 `docs/scaling.md`）。

## 5. 伦理与合规（先做，别补）

| 项 | 要求 | 状态 |
|---|---|---|
| 知情同意 | 老人观察用 `知情同意书-老年居民.md`，逐条口头说明 | ☐ |
| 工作人员代录授权 | 老人同意后才能代录；代录要记代办人 | ☐ |
| 家属协助边界 | 家属可协助操作，但**不能**直接获得老人全部数据；老人可撤销授权 | ☐ |
| 平板共享安全 | 不保留上一个人的登录态与草稿；结束即清理 | ☐ |
| 数据最小化 | 平板上不落地与本次办理无关的信息 | ☐ |
| 退出机制 | 老人可随时退出，数据一并作废 | ☐ |

## 7. 试点之后才谈的事（现在不做）

- 微信小程序（**先验证有人愿意用，再花工期**）；
- 多社区部署与跨社区统计；
- PostgreSQL 迁移（**2026-10-06 已决策：试点期不做**，触发条件与施工图见 `docs/spec/升级方案/PG迁移盘点与计划.md` §0）；
- 短信/电话自动外呼通道（试点期只做站内通知 + 人工电话记录）。

> 顺序理由：这些都属于"验证有效之后的扩张"，过早做会让**试点本身**做不完。
