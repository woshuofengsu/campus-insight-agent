# 试点运营规则确认单（**必须与社区一起填完，才能开试点**）

> **用途**：用户清单里明确要求——找到真实社区后，先确认 9 条运营规则。
> 这张表不是"走流程的纸"：**每一条都对应系统里的一个开关或一段已有能力**，
> 填之前先看"系统在哪配"那一列，能配的当场配好，不能配的（人事安排）由社区定。
>
> ⚠️ **未填完不开试点**：规则不清的试点，出了问题没人认领，数据也没法解释
> （例如"谁负责关单"没定，就会出现工单永远挂着，而"处理时长"这个指标直接失真）。
>
> 填法：`社区确认` 列由社区负责人填写并署名；`系统配置` 列由我在试点前改好并跑门禁。

## 一、责任与时限（人事 + 系统）

| # | 规则 | 社区确认（填） | 系统在哪配 / 怎么落实 |
|---|---|---|---|
| 1 | **谁负责接单**（本社区负责人名单、是否分片包楼） | | 角色 = `grid`（`user_profile.role`）。账号用 `scripts/bootstrap_admin.py` 建（**不许用 demo 前缀**）。分片包楼暂不支持自动分派，由负责人在工单台自行认领 → **这条要写清"人工认领"** |
| 2 | **谁负责关闭工单**（关闭是否需要第二人复核） | | 关闭动作在 `/grid/work-orders`（`action=close`，**关闭原因必填**）；系统记录操作人（`operator`/留痕）。"第二人复核"目前**只能靠流程约定**，系统不强制 → 若社区需要，必须明说（我记为已知限制） |
| 3 | **紧急问题多久响应** | | 按社区规定的 SLA：`utils/issue_progress` 按状态给时限，超时**会在页面上明说超时**；SLA 参数按社区分键存 `settings` 表（`data/db_settings.py`，写社区键） |
| 4 | **普通问题多久处理** | | 同上（同一套 SLA 配置）；治理情景模拟器里的"平均处理时长"是**估算参数**，与真实 SLA 分开，不许混用 |

## 二、联系与代办（最容易出事的两条）

| # | 规则 | 社区确认（填） | 系统在哪配 / 怎么落实 |
|---|---|---|---|
| 5 | **通知失败后怎么联系居民**（电话？上门？多久一次） | | 通知有**补发队列**（未读/失败可补发）；紧急通知走 `managers_of(tenant)` + 升级通知名单（`/grid/weather` 的"超时升级通知名单"）。补发**仍需人工确认**，系统不替人打电话 |

## 五、进入下一阶段的判断（只看三个结果）

用户明确说的三条，我把"证据从哪来"也写清楚，避免自评自话：

| 判断 | 谁来判 | 证据（不是"测试通过"顶替） |
|---|---|---|
| ① 老人能否**独立完成**核心任务 | **只能由人**（5–8 位老人，4 个任务） | `docs/eval/elderly-user-study-v1.md` 的记录表 + 脱敏 CSV；**当前 0 位，未开展** |
| ② 网格员能否**快速处理**一条真实工单 | **只能由人**（真实工单 + 真实负责人） | 真实工单的处理时长（系统里有 `reported_at`/各状态时间戳可导出）；**当前无真实工单** |
| ③ 系统能否**安全保存、查询、恢复**真实数据 | 机器可验（已有证据） | 空库初始化演练 10/10 · 备份恢复演练（恢复 0.02s，六项校验）· 预发环境演练 15/15（跨库/跨密钥隔离）· 手机号密文落库审计 `scripts/audit_phone_encryption.py` |

> ⚠️ 口径纪律：**第 ③ 条跑绿 ≠ 前两条完成**。自动化验证只能证明"机制有效、可审计"，
> 不能替代"老人真的能办完事"。材料里不许把测试通过写成真实用户验证（已由
> `tests/test_claims_consistency.py` 与 `tests/test_pilot_freeze.py` 守着）。
