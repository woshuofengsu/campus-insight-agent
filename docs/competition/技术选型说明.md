## 决策总览（一页速览）

| # | 决策点 | 我们的选择 | 主要备选 | 一句话理由 | 代价 |
|---|---|---|---|---|---|
| 1 | 多智能体编排 | **自研黑板 + 编排器**（705 + 112 行） | LangGraph / CrewAI / AutoGen | 主链路要精确控制执行链、留痕与转人工 | 无现成图可视化与检查点，工具生态要自己写 |

| 7 | 鉴权 | **标准库 HS256 JWT** + 角色守卫 | 第三方 JWT 库 / 服务端会话 | 零依赖、可控；生产密钥 fail-closed | 无 refresh token 与吊销列表 |
| 8 | 字段加密 | **AES-256-GCM**（`cryptography`，`g1$` 版本前缀） | 自研 HMAC-CTR / 仅脱敏 | 真加密且可平滑换算法 | 密钥派生无盐无迭代；无信封加密 |
| 9 | 前端栈 | **Vue3 + Vite + Naive UI** | React 19 + Ant Design 6 | 差距在设计投入，不在框架 | AI 组件生态少，对话组件需手写 |
| 10 | 适老 | **独立老年端（8 页重做）** | 全局放大字号 | 老人需要的是"少而大"而非"小放大" | 三端维护成本；单屏信息密度低 |
| 11 | 移动端形态 | **Web + PWA（可添加到主屏幕）** | 原生 App / 带离线 SW | 免安装；不做离线以免展示过期数据 | 无离线能力；依赖浏览器 |
| 12 | 部署形态 | **本机回环 + 可选临时隧道** | 云服务器 / Docker | 演示零成本、数据不出本机 | 无访问控制；域名每次变化 |

## 一、多智能体编排：自研黑板 + 编排器 vs 成熟框架

**结论**：主链路用自研编排（`agent/orchestrator.py` 705 行 + `agent/blackboard.py` 112 行）。
早期原型用 LangChain AgentExecutor 的版本保留在 `app.py` 作为备线对照，不作为主线。

| 对比项 | 自研（当前） | LangGraph / CrewAI / AutoGen |
|---|---|---|
| 执行链可控性 | 每一跳由代码显式决定，可插入校验与仲裁 | 由框架运行时调度，插入自定义检查点需读源码 |
| 留痕 | 每个角色的动作、协商消息、仲裁决策统一落 `agent_logs` | 需自行适配框架的回调/追踪 |
| 失败处置 | 超时重试一次 → 仍失败转人工（生成处理包编号） | 多为抛异常或重试，转人工要自己接 |
| 循环防护 | 单目标协商 ≥2 轮强制转人工；链式遍历上限 5 轮 | 需自行实现终止条件 |
| 依赖 | 标准库 + 少量基础库 | 引入框架及其传递依赖，版本升级影响面大 |
| 生态 | 无（工具需自己写，现有 16 个） | 现成工具/集成多 |

**用真实场景走一遍**：一次输入内的跨角色协商

```
用户："明天高温，社区老人要注意什么？"
 ① 编排器建 ctx（含属地、天气、会话实体），派发给天气守护
 ② 天气守护取数 → post_message(type=notify) 给健康顾问
 ③ 健康顾问 process_negotiation → 生成健康提示 → post_message 给通知管理员
 ④ 通知管理员生成通知草稿 → task_response 回到发起方
 ⑤ 编排器 _drain_negotiations 逐轮消费队列，把"协作提示"合并进最终回复
 ⑥ 合规审计员对所有输出做脱敏/敏感词检查 → 通过后返回；不通过 → Arbiter 裁决 → 转人工
```

**代价与现状**：没有框架自带的图可视化与检查点恢复；新增能力要自己写工具（用 `pkgutil` 自动发现降低边际成本）。
**证据**：`agent/orchestrator.py::_dispatch / _drain_negotiations / _transfer_to_human`、`agent/blackboard.py`（历史封顶 500 条）、
`pytest tests/test_dispatch.py -q`、网格端「Agent 留痕」页可查仲裁记录。

## 二、检索：自研混合检索 vs 向量数据库 + 重排模型

**结论**：自研三路融合——**词法（同义词/方言扩展）+ 语义向量（百炼 `text-embedding-v3`，1024 维）+ RRF 融合（k=60）**，
不引入 ChromaDB/pgvector，也不上 Reranker 二段精排。

| 对比项 | 自研（当前） | ChromaDB / pgvector + BGE Reranker |
|---|---|---|
| 部署 | 与业务同库（SQLite + 进程内向量缓存 512 条），零额外服务 | 需独立向量库服务或 PG 扩展 + 模型文件 |
| 融合方式 | RRF（按排名融合，不依赖分数量纲） | 向量分数 + 关键词分数直接加权，或二段重排 |
| 召回质量 | 48 条口语金标 **hit@1 100%** | 语义召回更强，长尾与跨领域更好 |
| 规模适配 | 语料 62 条（55 条公开政策摘要）：规模小、优势不明显 | 数万条以上差距会拉开 |
| 可解释性 | 返回 `retrieval`（lexical/hybrid）、`base_score`、`region_level`，便于排查 | 分数来源较黑盒 |

**用真实数据走一遍**（同一个金标集，两套算子的对照）：

```
查询："老楼上下楼不方便，有没有办法？"（句中不含"电梯"二字）
【纯词法】命中《老旧小区加装电梯政策宣讲会》失败 → 整体 hit@1 = 85.7%
【加入语义向量 + RRF】语义路召回《…加装电梯操作指引》并前置 → 整体 hit@1 = 48/48 = 100%
属地用例（6 条，同题不同社区）Top-1 正确 4/4
```

**代价与现状**：语料规模仅 62 条，评测结论**不代表泛化能力**；无 Reranker，召回扩展不如图检索；
向量模型依赖外部 API（无 Key / 网络失败自动回落纯词法，`provider=none` 时行为与升级前逐字节一致）。
**证据**：`agent/rag.py`（`_RRF_K = 60`）、`utils/embedding.py`、`python scripts/rag_eval.py`。

## 三、知识图谱：轻量三元组 vs 图数据库

**结论**：用 SQLite 存实体—关系—提及（**89 实体 / 202 关系 / 772 提及**），**只做"按实体反查"**这一条链路，不引入 Neo4j。

| 对比项 | 轻量三元组（当前） | Neo4j |
|---|---|---|
| 用途 | 办单时"看到来龙去脉"：按实体反查历史工单与相关政策 | 多跳推理、路径分析、图算法 |
| 部署 | 与业务同库，无额外服务 | 独立数据库（JVM、内存占用、运维） |
| 数据规模 | 62 条政策 + 225 条工单，多跳场景本就不成立 | 适合十万级节点以上 |
| 可视化 | 不做（评审会追问"图谱解决了什么"） | 自带浏览器可视化 |

**用真实场景走一遍**：网格员处理电梯工单时按实体反查

```
GET /api/web/agent/kg/entity?name=电梯
→ 命中：**5 条历史工单 + 7 条相关政策 + 10 个关联实体**（端到端验收第 7 项实测）
用途：判断"这台电梯是不是反复报修"、该引用哪份政策，而不是让网格员自己去翻历史。
```

**代价与现状**：多跳查询与图算法能力弱（当前只支持一跳关联）；图谱是按需重建的派生数据（`python scripts/rebuild_kg.py`，或网格端一键重建 / `POST /api/web/agent/kg/rebuild`）。
**证据**：迁移 `_m45_knowledge_graph`、`data/db_kg.py`（`build_graph` / `query_entity` / `graph_stats`）、`python scripts/demo_acceptance.py`（第 7 项）。

## 四、数据库与迁移：SQLite + 自研版本化迁移 vs MySQL + Alembic

**结论**：SQLite（WAL）+ **46 个版本化迁移**（`data/db_core.py` 的 `_mN_` 注册表，幂等可重跑）；
**业务代码中不允许出现运行时 `ALTER TABLE`**（已核查：`ALTER` 仅存在于迁移函数与 `_add_column` 辅助内）。

| 对比项 | 当前（SQLite + 自研迁移） | MySQL + Alembic |
|---|---|---|
| 运维 | 单文件、零配置，演示/单社区可直接拷库 | 需数据库服务、账号、备份策略 |
| 迁移机制 | `_mN_name` 注册表 + `PRAGMA` 判存，新建库与存量升级**同一条路径** | Alembic 自动生成迁移脚本（功能更全） |
| 并发 | WAL + busy_timeout；**单写者** | 行级锁、真正并发写 |
| 多进程/多副本 | 不成立（换 PG 才成立） | 支持 |

**用真实场景走一遍**：新库与老库的升级路径

```
全新部署：init_db() → 顺序执行 46 个迁移 → schema_version = 46
存量升级：同一入口 → 逐版本比对并补齐（幂等，可重复执行）
历史欠账：v46 把早期"运行时补列"全部收回迁移链 —— 现在业务层 0 处 ALTER
```

**代价与现状**：单写者、多进程/多副本不成立（扩容路径 Redis + PostgreSQL 已在交付说明中给出）。
**证据**：`data/db_core.py`（`_m1_…` 至 `_m46_phone_enc_and_schema_drift`）、`PRAGMA integrity_check = ok`。

## 五、LLM 使用姿态：规则为骨、LLM 为脑 vs 全 LLM 编排

**结论**：四个特性开关（`LLM_ORCHESTRATION` / `POLICY_LLM_RAG` / `RECEPTION_LLM_FALLBACK` / `LLM_NEGOTIATION`）
控制 LLM 介入点；**代码默认全关**（纯规则可完整跑通），演示姿态按需打开。

| 能力 | 用的什么 | 关了 LLM 会怎样 |
|---|---|---|
| 意图识别 | 确定性规则 + 同义/方言归一；模糊时 LLM 闭集兜底 | 模糊表达落不到意图 → 走引导话术或转人工（不静默失败） |
| 政策问答 | 检索片段 + 引用强制；弱命中才 LLM 生成 | 弱命中直接转人工，不生成内容 |
| 跨角色协商 | 规则链为主，LLM 参与目标选择（白名单内） | 退化为固定规则链，仍会联动 |
| 工单状态机 / 权限 / 脱敏 / 风控 | **始终是确定性代码** | 不受影响 |

**用真实数据走一遍**：实测成本与延迟

```
单轮对话（演示姿态，含 LLM）：约 **+0.9 秒 / +¥0.0002**
累计（库内记账 `llm_usage`，2026-09-14 快照）：**57 次调用 / ¥0.0139**
（其中评测 40 题 ¥0.0109、跨角色协商 15 次 ¥0.0030）
可复核：python scripts/llm_cost.py
```

**代价与现状**：模糊/长尾表达的处理不如全 LLM 方案；需要维护规则与 LLM 两条路径的一致性（测试覆盖两种姿态）。
**证据**：`agent/intent_llm.py`、`agent/policy_rag.py`、`agent/llm_client.py`、`python scripts/llm_cost.py`。

## 六、实时通知：WebSocket vs SSE vs 轮询

**结论**：采用 **WebSocket**（`/ws/notify`），连接池在进程内。

| 对比项 | WebSocket（当前） | SSE | 轮询 |
|---|---|---|---|
| 方向 | 双向（可心跳、可客户端订阅） | 单向（服务端→客户端） | 单向（客户端发起） |
| 断线重连 | 需自行处理 | 浏览器自动重连 | 天然无状态 |
| 延迟/开销 | 低延迟、长连接 | 低延迟 | 取决于间隔，空转开销大 |
| 多进程 | 需 Redis 发布订阅（当前单进程内存池） | 同左 | 无需共享状态 |

**用真实场景走一遍**：网格员改工单状态 → 居民端收到通知

```
网格员：工单 #123 处理中 → 已解决
 ① 服务端写入状态并生成通知
 ② 通过 /ws/notify 推送给该用户（在线）→ 居民端角标实时更新
 ③ 用户离线：通知落库，下次进入消息中心可见（不依赖长连接）
```

**代价与现状**：连接池在进程内，多 worker 需 Redis；前端需处理重连与心跳。
**证据**：`api_web.py`（WebSocket 路由与安全头）、`web/src/views/grid/Notices.vue`（前端订阅与重连）。

## 七、鉴权：标准库 JWT vs 第三方库 / 服务端会话

**结论**：用标准库 `hmac` 自实现 **HS256 JWT**（无第三方 JWT 依赖），token 内嵌角色与社区，
配合角色守卫与登录失败锁定；生产姿态密钥缺失或为仓库占位值时**拒绝启动**。

| 对比项 | 标准库 JWT（当前） | 第三方 JWT 库 | 服务端会话 |
|---|---|---|---|
| 依赖 | 零额外依赖 | 引入库及其传递依赖 | 需会话存储（内存/Redis） |
| 水平扩展 | 无状态，天然可扩展 | 同左 | 需共享会话存储 |
| 退出/吊销 | **无吊销列表**（靠短有效期 + 锁定策略） | 库提供部分能力 | 天然可吊销 |
| 实现风险 | 自行实现需谨慎（已用标准 HMAC + 固定算法，禁 `alg` 混淆） | 成熟实现 | 成熟 |

**用真实场景走一遍**：越权与爆破防护

```
① 无 token 访问受保护接口 → 401（鉴权中间件）
② 居民 token 访问网格端指标接口 → 按角色拒绝（fail-closed）
③ 连续 5 次密码错误 → 同 username|IP 锁定 5 分钟（即便密码正确也拒绝）
④ 生产姿态（DEMO_MODE=false）：演示登录硬关闭；密钥缺失/占位 → 启动失败
```

**代价与现状**：无 refresh token、无吊销列表；令牌有效期是缓解手段而非根治（已列入后续工作）。
**证据**：`api_routes/deps.py`、`api_routes/auth.py`（`login` 的失败计数与锁定）、`api_web.py`（JWT 中间件与安全响应头）。

## 八、字段加密：AES-256-GCM vs 自研流密码 / 仅脱敏

**结论**：手机号等敏感字段用 **AES-256-GCM**（`cryptography` 库）加密落库，密文带算法版本前缀 `g1$`；
早期自研 HMAC-CTR 方案**仅保留解密兼容**。明文列置空，展示统一脱敏。

| 对比项 | AES-256-GCM（当前） | 早期自研 HMAC-CTR | 仅脱敏不加密 |
|---|---|---|---|
| 机密性 | 真加密（AEAD，含完整性校验） | 自研构造，风险高 | 无（库内即明文） |
| 算法轮换 | 密文带 `g1$` 版本前缀，可按前缀分支解密、平滑重加密 | 无版本信息 | 不适用 |
| 审计 | 8 张含手机号表明文计数 0，脚本可复算 | — | 明文计数 > 0 |
| 缺库行为 | `cryptography` 缺失时**拒绝加密**（fail-closed，不静默降级） | — | — |

**用真实数据走一遍**：审计命令与结果

```
python scripts/audit_phone_encryption.py
→ 含 phone 列的表：8；全部具备 *_enc 兄弟列，明文计数 0
密文形态：g1$<base64(12 字节 nonce | 密文 | tag)>
密钥派生：SHA-256(CRYPTO_KEY) → 32 字节（**无盐、无迭代**，已列入改进项）
```

**代价与现状**：密钥派生强度不足、无信封加密与轮换演练；**居民在工单正文里手写的他人手机号未脱敏**（自由文本 PII 未治理，已列入近期工作）。
**证据**：`utils/crypto.py`（AESGCM、`g1$`、12B nonce）、`scripts/audit_phone_encryption.py`、`tests/test_phone_encryption_v39.py`。

## 九、前端技术栈：Vue3 + Naive UI vs React + Ant Design

**结论**：采用 **Vue3 + Vite + Naive UI**，不追换 React/AntD。理由不是"框架更强"，而是：
**同名对标项目（React 19 + AntD 6）观感更好，差距来自设计投入而不是框架能力**——那 6 处真实差距（主视觉、动效层次、暗色一致性等）我们用设计令牌 + 客观审计补齐了，换栈并不能自动获得。

| 对比项 | Vue3 + Naive UI（当前） | React 19 + Ant Design 6 |
|---|---|---|
| 三端差异化 | 令牌体系自建，老年端可彻底重做 | 组件更"企业范"，改造成本相近 |
| AI 组件生态 | 少，对话/执行链组件手写（换来可完全自控） | 有 Ant Design X 等现成 AI 组件 |
| 审计友好度 | 组件结构简单，`ui_audit`/`mobile_audit` 可直接量对比度/热区/字号 | 需处理更多组件内部样式 |
| 迁移成本 | — | 重写三端 31 个页面，收益不确定 |

**用真实数据走一遍**：客观审计而非主观评价

```
python scripts/ui_audit.py    → 34 个路由页 / 54 个页面视口 × 9 类检查：0 违规
python scripts/mobile_audit.py → 21 页 × 7 类检查：全部通过
```

**代价与现状**：AI 交互组件需手写（多智能体执行链可视化为自研）；生态组件数量少于 AntD。
**证据**：`web/src/style.css`（设计令牌）、`web/src/views/{resident,grid,elderly}/`、两个审计脚本。

## 十、适老设计：独立老年端 vs 全局放大字号

**结论**：老年端 **8 个页面独立重做**（不是居民端放大）：字号 ≥20px、热区 ≥72px、层级压到最少、
只保留 SOS 一个呼吸动效、支持语音播报与预置短语、一键拨号。

| 对比项 | 独立老年端（当前） | 全局放大字号 |
|---|---|---|
| 信息密度 | 低（换可读性与误触率） | 高（老人易误触、迷失） |
| 语音 | 有（端侧 Web Speech，失败显式降级为打字 + 预置短语） | 通常无 |
| 紧急求助 | 一键 SOS + 二次确认 + 留痕，不自动拨 110/120 | 一般无 |
| 维护成本 | 三端各自维护 | 一套样式 |

**用真实数据走一遍**：审计卡阈值

```
mobile_audit：21 页 × 7 类检查 0 违规（含 iOS 输入框聚焦放大、底栏遮挡、横屏遮罩、老年端 20px 字号下限）
缺陷修复实例：老年端天气属地标签曾为 18.4px，被审计判不合格 → 调整为 1.3rem 后通过
```

**代价与现状**：三端维护成本高；老年端单屏信息量小；**语音在 iOS Safari / 微信内置浏览器可能不可用**（已备降级路径，真机待复验）。
**证据**：`web/src/views/elderly/`、`web/src/mobile.css`、`python scripts/mobile_audit.py`。

## 十一、移动端形态：PWA 可安装 vs 离线能力

**结论**：提供 manifest 与图标（可添加到主屏幕、standalone 打开），**不实现 service worker，不提供离线能力**。

| 对比项 | 当前（可安装、不离线） | 带 service worker 离线 |
|---|---|---|
| 断网可用 | 不可用（明确不宣称） | 可缓存界面与数据 |
| 数据正确性 | 始终取后端实时数据 | 可能展示过期的政策与工单状态 |
| 实现与调试成本 | 低 | 高（缓存策略、版本失效、脏数据排查） |

**理由**：接诉即办的时效性意味着"过期数据比没有数据更危险"；界面上线壳离线但没有数据，对居民没有实际价值。
**代价与现状**：无离线；依赖浏览器能力（语音等）。
**证据**：`web/public/manifest` 相关配置与图标、`web/index.html`（iOS 全屏 meta）、`docs/mobile-deploy.md`。

## 十二、部署形态：本机回环 + 临时隧道 vs 云 / 容器

**结论**：演示用**本机服务（默认只绑 127.0.0.1）**，需要评委手机访问时临时开 HTTPS 隧道，**用完即关**。
已提供 Dockerfile 与 nginx 部署说明作为生产路径。

| 对比项 | 当前（本机 + 临时隧道） | 云服务器 / Docker |
|---|---|---|
| 成本 | 0 元 | 服务器费用 |
| 数据位置 | 全在本机（数据不出域） | 需自建或租用合规环境 |
| 访问控制 | **无**（拿到链接即可访问）→ 因此限时开放 | 可配 WAF/白名单/证书 |
| 稳定性 | 依赖本机与临时域名 | 正式域名与证书 |

**用真实场景走一遍**：演示当天的开关

```
python scripts/serve_public.py        # 起服务 + 隧道 + 刷新扫码页；默认仅回环，除非加 --lan
python scripts/probe_public.py        # 公网 8 项端到端探测（8/8）
python scripts/serve_public.py --stop  # 演示结束立即关闭公网入口
```

**代价与现状**：无访问控制、临时域名每次变化、依赖本机在线；正式域名/证书/白名单未部署。
**证据**：`scripts/serve_public.py`、`scripts/probe_public.py`、`docs/deploy-https.md`、`Dockerfile`。

## 附：主动"不做"的清单（连同理由）

评委常问"为什么不做 X"。以下为我们**评估后主动放弃**的项，均为取舍而非遗漏：

| 未做项 | 理由 | 何时会做 |
|---|---|---|
| Neo4j 图数据库 | 62 条语料 + 一跳反查场景，独立图库的运维成本换不来收益 | 语料与实体量级提升后 |
| BGE Reranker / 向量数据库 | 当前金标 hit@1 已 100%，且要避免重依赖；语料规模不足以体现二段精排优势 | 语料 > 数千条时 |
| 原生 App / 小程序 | 免安装优先；老年端可用性靠大字大热区与语音保障 | 需要系统级能力（如通讯录、离线）时 |
| service worker 离线 | 过期政策/工单会误导居民 | 若做"只看界面壳 + 明确提示数据过期" |
| 多租户查询隔离 | 演示级仅预留 `tenant_id`，查询层未按租户过滤 | 接入第二个真实社区时 |
| 城市大脑级大屏重设计 | 大屏在手机上直接降级为提示层；投入产出比低 | 有真实街道看板需求时 |
| 对接 12345 / 街道真实系统 | 需数据授权与字段映射，当前仅预留接口层 | 试点立项后 |
| 自由文本 PII 脱敏 | 尚未实现（已知缺口） | 近期：入库前正则脱敏 + 提示 |
