## 一、演示前 5 分钟（必须逐条打勾）

```bash
python scripts/demo_preflight.py     # 9 项自检必须全绿（schema/密钥姿态/加密覆盖/账号/服务身份/前端产物/登录页口径）
python scripts/demo_acceptance.py    # 12 项真实 HTTP 端到端（约 1 分钟，建议演示前跑一次）
```

- [ ] 浏览器已打开 `http://127.0.0.1:8000/login`，**窗口全屏**（F11），缩放 100%
- [ ] 手机演示时才起公网：`python scripts/serve_public.py` → 打开 `.shots/手机访问.html` 扫码页；**演示完 `--stop`**
- [ ] 手机用 **4G/5G**（校园网 DNS 对新隧道域名可能不解析）
- [ ] 万一现场网络/服务出问题 → 直接播 `.recordings/` 里的录屏（浏览器全屏最稳）
- [ ] 动过 `web/src` 就先 `cd web && npm run build`（两个审计脚本有 dist 新鲜度闸，忘了会直接报错）

**演示账号**

### 场景 1 · 居民端：一句话报修（60 秒）

| 操作 | 点「居民」进入 `/resident/home` |
|---|---|

> 🎤 "居民端首页就是四个字：知、报、议、督。最上面是他所在社区——海淀小区的实时脉搏。"

| 操作 | 点右下角对话入口，输入并发送 |
|---|---|

```
3号楼2单元电梯又坏了，停在5楼不动了，家里老人下不来楼
```

| 预期 | 自动分类「设施维修」→ 定级「紧急」→ 生成工单号 → 回复带操作按钮 |
|---|---|

> 🎤 "一句人话，不选分类、不填表单。系统自动分到设施维修、自动判定紧急，因为这户家里有老人下不来楼。
> 这不是关键词匹配，是**接待员智能体把任务派给报修调度智能体**，由它建单。"

| 操作 | 点开回复下方的「🤖 多智能体执行链（N 步）」 |
|---|---|

| 展示 | 每一步：哪个角色、做了什么、Verifier 校验、Arbiter 仲裁、是否协商 |
|---|---|

> 🎤 "这是关键。普通产品到这里就给你一句话；我们给你**这一轮到底发生了什么**——
> 接待员定性、报修调度建单、合规审计过一遍、有冲突就仲裁，每一步都有记录，可以回查。
> 这就是我们说的'可追责'，不是口号，是这一列步骤。"

| 操作 | 进 `/resident/work-orders`，点刚提交的工单 |
|---|---|

> 🎤 "报修单里能看到处理留痕和时间戳。**居民不需要打电话问进度**，这就是'报'的闭环。"

### 场景 2 · 属地化：同一句话，两个社区（60 秒）⭐ 本场最重要

| 操作 | 进 `/resident/qa`，输入 |
|---|---|

```
我们社区高龄老人有什么补贴？
```

| 预期 | 命中《北京市海淀区高龄老人津贴申领实施细则》，标注「适用地区：北京市海淀区」，属地级别 `local_district` |
|---|---|

> 🎤 "注意这里的关键词：**海淀区的细则**。因为这位居民属于海淀小区，系统按他的**社区归属**优先给了区级文件。"

| 操作 | 右上角退出登录 → 输入账号 `demo_resident_cy` / `demo123` → 进 `/resident/qa`，**问同一句话** |
|---|---|

| 预期 | 命中《北京市老年人养老服务补贴津贴管理实施办法》，标注「适用地区：北京市」，属地级别 `local_city` |
|---|---|

> 🎤 "同一个人问同一句话——现在这位居民属于朝阳试点社区，系统**不再给海淀区的文件**，
> 而是给北京市级的办法。因为海淀那份只适用海淀区，拿它回答朝阳居民是错的。"

| 操作 | 指着页面上的「适用地区」标签 |
|---|---|

> 🎤 "这里有三点我想说清楚，也是我们和很多'智慧社区'方案的区别：
> **第一，我们不采定位。** 属地来自账号的网格归属——网格是确定的，不需要也不应该为一个政策排序去采 GPS，老人家里定位既不准也不必要。
> **第二，属地只影响'选谁'，绝不影响'能不能答'。** 打分里相关度决定能不能自动回答，属地只决定在都达标的候选里优先谁。
> 我们有一条专门的测试会**故意制造排序倒挂**，断言系统仍然照常作答——否则就会出现'因为本地政策分低就把能答的变成转人工'。
> **第三，真的没有本地政策时，我们不会硬凑。** 会给市级/全国的依据，并且在正文里明确写它的适用地区，让居民知道这不是本社区口径。"

> 💡 若评委追问技术细节：`pytest tests/test_region_policy.py -q`（14 条属地用例，含两条端到端对比）。

### 场景 5 · 老年关怀端：底线在哪（60 秒）⭐ 人文赋能加分点

| 操作 | 退出 → 点登录页「老年」→ `/elderly/home` |
|---|---|

> 🎤 "现在请评委看一下字号和按钮大小——老年端不是把居民端放大，是**重做**：
> 字号不小于 20 像素、热区不小于 72 像素、层级砍到最少、支持语音播报和一键拨号。"

| 操作 | 点一个预置短语（如「我不舒服」） |
|---|---|

> 🎤 "老人不需要打字。语音说得清就说，说不清就点一下。"

| 操作 | 点 SOS / 联系家属（弹二次确认，说明会留痕） |
|---|---|

> 🎤 "紧急联系是两步：确认、拨打。拨了会留痕，家属和社区都能看到。
> 这里我要主动说两条底线：
> **第一，健康顾问不做诊断。** 诊断句式会被专门规则拦下来，它只给建议和就医引导——这是合规，也是对老人负责。
> **第二，任何答不了的情况都不是冷冰冰的报错**，而是转人工并给居民一个处理编号。"

| 操作 | 进 `/elderly/notices`（听通知） |
|---|---|

> 🎤 "通知支持朗读。老人不用看屏幕也能知道社区这周有什么安排。"

| 操作 | 退出 → `demo_grid` 登录 → `/screen` 治理大屏 |
|---|---|

> 🎤 "最后是全屏治理大屏：工单流转、类别分布、趋势、关怀指标，30 秒自动刷新。"

| 操作 | 回到登录页（或停在任一页面）收尾 |
|---|---|

> 🎤 "总结一下我们的取舍：我们**没有**追求让 AI 全自主办事。
> 涉及安全、费用、政策依据、反复协商的情况，系统一律转人工并留下可追的处理包。
> 我们也不宣称离线能力、不宣称治理成效，因为**没有试点就没有成效**——这些边界都写在交付说明里。
> 我们相信基层治理里 AI 的价值不是替代人，而是**把人的注意力省下来**。
> 这就是我们理解的'人文赋能'：不是把字放大，而是**不越界、不采集、不静默失败**。"

## 四、现场应急

| 情况 | 处理 |
|---|---|
| 服务起不来 / 白屏 | 跑 `python scripts/demo_preflight.py`（会指出具体哪项不合格）；来不及就播录屏 |
| Agent 回复不符合预期 | 刷新重试一次；仍不行就直接讲执行链与留痕（内容次要，机制是重点） |
| 大屏没数据 | 检查是否用网格员身份登录（指标端点按角色锁定） |
| 手机扫码打不开 | 让评委用 4G/5G；或口述 URL + 打开 `.shots/手机访问.html` 展示完整链接 |
| 网络完全不可用 | 全程用本机服务（`http://127.0.0.1:8000`），不依赖公网 |
| 评委要现场验证数字 | `python scripts/demo_acceptance.py`（12 项，约 1 分钟）最稳；数字口径用 `python scripts/check_claims.py` |
