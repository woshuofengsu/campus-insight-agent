## 一、项目概述

### 1.1 项目名称

**校园先知 · CampusInsight Agent**

### 1.2 一句话描述

让每个学生都能"知校园事、报校园修、议校园政、督校园治"的 AI 微治理伙伴。

### 1.3 项目定位

面向高校校园的**基层微治理 AI 参与平台**。

高校是一座几万人的微型社会——有基础设施维护需求、有公共卫生管理需求、有民意收集与反馈需求、有政策制定与监督需求。校园先知以大学校园为可控的治理实验场，验证一套"AI + 公众参与 + 数据透明"的基层治理方法论。

核心理念：把校园视为微型治理沙盒。在这个边界清晰、信息可控的环境中，先让 AI Agent 跑通"感知→参与→表达→监督"全闭环，再向外迁移到社区、街道、养老机构等更大范围的基层治理场景。

不是"帮学生管日程"的个人工具，不是"帮管理者看报表"的管理后台——是一个让学生从"被管理者"变成"治理参与者"的桥梁，也是一个为更广泛的基层治理场景验证 AI 介入模式的实验平台。

## 二、核心创新点

### 2.1 四字架构：知→报→议→督

| 环节 | 板块 | 一句话 | 治理价值 |
|------|------|--------|----------|
| **知** | 🌊 校园脉搏 | 这周发生了什么？下周有什么大事？ | 知情权——不被蒙在鼓里 |
| **报** | 🔧 随手报修 | 发现问题，自然语言描述，AI自动分类上报 | 参与权——我的报修有人管 |
| **议** | 🗳️ 有话说 | 提提案、附议别人、参与AI发起的议题 | 表达权——我的声音被听见 |
| **督** | 📊 治理看板 | 工单进度、提案排行、治理健康度 | 监督权——我看到改变在发生 |

### 2.2 治理工作流引擎

本项目在 LangChain Agent 的基础上增加了预处理和后处理层，用 OODA 的阶段划分来组织这些逻辑——这是区别于普通 Chatbot 的核心差异：

- **Observe（感知）**：巡检天气变化、工单状态、议题热度——不等学生开口，系统先发现问题线索
- **Orient（定位）**：根据用户输入的关键词判断意图——报修？查询？提案？闲聊？——注入对应的角色提示
- **Decide+Act（执行）**：LangChain Agent 自主调用工具——自动分类定级、查重已有提案、检测热点发起议题
- **Reflect（反思）**：安全网检测 LLM 是否跳过了必要的工具调用；追踪工单是否过期、提案是否有进展——**治理要闭环**

### 2.3 降低参与门槛——自然语言即界面

学生不需要学任何操作。用自然语言完成一切：
- "三教二楼男厕所水龙头漏水" → AI自动识别→分类"设施维修"→定级→生成工单
- "我觉得图书馆应该延长到23点" → AI检查是否有相似提案→引导创建或附议已有提案
- "食堂涨价你怎么看" → AI发现这是热点话题→自动发起议题→汇集学生意见

### 2.4 数据驱动信任——治理透明窗

学生能看到：
- 总共上报了多少问题，解决了多少
- 自己上报的问题现在是什么状态
- 自己的提案获得了多少附议
- 校园治理健康度通过三维加权算法实时计算（解决率40% + 平均解决周期35% + 积压趋势25%）

**透明本身就是最好的信任机制。**

## 三、解决的实际痛点

| 痛点 | 严重程度 | 传统做法 | 校园先知的方案 |
|------|----------|----------|---------------|
| 发现问题不知道找谁报修 | 高 | 不知道→算了→没人管→越来越差 | 自然语言描述 → AI自动上报到正确分类 |
| 提了建议石沉大海 | 高 | 投意见箱→没回音→不再提 | 提案+附议→附议达标自动推送→校方回应→学生看到 |
| 不知道校园在发生什么 | 中 | 偶尔看通知栏 | 校园脉搏：每周简报+即将发生 |
| 感觉自己的参与没意义 | 高 | 无反馈→无所谓→不参与 | 治理看板：看到参与数据→感到改变→持续参与 |
| 民意收集靠偶遇 | 中 | 问卷调查→低回收率 | AI自动发现热点→发起议题→对话式参与 |

## 五、Demo 场景

### 场景 1：知 + 报（30 秒）

学生打开应用 → 🌊 校园脉搏显示本周简报 → 发现设施问题 → 自然语言描述 → AI自动分类定级 → 生成工单 → Agent回复："已上报，工单 #043。你的上报让校园更好了一点。"

### 场景 2：议（1.5 分钟）

学生浏览 🗳️ 有话说 → 看到AI自动发起的议题"食堂涨价你怎么看？"→ 表达意见 → 看到别人的提案"图书馆延长闭馆"→ 附议（已有42人附议，校方已回应）→ 自己创建提案"增设快递柜"→ AI检查无重复→创建成功

### 场景 3：督（1 分钟）

感知引擎检测到学生昨天报修的工单状态变为"已解决"→ Agent主动推送反馈卡片 → 学生打开📊治理看板 → 看到本周参与了2次讨论、1次上报 → 治理健康度"良"在读

## 六、竞品对比

| 维度 | 校园App/公众号 | 通用Chatbot | **校园先知** |
|------|--------------|------------|-------------|
| 交互模式 | 填表单 | 一问一答 | **自然语言+主动感知** |

| 数据透明 | 不公开 | 无 | **治理看板实时可见** |

## 七、社会价值

1. **降低参与门槛**：自然语言上报+提案，让不擅长使用正式渠道的居民也能参与治理
2. **建立治理信任**：数据透明的治理看板让居民看到"自己的声音被听见了"
3. **缩短响应链路**：从"发现问题→层层转达→不知道谁处理"到"说话→自动工单→追踪→解决→通知"
4. **量化治理效果**：三维加权健康度评分让治理成效从"感觉变好了"变成"数据说变好了"

## 八、可迁移性：从微型沙盒到真实社会

### 8.1 为什么从校园开始

大学校园是基层治理最理想的原型验证环境：

| 特质 | 校园 | 迁移价值 |
|------|------|----------|
| 规模可控 | 几万人，边界清晰 | 变量可控——先跑通再放大 |
| 问题类型全 | 设施维修、公共卫生、食品安全、政策反馈 | 覆盖基层治理主要场景 |
| 反馈链路短 | 学生→辅导员→后勤，三层以内 | 闭环验证成本低 |
| 数据可获得 | 天气、疾控公报、校内工单 | 感知引擎有真实数据源 |
| 参与意愿强 | 学生天然关心校园环境 | 无需额外的激励机制 |

### 8.2 迁移场景映射

本项目的 OODA 治理引擎与工具层在设计上保持场景无关。以下为三组可行的横向迁移：

| 治理维度 | 校园先知（当前） | → 社区治理 | → 养老机构 | → 企业园区 |
|---------|---------------|-----------|-----------|-----------|
| 知 | 校园脉搏：天气+热点+事件 | 社区周报：天气+投诉热区+社区通知 | 老人日报：天气+健康预警+活动安排 | 园区简报：天气+设施状态+会议通知 |
| 报 | 随手报修：设施/环境/安全 | 居民上报：路灯、噪音、违建 | 一键求助：健康异常、设施故障、生活需求 | 员工反馈：工位设施、食堂、安全 |
| 议 | 有话说：提案+附议+AI议题 | 居民议事：社区提案+居民投票 | 银龄之声：服务建议+活动需求征集 | 员工建言：流程改进+福利建议 |
| 督 | 治理透明窗：KPI+趋势+明细 | 治理公开：响应率+满意度+趋势 | 服务质量监督：响应速度+解决率+家属评价 | 运维看板：工单解决率+满意度 |

### 8.3 迁移成本分析

每一组横向迁移的核心工作**仅涉及**：
- Persona Router 关键词列表替换（~60 个关键词/角色 × 4 角色）
- 工具描述文本与参数名调整（14 个文件，各改 ~50 字）
- 种子数据替换（保留数据规模和叙事结构，换角色和场景名）
- System Prompt 上下文替换（保留 OODA 结构和工具映射表）

**Agent 引擎、数据库 schema、UI 组件、测试体系——零改动。**
