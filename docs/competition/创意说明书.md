## 一、项目概述

### 1.1 项目名称

**校园先知 · CampusInsight Agent**

### 1.2 一句话描述

面向高校校园的基层微治理参与平台，以自然语言为交互界面，覆盖问题上报、提案讨论、数据监督的完整闭环。

### 1.3 项目定位

面向高校校园的**基层微治理参与平台**。

高校是一座几万人的微型社会——有基础设施维护、公共卫生管理、民意收集与反馈、政策制定与监督等完整的治理需求。校园先知以大学校园为可控的实验场地，验证一套"公众参与 + 数据透明"的基层治理方法。

核心理念：把校园视为微型治理沙盒——在边界清晰、信息可控的环境中先跑通"感知→参与→表达→监督"的完整链路，再迁移到社区、街道、养老机构等更大范围的基层治理场景。

不是日程管理工具，不是管理后台——是连接学生与校园治理的通道，也是为更广泛的基层治理场景提供参考的验证系统。

### 1.4 为什么需要这个平台

当前高校校园治理面临三个结构性困境：

**信息断层** —— 学生发现问题（教室灯坏了、食堂卫生差、浴室水温不稳）但不知道找谁。后勤部门有维修能力但不知道哪里出了问题。信息不对称导致小问题拖成大问题。

**反馈真空** —— 学生提了建议（延长图书馆时间、增加自习室插座、改善食堂菜品）之后，没有任何反馈。建议投进了意见箱就像投进了黑洞。几次没有回应之后，学生不再提了。

**信任赤字** —— 学生看不到学校做了什么、花了多少钱、解决了多少问题。数据不公开，过程不透明。当参与无法被感知，参与本身就失去了意义。

这三个问题不是某个学校的特例——在几万人的校园、几千人的社区、几百人的养老机构里都会反复出现。校园先知试图用一套"感知→参与→表达→监督"的轻量级治理框架来解决这个结构性问题。

### 1.5 目标用户

| 角色 | 身份 | 核心诉求 | 使用场景 |
|------|------|----------|----------|
| **学生** | 本科/研究生，20-25岁 | 快速报修、表达意见、看到反馈 | 发现教室灯坏了→随手报修→2天后收到"已修好"通知 |
| **教师/行政** | 辅导员、后勤、校领导 | 掌控全局、分配任务、量化考核 | 早上打开工作台→看到3条紧急工单→一键派单→下午查看解决率 |

双角色共用一个系统，看到的是同一份数据——这本身就是透明机制。

## 二、核心设计

### 2.1 四字架构：知→报→议→督

| 环节 | 板块 | 含义 | 治理价值 |
|------|------|------|----------|
| **知** | 校园脉搏 | 本周热点、校园事件、天气 | 知情权——了解身边正在发生什么 |
| **报** | 随手报修 | 自然语言描述问题，自动分类上报 | 参与权——反映的问题有记录有追踪 |
| **议** | 有话说 | 提交提案、附议他人、参与议题讨论 | 表达权——声音被听见、诉求被响应 |
| **督** | 治理看板 | 工单进度、提案排行、治理健康度 | 监督权——看到改变发生、参与有意义 |

### 2.2 工作流设计

本项目在 LangChain Agent 的基础上增加了预处理层和后处理层，参照 OODA（Observe-Orient-Decide-Act，观察-判断-决策-行动）循环的阶段划分来组织这些逻辑。核心思路是：让 LLM 专注于它擅长的自然语言理解和生成，而环境感知、意图判断、质量检查、统计推理这些环节由确定性代码完成。

五个阶段：

- **Observe（感知）**：查询天气、统计工单热点、采集时间上下文——在用户开口之前完成环境数据收集
- **Orient（定位）**：通过关键词匹配判断用户意图——报修、查询、提案还是闲聊——据此选择对应角色
- **Decide+Act（决策与执行）**：LangChain Agent 调用治理工具——自动分类定级、查重提案、发起议题
- **Reflect（反思）**：检查 LLM 的回复质量——是否跳过了必要的工具调用、是否编造了不存在的工单号。如有问题则纠正

### 2.3 降低参与门槛——自然语言即界面

用户不需要学习操作，用自然语言即可完成全部交互：
- "三教二楼男厕所水龙头漏水" → 自动识别为设施维修 → 定级 → 生成工单
- "我觉得图书馆应该延长到 23 点" → 检查是否有相似提案 → 引导附议或创建
- "食堂涨价你怎么看" → 检测为热点话题 → 发起议题 → 收集意见

### 2.4 数据透明建立信任——治理透明窗

学生端可直接查看：
- 全校累计上报数量与解决数量
- 自己上报问题的当前状态和处理进展
- 自己提交提案的附议人数和采纳状态
- 治理健康度评分（三维加权：解决率 40% + 速度分数 35% + 积压趋势 25%）

数据透明本身就是信任机制。

### 2.5 Agent 智能体核心特性

与普通聊天机器人不同，校园先知是一个具备自主决策能力的 AI Agent。以下是体现 Agent 特性的四个核心设计：

**环境感知（Context Awareness）**：Agent 在每次对话前主动采集环境数据——天气状况、校园热点事件、工单统计快照、当前时间上下文。这些数据不是用户要求的，而是 Agent 自主判断"这些信息对本次对话有帮助"而提前准备的。例如学生问"最近流感严重吗"，Agent 已经预先拉取了疾控数据和校园脉搏快照，无需再逐项查询。

**工具调用与编排（Tool Orchestration）**：Agent 不是"一问一答"的问答机，而是根据用户意图自主决定调用哪些工具、以什么顺序调用。遇到报修请求时，Agent 自主编排 4 步调用链——分类识别（report_issue）→ 查重检查（query_issues）→ 工单创建（report_issue 写入）→ 统计更新（get_governance_stats）。每一步都是 Agent 的自主决策，而非预设的 if-else 分支。

**自省与纠错（Self-Reflection）**：Agent 在回复用户之前，会通过反射器（Reflector）自检输出质量——是否跳过了必要的工具调用？是否在文本中编造了不存在的工单号？工具调用链是否完整？发现问题后自动补充或纠正。这套机制确保了 LLM 的不可靠性被控制在可接受范围内。

**离线韧性（Offline Resilience）**：当 LLM API 不可用时，Agent 自动切换到离线模式——基于规则引擎 + 关键词匹配 + 数据库直查的降级方案。学生仍然可以查工单状态、看校园脉搏、提交报修请求（走关键词分类），整个系统不会因为 LLM 不可用而中断服务。

## 三、解决的实际问题

| 问题 | 严重程度 | 当前做法 | 本项目方案 |
|------|----------|----------|-----------|
| 发现问题不知道找谁 | 高 | 不知→算了→没人管→越来越差 | 自然语言描述 → 自动分类上报 |

| 民意收集靠偶然 | 中 | 问卷调查→回收率低 | 系统发现热点→发起议题→对话式收集 |

## 五、演示场景

### 场景 1：知 + 报（40 秒）

打开应用 → 校园脉搏页面展示本周简报（天气、热点类别、校园事件）→ 对话页输入问题描述 → 系统自动分类定级、生成工单、返回工单号 → 展开处理流程面板查看各阶段执行记录。

### 场景 2：议（60 秒）

有话说页面查看提案列表（按附议数排序，含已采纳/已回应提案）→ 对已有提案一键附议 → 创建新提案时系统自动语义查重，提示相似提案 → 系统根据热点自动发起议题，学生在对话中发表意见。

### 场景 3：督（50 秒）

治理透明窗查看三维加权健康度评分及 7 天趋势图 → 治理大屏全屏实时仪表盘 → 工单状态变更时主动推送通知 → 学生看到自己的参与被记录和反馈。

### 场景 4：教师端管理闭环（60 秒）

教师角色切换到工作台 → KPI 总览（待处理工单、今日新增、紧急数、健康度）→ 工单管理页筛选"紧急+待处理"→ 一键修改工单状态为"处理中"→ 提案管理页查看热门提案并回复"已提交后勤评估"→ 数据洞察页查看本周趋势与类别分布 → 感知到治理运转的完整链路。

## 七、创新点总结

### 7.1 将 OODA 循环引入校园治理 Agent

本项目将军事/应急管理领域的 OODA（Observe-Orient-Decide-Act-Reflect）循环适配为 AI Agent 的工作流框架。这不是对理论框架的生搬硬套——OODA 的阶段划分恰好将预处理和后处理逻辑组织到了清晰的工程边界里。Observe 和 Orient 在用户开口之前完成环境感知和意图路由，Decide+Act 由 LangChain Agent 执行工具编排，Reflect 在回复完成后做质量检查和关联分析。每个阶段的输入/输出都是可观测、可调试、可测试的。

### 7.2 "预处理 + Agent + 后处理"三层架构

单层 LLM Agent 面临的典型问题——幻觉、遗漏工具调用、缺乏上下文感知——被分发到三个独立的处理层中解决。预处理层负责环境数据采集和意图路由（确定性代码，零 LLM 消耗），核心 Agent 层负责自然语言理解和工具编排（LLM 擅长的事），后处理层负责质量校验和统计洞察生成（确定性 SQL + 独立 LLM）。三层解耦意味着任何一层的失败都不会导致整个系统崩溃。

### 7.3 确定性代码与 LLM 的分工边界

大部分 AI 项目将 LLM 用于所有环节——包括它不擅长的统计推理和数据查询。本项目的设计原则是：LLM 只负责自然语言理解和生成，环境感知、意图判断、质量检查、统计关联分析全部由确定性代码完成。这种边界划分让系统行为可预测：同样的输入产生同样的分类结果，同样的工单数据产生同样的健康度评分。

### 7.4 场景无关的治理工作流

治理工作流（知→报→议→督）、工具层架构（16 个插件式工具）、数据库结构（15 张表）、校验机制（enforce + closed_loop）、降级链路（重试→规则引擎→DB 直查）全部保持场景无关。场景迁移只需替换 4 个配置——关键词列表、工具描述文本、种子数据、System Prompt。从校园治理到社区治理的横向迁移预计 6-8 小时，不需要改动核心代码。

### 7.5 实时感知 + 主动推送

不同于被动等待用户输入的传统设计，本系统在每次用户访问时自动执行感知巡检——对比本周与上周工单趋势、检测分类/地点异常激增、统计 SLA 超期积压、采集舆情情绪分布。感知结果既用于对话上下文注入（让 Agent"知道"最近校园发生了什么），也用于教师端工作台的实时告警。

## 八、社会价值

1. **降低参与门槛**：自然语言交互，不需要学习操作流程或记住入口位置
2. **建立治理信任**：数据透明的治理看板让参与者看到处理进展和结果
3. **缩短响应链路**：从"发现问题→层层转达→不知道谁处理"变成"描述→自动工单→追踪→解决→通知"
4. **效果可量化**：三维加权健康度评分让治理成效从主观感受变成客观数据

## 九、可迁移性

### 9.1 为什么从校园开始

大学校园是基层治理方法的理想原型验证环境：

| 特质 | 校园 | 对验证的价值 |
|------|------|-------------|
| 规模可控 | 几万人，物理边界清晰 | 变量可控，先跑通小闭环再放大 |
| 问题类型全 | 设施维修、公共卫生、食品安全、政策反馈 | 覆盖基层治理主要场景 |
| 反馈链路短 | 学生→辅导员→后勤，三层以内 | 闭环验证成本低，迭代快 |
| 数据可获得 | 天气 API、疾控月度公报、校内工单历史 | 感知层有真实数据源 |
| 参与意愿强 | 学生天然关心校园环境 | 无需额外的激励设计 |

### 9.2 迁移场景映射

本项目的治理工作流与工具层在设计上保持场景无关。以下是三组可行的横向迁移：

| 治理维度 | 校园（当前） | → 社区治理 | → 养老机构 | → 企业园区 |
|---------|------------|-----------|-----------|-----------|
| 知 | 校园脉搏 | 社区周报 | 老人日报 | 园区简报 |
| 报 | 随手报修 | 居民上报 | 一键求助 | 员工反馈 |
| 议 | 有话说 | 居民议事 | 银龄之声 | 员工建言 |
| 督 | 治理透明窗 | 治理公开 | 服务监督 | 运维看板 |
| 角色 | 学生 / 教师 | 居民 / 网格员 | 老人 / 护工 | 员工 / 行政 |

### 9.3 迁移成本

每组横向迁移涉及的工作：
- Persona Router 关键词列表替换（4 组共 368 个关键词）
- 工具描述文本与参数名调整（11 个工具文件，16 个工具）
- 种子数据替换（保留数据规模和叙事结构，换角色和场景名）
- System Prompt 上下文替换（保留工作流结构和工具映射表）

**治理工作流、数据库结构、UI 组件、测试体系——不需要改动。** 单组迁移预计 6-8 小时。
