二、完整版（5 分 30 秒）

场景 0 · 开场（20 秒）

操作停在登录页，不点任何按钮
🎤 "社区先知，一套面向基层治理的多智能体平台，服务三类人：居民、网格员、老年人。
左边是居民端入口，中间是网格员端，右边是老年关怀端——三个端不是三套界面，是三种服务关系。
今天我用五分钟演示一条完整的治理闭环，以及我们和普通对话机器人最不一样的两件事：
多智能体是真的在协商，以及对老人和隐私是真的有底线。"
操作滑到登录页底部的口径说明
🎤 "顺带一提，页面上这些数字——632 项可运行用例、130 条接口、9 个智能体角色——不是写死在文档里的，
是页面启动时从代码库读的，跑一个脚本就能复算。我们不喜欢用形容词描述质量。"

场景 1 · 居民端：一句话报修（60 秒）

操作点「居民」进入 /resident/home
🎤 "居民端首页就是四个字：知、报、议、督。最上面是他所在社区——海淀小区的实时脉搏。"
操作点右下角对话入口，输入并发送 
3号楼2单元电梯又坏了，停在5楼不动了，家里老人下不来楼
预期自动分类「设施维修」→ 定级「紧急」→ 生成工单号 → 回复带操作按钮
🎤 "一句人话，不选分类、不填表单。系统自动分到设施维修、自动判定紧急，因为这户家里有老人下不来楼。
这不是关键词匹配，是接待员智能体把任务派给报修调度智能体，由它建单。"
操作点开回复下方的「🤖 多智能体执行链（N 步）」
展示每一步：哪个角色、做了什么、Verifier 校验、Arbiter 仲裁、是否协商
🎤 "这是关键。普通产品到这里就给你一句话；我们给你这一轮到底发生了什么——
接待员定性、报修调度建单、合规审计过一遍、有冲突就仲裁，每一步都有记录，可以回查。
这就是我们说的'可追责'，不是口号，是这一列步骤。"
操作进 /resident/work-orders，点刚提交的工单
🎤 "报修单里能看到处理留痕和时间戳。居民不需要打电话问进度，这就是'报'的闭环。"

场景 2 · 属地化：同一句话，两个社区（60 秒）⭐ 本场最重要

操作进 /resident/qa，输入 
我们社区高龄老人有什么补贴？
预期命中《北京市海淀区高龄老人津贴申领实施细则》，标注「适用地区：北京市海淀区」，属地级别 local_district
🎤 "注意这里的关键词：海淀区的细则。因为这位居民属于海淀小区，系统按他的社区归属优先给了区级文件。"
操作右上角退出登录 → 输入账号 demo_resident_cy / demo123 → 进 /resident/qa，问同一句话
预期命中《北京市老年人养老服务补贴津贴管理实施办法》，标注「适用地区：北京市」，属地级别 local_city
🎤 "同一个人问同一句话——现在这位居民属于朝阳试点社区，系统不再给海淀区的文件，
而是给北京市级的办法。因为海淀那份只适用海淀区，拿它回答朝阳居民是错的。"
操作指着页面上的「适用地区」标签
🎤 "这里有三点我想说清楚，也是我们和很多'智慧社区'方案的区别：
第一，我们不采定位。 属地来自账号的网格归属——网格是确定的，不需要也不应该为一个政策排序去采 GPS，老人家里定位既不准也不必要。
第二，属地只影响'选谁'，绝不影响'能不能答'。 打分里相关度决定能不能自动回答，属地只决定在都达标的候选里优先谁。
我们有一条专门的测试会故意制造排序倒挂，断言系统仍然照常作答——否则就会出现'因为本地政策分低就把能答的变成转人工'。
第三，真的没有本地政策时，我们不会硬凑。 会给市级/全国的依据，并且在正文里明确写它的适用地区，让居民知道这不是本社区口径。"
💡 若评委追问技术细节：pytest tests/test_region_policy.py -q（14 条属地用例，含两条端到端对比）。

场景 3 · 议事与提案（45 秒）

操作回居民端 /resident/proposals
🎤 "20 条提案按附议数排序——加装电梯 89 人、增设停车位 73 人，状态都是已采纳。
居民用附议表达诉求，社区用行动回应，不是空谈。"
操作点开任一提案详情 → 看「处理留痕」
🎤 "每个提案都有处理留痕：谁在什么时候回复、采纳、实施。公开留痕本身就是信任。"

场景 4 · 网格员端：管理与留痕（60 秒）

操作退出 → 用 demo_grid / demo123 登录 → /grid/dashboard
🎤 "换成网格员视角。工作台是治理侧的仪表盘：待处理、紧急、SLA 超期、健康度，还有 LLM 用量费用卡——
花了多少钱是逐笔记账的，不是估的。"
操作进 /grid/work-orders，把刚才居民报修的工单从「待处理」改成「处理中」→「已解决」
🎤 "网格员处理工单，状态变更会推给居民端。刚才居民报的电梯故障，现在已解决。"
操作回到网格端工作台，点开「Agent 日志 / 留痕」，筛「仲裁」
展示353 条 agent_logs 中的仲裁记录：规则名、决策、时间
🎤 "这就是我们的双层防线：Verifier 负责事实与安全（幻觉、隐私、医疗诊断句式），
Arbiter 负责冲突裁决——按合规优先 → 安全 → 专业 → 费用/不可逆需人工 → 数据版本的顺序，
第一条命中的规则生效，并且每次裁决都落库。所以智能体之间不一致时，不是'谁声音大听谁的'，是有规则、有记录。"
操作进 /grid/qa，展示知识库管理页的「适用地区」列
🎤 "知识库 62 条，55 条是可溯源的公开政策摘要，每条都标了适用地区。政策问答不是让模型背条文，是检索到材料再作答。"

场景 5 · 老年关怀端：底线在哪（60 秒）⭐ 人文赋能加分点

操作退出 → 点登录页「老年」→ /elderly/home
🎤 "现在请评委看一下字号和按钮大小——老年端不是把居民端放大，是重做：
字号不小于 20 像素、热区不小于 72 像素、层级砍到最少、支持语音播报和一键拨号。"
操作点一个预置短语（如「我不舒服」）
🎤 "老人不需要打字。语音说得清就说，说不清就点一下。"
操作点 SOS / 联系家属（弹二次确认，说明会留痕）
🎤 "紧急联系是两步：确认、拨打。拨了会留痕，家属和社区都能看到。
这里我要主动说两条底线：
第一，健康顾问不做诊断。 诊断句式会被专门规则拦下来，它只给建议和就医引导——这是合规，也是对老人负责。
第二，任何答不了的情况都不是冷冰冰的报错，而是转人工并给居民一个处理编号。"
操作进 /elderly/notices（听通知）
🎤 "通知支持朗读。老人不用看屏幕也能知道社区这周有什么安排。"

场景 6 · 治理大屏与收尾（45 秒）

操作退出 → demo_grid 登录 → /screen 治理大屏
🎤 "最后是全屏治理大屏：工单流转、类别分布、趋势、关怀指标，30 秒自动刷新。"
操作回到登录页（或停在任一页面）收尾
🎤 "总结一下我们的取舍：我们没有追求让 AI 全自主办事。
涉及安全、费用、政策依据、反复协商的情况，系统一律转人工并留下可追的处理包。
我们也不宣称离线能力、不宣称治理成效，因为没有试点就没有成效——这些边界都写在交付说明里。
我们相信基层治理里 AI 的价值不是替代人，而是把人的注意力省下来。
这就是我们理解的'人文赋能'：不是把字放大，而是不越界、不采集、不静默失败。"

四、现场应急

情况处理
服务起不来 / 白屏跑 python scripts/demo_preflight.py（会指出具体哪项不合格）；来不及就播录屏
Agent 回复不符合预期刷新重试一次；仍不行就直接讲执行链与留痕（内容次要，机制是重点）
大屏没数据检查是否用网格员身份登录（指标端点按角色锁定）
手机扫码打不开让评委用 4G/5G；或口述 URL + 打开 .shots/手机访问.html 展示完整链接
网络完全不可用全程用本机服务（http://127.0.0.1:8000），不依赖公网
评委要现场验证数字python scripts/demo_acceptance.py（12 项，约 1 分钟）最稳；数字口径用 python scripts/check_claims.py
