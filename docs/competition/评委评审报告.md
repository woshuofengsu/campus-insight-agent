## 一、结构创新度（35 分）—— 自查 31

**评委能看到的事实**

- **9 个声明式角色 + 黑板消息队列**：`receptionist` / `repair_dispatch` / `proposal_collab` / `policy_expert` /
  `health_advisor` / `weather_guardian` / `notification_manager` / `grid_assistant` / `compliance_auditor`；
  角色间五类消息（task_request / task_response / notify / error / handoff）真往返。
- **一次输入内的跨角色链式协商**：如"极端天气 → 健康顾问 → 通知管理员"，**执行链会被智能体自己改变**；
  有循环防护（单目标 ≥2 轮强制转人工）。
- **双层防线**：Verifier（幻觉 / 隐私 / 医疗诊断句式 / 政策引用下标）→ Arbiter（合规优先 → 安全 → 专业 →
  费用或不可逆需人工 → 数据版本），**每次裁决落库**（`agent_logs` 可筛"仲裁"）。
- **属地化（一区一策）**：政策按行政区划"本地优先、全国兜底"，**属地只改排序、不改能否自动回答**，**不采定位**。
- **质量做成可复算的数字**：625 项可运行用例、12 项真实 HTTP 端到端、54 个页面视口客观审计、
  检索金标 48 条 hit@1 100%、故障注入 8/8 拦下。

**加分点**：把"多智能体"从营销词变成**可投屏的执行链**（前端「🤖 多智能体执行链（N 步）」逐条列出角色与检查），
这是大多数作品拿不出来的东西。

**扣分风险（诚实）**

1. **编排框架仍是"编排器给出入口 + 角色按消息决定后续"**，不是完全去中心化的自主协商；措辞必须准确，不能说"全自主"。
2. 协商的**深度**受演示数据限制（链式往返 2–3 跳），没有更大规模的角色生态。
3. 属地化的行政区划链只做到街道/区/市/省四层，没做跨区政策冲突的复杂场景。

**证据**：`agent/orchestrator.py`（`_drain_negotiations` 链式协商 + 循环防护）、`agent/arbiter.py`（5 条规则）、
`pytest tests/test_dispatch.py -q`、投屏 `agent_logs`。

## 二、人机协同力（25 分）—— 自查 22

**评委能看到的事实**

- **规则为骨、LLM 为脑**：状态机 / 权限 / 脱敏 / 风控 / 阈值全是确定性代码；LLM 只做模糊意图、政策生成、
  跨角色协商——**四个开关可一键关回纯规则**（现场可对比两种姿态）。
- **人在环是默认姿态**：合规不通过、Verifier 高风险、协商超轮次、政策无达标材料、仲裁兜底 →
  **五类情形一律转人工并生成处理包（`handoff_id`）**，不是弹个"请联系工作人员"。
- **网格端闭环**：SLA 工单、提案办理、知识发布、"适用地区"维护、Agent 留痕查询、治理大屏。
- **老年端独立设计**：≥20px 字号、≥72px 热区、预置短语、语音播报、一键拨号/SOS，且**不依赖语音也有保底路径**。
- **成本可计量**：`llm_usage` 逐笔记账，**单次均价 ¥0.0002**（2026-09-14 快照：57 次调用合计 ¥0.0139），单轮 +¥0.0002 / +0.9s。

**加分点**：**从头到尾不出现"AI 决定一切"**——每一处 AI 的地方都写明"人怎么接手"。

**扣分风险**

1. 转人工的**处理侧界面**还是"待办 + 处理包"，没有坐席工作台（真人接手的效率工具）。
2. **没有真实网格员/居民用户测试**（已列为已知边界），协同力只有机制论证、没有实测数据。
3. 语音能力依赖浏览器，非 Chromium 真机未验证。

**证据**：`python scripts/demo_preflight.py`（姿态行）、`agent/llm_client.py` + `llm_usage` 表、
`/grid/work-orders` 现场流转、老年端现场演示。

## 三、问题精准度（20 分）—— 自查 17

**评委能看到的事实**

- **问题定义具体**：老小区里"同一件事在三方之间反复翻译"——居民说人话、系统要结构化、政策是条文、
  老人不会打字。系统做的是**翻译 + 责任链**。
- **场景取舍克制**：只做四项（报修 / 通知 / 政策问答 / 适老 SOS），不承诺"城市大脑"。
- **一区一策真实可演**：海淀小区 → 区级细则；朝阳试点社区 → 市级办法（现场切账号即可复现）；
  **跨区兜底会标注"该依据的适用地区是…"**。
- **边界写进材料**：12 条已知边界（无试点、无真机、单进程、多租户未隔离、自由文本 PII 未治理…）。

**扣分风险**

1. **没有真实痛点数据**（如某社区工单量的真实分布），问题定义主要靠公开资料与常理推断。
2. 舆情、12345 对接、多社区隔离只有框架，没有落地。
3. 政策语料 55 条，规模偏小；覆盖养老/医疗/住房等高频类目。

**证据**：`docs/competition/创意说明书-提交版.md`（问题定义 + 边界）、
`python scripts/demo_acceptance.py`（第 12 项属地对比）、`docs/spec/地区识别落地方案.md`。

## 四、应用可行性（15 分）—— 自查 12

**评委能看到的事实**

- **可复算的工程闭环**：schema v46 + 46 个版本化迁移（禁止运行时裸 ALTER）、8 张表手机号 AES-256-GCM 加密
  （明文 0）、生产姿态密钥 **fail-closed**、审计留痕。
- **一套命令跑起来**：`python -m uvicorn api_web:app` → 自动迁移建库灌种子；`serve_public.py` 让评委手机扫码。
- **成本极低**：规则优先 + 四个开关，边际成本可忽略（**单次均价 ¥0.0002**（2026-09-14 快照：57 次调用合计 ¥0.0139））。
- **可迁移**：场景耦合只在角色声明 / 工具集 / 语料 / 属地映射 / 页面文案五处，核心引擎不动。
- **落地路径写清三步**：单社区试点四项 → 生产化（Redis/PG/域名/对接）→ 多社区多租户。

**扣分风险**

1. **单进程 + SQLite**：真实街道规模（数千户）需要 Redis + PostgreSQL，扩容清单已写但未实施。
2. **未接真实系统**（12345 / 物业 / 街道工单），导入适配器是框架。
3. **等保三级、PIPL 同意书、共享台账、KMS** 均为规划项（在 `合规路线-一页.md` 如实标注）。
4. **没有试点单位**：意向阶段，零真实用户。

**证据**：`docs/scaling.md`、`docs/competition/合规路线-一页.md`、`docs/competition/落地路径-一页.md`、
`python scripts/audit_phone_encryption.py`。

## 六、合计与判断

| 维度 | 权重 | 自查 | 主要扣分原因 |
|---|---:|---:|---|
| 结构创新度 | 35 | **31** | 协商深度有限；措辞不能夸大 |
| 人机协同力 | 25 | **22** | 无坐席工作台；无真实用户测试 |
| 问题精准度 | 20 | **17** | 缺真实痛点数据；语料规模小 |
| 应用可行性 | 15 | **12** | 单进程/SQLite；未接真实系统；合规项多为规划 |
| 展示表现力 | 5 | **4** | 现场依赖网络；无真实成效 |
| **合计** | **100** | **86** | |

**一句话结论**：**机制与工程是强项（可复算、可追责、有边界），成效与规模是弱项（无试点、无真机、单进程）。**
答辩策略应当是**主动暴露弱项、把强项演到极致**——评委对"知道自己边界在哪"的团队容忍度，
远高于对"什么都行"的团队。
