📍 当前阶段

本项目为 Demo 版本，以预置种子数据（38 条工单、19 条提案、14 条百科条目）运行完整治理闭环。下一步计划：与学校后勤部门合作，接入真实工单系统，从验证阶段进入实际校园运营。

一、一句话看懂

校园先知是一个"会自己干活"的 AI Agent——它会主动感知校园环境、自主决定调用 16 个治理工具、并且在每次回复后自我校验、发现自己"说错话"就自动纠正。校园治理是它验证"公众参与 + 数据透明"治理方法的第一个应用场景。

它不是聊天机器人，也不是填表单的管理后台。它的核心价值不在"能对话"，而在对话背后每一次真实的环境感知、工具调用、写库操作和自纠错。

二、它是什么：一个真正的 Agent

2.1 与聊天机器人的本质区别

聊天机器人是"你问一句、它答一句"，答案只来自模型内部知识，说错了也不知道。Agent 不同——它会自己决定"要不要查天气、要不要查工单、要不要创建提案"，然后真的去调用工具、真的写数据库、真的给你一个可以追踪的工单号。下面五个设计，是"真 Agent"和"套皮聊天"的分界线。

2.2 自主感知环境

Agent 在每次对话前主动采集环境数据——天气状况、校园热点事件、工单统计快照、健康风险（基于国家疾控局月度公报的季节模型）、当前时间上下文。这些数据不是用户要的，是 Agent 自主判断"这些信息对本次对话有帮助"而提前准备的。例如学生问"最近流感严重吗"，Agent 在感知阶段已经预先跑完了流感季节风险检查，无需逐项查询。

2.3 自主决策与工具编排

Agent 不是"一问一答"，而是根据意图自主决定调用哪些工具、以什么顺序调用。遇到报修请求时，它自主编排调用链——分类识别与工单创建（report_issue）→ 历史查重（query_issues）→ 统计更新（get_governance_stats）。每一步是 Agent 的自主决策，而非预设的 if-else 分支。工具层有 16 个治理工具，通过 pkgutil 自动发现，新增工具只需放入目录即可被识别。

2.4 自省与纠错

坦白讲：不是我不想做一个"完全自主"的 Agent，而是我最初做的纯自主 Agent，老是生成假工单。

一开始，我们把意图识别、工具选择全部交给 LLM 自主决策，系统直接跑 LangChain AgentExecutor。很快发现一个致命问题：LLM 会在没有调用任何工具的情况下，直接回复"已为你生成工单 #42"——数据库里什么都没有，但用户以为问题已经上报了。

这不是偶发 bug，是 LLM 的固有倾向：顺着用户的期待生成看似合理的答案，即使答案背后没有任何真实操作。如果放任不管，Agent 的每一次"我做了"都不可信。

于是我们把 LLM 最不可靠的两个环节，用确定性代码接了过来：

① 事前拦截——368 个关键词的意图路由：不再让 LLM 判断"用户到底想干什么"，改用确定性的关键词匹配识别意图——报修、查询、提案还是闲聊——据此选择对应角色（4 角色、368 关键词）。同样的输入，永远得到同样的分类。

② 事后兜底——enforce 校验：每轮回复后自动检查——如果用户意图是报修、但工具调用记录里没有 report_issue，就强制补调一次真实工具，用真实结果替换掉 LLM 编造的回复。配合反射器的 10 维 SQL 关联分析和 z-score 异常检测，把 LLM 的不可靠性控制在可接受范围内。

这不是事后补救，而是一条设计原则：真正的 Agent，不是"放任 LLM 自由发挥"，而是清楚地知道它哪里可靠、哪里不可靠，把不能出错的环节交给不会说谎的代码。大多数 Agent 会"假装"调了工具，这个不会。

需要说明的是，这套校验机制当前仍是 Demo 版本的基础实现——后续接入真实工单系统后会持续改进、进一步打磨，把"假工单"这类问题解决得更彻底。

2.5 关联分析

每次对话后，Agent 解析整条工具调用链，执行 10 维 SQL 关联分析——空间关联、时间趋势、复发检测、z-score 异常、类别关联、报→议升级路径等——再调用独立 LLM 生成 2-3 句治理洞察，附加在回复之后。这让 Agent 不只回答"你的工单已创建"，还能告诉你"最近 7 天三教区域的设施问题激增了 3 倍"。

2.6 离线韧性

当 LLM API 不可用时，Agent 自动切换到三层降级——先指数退避重试，再切到规则引擎（无 LLM 依赖，直接 SQL 查询 + 关键词分类），最后降级到数据库直查。学生仍能查工单状态、看校园脉搏、提交报修请求，系统不会因 LLM 不可用而中断服务。

三、它解决什么问题

3.1 三个结构性困境

当前高校校园治理面临三个困境：

信息断层 —— 学生发现问题（教室灯坏了、食堂卫生差、浴室水温不稳）但不知道找谁。后勤部门有维修能力但不知道哪里出了问题。信息不对称导致小问题拖成大问题。

反馈真空 —— 学生提了建议（延长图书馆时间、增加自习室插座、改善食堂菜品）之后没有任何反馈。建议投进意见箱就像投进黑洞。几次没有回应之后，学生不再提了。

信任赤字 —— 学生看不到学校做了什么、花了多少钱、解决了多少问题。数据不公开，过程不透明。当参与无法被感知，参与本身就失去了意义。

这三个问题不是某个学校的特例——在几万人的校园、几千人的社区、几百人的养老机构里都会反复出现。

3.2 目标用户

角色身份核心诉求使用场景
学生本科/研究生，20-25岁快速报修、表达意见、看到反馈发现教室灯坏了→随手报修→2天后收到"已修好"通知
教师/行政辅导员、后勤、校领导掌控全局、分配任务、量化考核早上打开工作台→看到3条紧急工单→派单→下午查看解决率

双角色共用一个系统，看到的是同一份数据——这本身就是透明机制。

3.3 治理闭环：知→报→议→督

环节板块含义治理价值
知校园脉搏本周热点、校园事件、天气知情权——了解身边正在发生什么
报随手报修自然语言描述问题，自动分类上报参与权——反映的问题有记录有追踪
议有话说提交提案、附议他人、参与议题讨论表达权——声音被听见、诉求被响应
督治理看板工单进度、提案排行、治理健康度监督权——看到改变发生、参与有意义

用户不需要学习操作，用自然语言即可完成全部交互：

  • "三教二楼男厕所水龙头漏水" → 自动识别为设施维修 → 定级 → 生成工单
  • "我觉得图书馆应该延长到 23 点" → 检查是否有相似提案 → 引导附议或创建
  • "食堂涨价你怎么看" → 检测为热点话题 → 发起议题 → 收集意见

四、怎么实现：OODA 五阶段

本项目在 LangChain Agent 的基础上增加了预处理层和后处理层。OODA 在这里是一个工程组织原则——用它的阶段划分把预处理和后处理逻辑装进清晰的边界。核心分工：LLM 负责自然语言理解和生成，环境感知、意图判断、质量检查、统计推理由确定性代码完成。

  • Observe（感知）：查询天气、统计工单热点、采集时间上下文——在用户开口之前完成环境数据收集
  • Orient（定位）：关键词匹配判断用户意图——报修、查询、提案还是闲聊——据此选择对应角色（4 角色 368 关键词）
  • Decide+Act（决策与执行）：LangChain Agent 调用治理工具——自动分类定级、查重提案、发起议题
  • Reflect（反思）：检查 LLM 回复质量——是否跳过必要的工具调用、是否编造了不存在的工单号，如有问题则纠正
  • Associate（关联）：解析工具调用链，执行 10 维 SQL 关联分析，生成治理洞察

五、演示场景

场景 1：知 + 报（40 秒）

打开应用 → 校园脉搏页面展示本周简报（天气、热点类别、校园事件）→ 对话页输入问题描述 → 系统自动分类定级、生成工单、返回工单号 → 展开处理流程面板查看各阶段执行记录。

场景 2：议（60 秒）

有话说页面查看提案列表（按附议数排序，含已采纳/已回应提案）→ 对已有提案附议 → 创建新提案时系统自动查重，提示相似提案 → 系统根据热点自动发起议题，学生在对话中发表意见。

场景 3：督（50 秒）

治理透明窗查看三维加权健康度评分及 7 天趋势图 → 治理大屏全屏实时仪表盘 → 工单状态变更时主动推送通知 → 学生看到自己的参与被记录和反馈。

场景 4：教师端管理闭环（60 秒）

教师角色切换到工作台 → KPI 总览（待处理工单、今日新增、紧急数、健康度）→ 工单管理页筛选"紧急+待处理"→ 修改工单状态为"处理中"→ 提案管理页查看热门提案并回复"已提交后勤评估"→ 数据洞察页查看本周趋势与类别分布 → 感知到治理运转的完整链路。

六、创新点总结

6.1 防幻觉安全网

LLM 最常见的失败不是答错，而是"假装调了工具"——嘴上说"已生成工单 #42"，实际什么都没做。本项目在回复后自动校验工具调用记录，发现报修意图却没真正调用 report_issue 时，强制补调真实工具、替换掉编造的回复。这让 Agent 的每一次"我做了"都有数据库里的真实记录做背书。

6.2 反射器关联分析

大多数 Agent 止步于"回答完就结束"。本项目在回复后追加一层 10 维 SQL 关联分析（z-score 异常检测、跨时间对比、报→议升级路径），让 Agent 不只能回答问题，还能发现"最近某区域某类问题激增"这样的治理洞察。

6.3 确定性代码与 LLM 的分工边界

大部分 AI 项目把 LLM 用于所有环节，包括它不擅长的统计推理和数据查询。本项目明确划分：LLM 只负责自然语言理解和生成，环境感知、意图判断、质量检查、统计关联分析全部由确定性代码完成。这让系统行为可预测——同样的输入产生同样的分类结果。

6.4 场景无关的治理工作流

治理工作流、工具层架构、数据库结构、校验机制、降级链路全部保持场景无关。场景迁移只需替换 4 个配置——关键词列表、工具描述文本、种子数据、System Prompt。从校园治理到社区治理的横向迁移预计 6-8 小时，不需要改动核心代码。

6.5 实时感知 + 主动推送

不同于被动等待用户输入的传统设计，本系统在每次用户访问时自动执行感知巡检——对比本周与上周工单趋势、检测分类/地点异常激增、统计 SLA 超期积压。感知结果既用于对话上下文注入（让 Agent"知道"最近校园发生了什么），也用于教师端工作台的实时告警。

七、社会价值

  • 1. 降低参与门槛：说一句话就生成结构化工单，不需要找入口、选分类、填表单
  • 2. 建立治理信任：学生能看到自己上报的问题被追踪、被解决——参与不再投进黑洞
  • 3. 缩短响应链路：从"发现问题→层层转达→不知道谁处理"变成"描述→自动工单→追踪→解决→通知"
  • 4. 效果可量化：三维加权健康度评分让治理成效从主观感受变成客观数据

需要说明的是：以上价值当前在 Demo 阶段通过种子数据得到验证，实际治理成效有待接入真实工单系统后进一步检验。

八、可迁移性

8.1 为什么从校园开始

大学校园是基层治理方法的理想原型验证环境：

特质校园对验证的价值
规模可控几万人，物理边界清晰变量可控，先跑通小闭环再放大
问题类型全设施维修、公共卫生、食品安全、政策反馈覆盖基层治理主要场景
反馈链路短学生→辅导员→后勤，三层以内闭环验证成本低，迭代快
数据可获得天气 API、疾控月度公报、校内工单历史感知层有真实数据源
参与意愿强学生天然关心校园环境无需额外的激励设计

8.2 迁移场景映射

本项目的治理工作流与工具层在设计上保持场景无关。以下是三组可行的横向迁移：

治理维度校园（当前）→ 社区治理→ 养老机构→ 企业园区
知校园脉搏社区周报老人日报园区简报
报随手报修居民上报一键求助员工反馈
议有话说居民议事银龄之声员工建言
督治理透明窗治理公开服务监督运维看板
角色学生 / 教师居民 / 网格员老人 / 护工员工 / 行政

8.3 迁移成本

每组横向迁移涉及的工作：

  • Persona Router 关键词列表替换（4 组共 368 个关键词）
  • 工具描述文本与参数名调整（11 个工具文件，16 个工具）
  • 种子数据替换（保留数据规模和叙事结构，换角色和场景名）
  • System Prompt 上下文替换（保留工作流结构和工具映射表）

治理工作流、数据库结构、UI 组件、测试体系——不需要改动。 单组迁移预计 6-8 小时。

校园先知——以大学校园为微型治理实验场，验证一套可迁移至社区、养老、园区等更广泛场景的基层治理方法。让每个学生都成为校园治理的参与者，而不仅仅是旁观者。
