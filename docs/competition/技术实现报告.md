## 三、核心架构：治理工作流编排

本项目的 Agent 引擎以 LangChain AgentExecutor 为核心，在其前后增加了**预处理层**（环境感知 + 意图路由）和**后处理层**（质量控制 + 关联分析），形成一套面向校园治理场景的工作流编排方案。

设计思路借鉴了 OODA（Observe-Orient-Decide-Act）循环的阶段划分——不是因为 OODA 本身有特殊的技术含义，而是因为它的阶段划分恰好能帮我们把不同的预处理和后处理逻辑组织到清晰的边界里：

```
用户输入
   │
   ▼
┌──────────────────────────────────────────────────┐
│  [预处理] OBSERVE — 环境感知                       │
│  查天气 API、统计工单热点、采集时间上下文             │
│  纯函数式数据收集，不涉及 LLM                        │
├──────────────────────────────────────────────────┤
│  [预处理] ORIENT — 意图路由 + 上下文注入             │
│  关键词匹配检测用户意图 → 注入角色提示                │
│  拼接时间/天气/热点/告警 → 形成消息前缀               │
│  （当前版本用关键词匹配，后续规划轻量级分类模型）       │
├──────────────────────────────────────────────────┤
│  [核心] DECIDE + ACT — LangChain Agent 执行         │
│  LangChain AgentExecutor + 10 个治理工具            │
│  DeepSeek 自主编排工具调用顺序                       │
│  return_intermediate_steps=True 捕获完整调用链       │
├──────────────────────────────────────────────────┤
│  [后处理] REFLECT — 质量控制与安全网                  │
│  提取 <think> 块 → 过滤 LangChain 日志泄露行         │
│  检查高危告警是否被响应提及                           │
│  安全网：LLM 未调用工具时强制执行 report_issue        │
│  失败时诚实告知用户，不编造假工单号                    │
├──────────────────────────────────────────────────┤
│  [后处理] ASSOCIATE — 关联洞察（反射器）              │
│  解析工具调用链 → 10 维 SQL 分析（含 z-score 异常检测）│
│  独立 LLM 生成自然语言治理洞察                        │
│  构建结构化推理链 → UI 可视化                         │
└──────────────────────────────────────────────────┘
   │
   ▼
结构化响应 + 推理链 + 主动建议 → 渲染到聊天 UI
```

**关于"OODA"命名的说明**：这不是一套新的认知理论——本质上是 LangChain Agent 的工程增强：前置了环境感知和意图路由来减少 LLM 的无效调用，后置了质量检查和关联分析来弥补 LLM 的不可靠性。工程上的诚实比概念的包装更重要。

### 与普通 Chatbot 的本质区别

| 维度 | 普通 Chatbot | 校园先知 |
|------|-------------|---------|
| 环境感知 | 无 — 只响应用户输入 | **主动** — 每次对话前巡检天气/热点/工单状态 |
| 意图路由 | 靠 LLM 自己判断 | **关键词 + 语义回退** — 零延迟，可调试，不消耗 token |
| 工具调用 | 单次 LLM 决策，调用失败无感知 | **可追溯 + 安全网** — 捕获每步调用，LLM 跳过工具时强制执行 |
| 质量控制 | 无 — 输出什么就是什么 | **多层检查** — 空回复/告警遗漏/短回复自动补救 |
| 关联分析 | 无 | **统计驱动** — z-score 异常检测 + 跨周对比 + 报→议升级路径 |
| 容错降级 | LLM 挂了就挂了 | **三层降级** — 重试(2次) → DB 直查 → 快速报修表单兜底 |
| 闭环反馈 | 无 | **完整** — 上报→分类→追踪→解决→通知→推理链可视化 |

## 四、反射器（Reflector）— 核心技术创新

反射器是本项目技术深度最高的模块（[agent/reflector.py](agent/reflector.py)，618 行）。它在 Agent 完成回复后运行，执行 3 层分析：

### 4.1 工具步骤解析

将 LangChain `intermediate_steps` 转换为结构化步骤卡片，含阶段分类（observe/act）、工具摘要（12 工具分发表）、输入/输出截取。

### 4.2 文本动作回退解析（13 条正则规则）

当 DeepSeek 在文本中直接描述动作（如"已为你生成工单 #42"）而未走 LangChain 正式工具调用时，反射器通过正则匹配恢复伪步骤。这是**工程实践的体现**——不假设 LLM 行为完美，而是优雅降级。

### 4.3 7 维 SQL 关联分析

| 维度 | 分析方法 | 治理价值 |
|------|----------|----------|
| **空间关联** | 提取用户输入中的地点关键词，查同区域待处理工单 | 发现"问题集中区" |
| **时间趋势** | 按类别统计近 7 天新增量 | 发现上升趋势 |
| **复发检测** | 关键词匹配已解决工单 | 发现"假闭环" |
| **异常检测** | 本周 vs 前 4 周均值对比（阈值 1.5x + 至少 3 件） | 发现激增预警 |
| **类别关联** | 同地点不同类别工单共现分析 | 发现连锁反应 |
| **提案关联** | 热门待处理类别 → 匹配相关提案 | 推动"报→议"升级 |
| **解决效率** | 按类别统计平均解决天数 | 发现低效环节 |

### 4.4 LLM 治理洞察生成

当关联数据达到阈值（spatial ≥ 3、temporal ≥ 5、any anomaly），反射器调用**独立 LLM**（`openai.OpenAI` 直连 DeepSeek）生成 2-3 句自然语言洞察。这不只是扔数据——LLM 解读模式含义并给出具体行动建议。该 LLM 调用完全独立于主 Agent，即时失败也不影响回复质量。

## 六、Persona Router — 轻量级意图路由

`detect_persona()` 函数（[agent/prompt.py](agent/prompt.py)）使用关键词匹配实现零延迟的意图检测，将用户输入映射到 4 种角色模式：

| 角色 | 触发关键词数 | 典型场景 |
|------|:-----------:|----------|
| 🔧 报修助手 | 40 | "教三楼灯坏了" → 自动分类+定级+生成工单 |
| 🗳️ 议事顾问 | 22 | "建议延长图书馆时间" → 查重→引导创建或附议 |
| 📊 数据分析师 | 28 | "统计最近报修趋势" → 调取治理统计数据 |
| 🌊 校园观察员 | 17 | "校园脉搏" → 获取快照+播报 |

优先级规则：强数据关键词（统计/分析/趋势）→ 数据分析师胜出；提案关键词出现时议事顾问覆盖观察员。

## 七、数据库设计

11 张表，SQLite WAL 模式，外键约束开启。迁移使用 `ALTER TABLE ADD COLUMN` + try/except 兼容旧数据库。

### 治理核心表（5 张）

```sql
-- 校园工单
campus_issues (id, title, category, location, description, urgency, status,
               author, reported_at, resolved_at)

-- 提案
proposals (id, title, description, category, supporter_count, status,
           response_text, author, created_at)

-- 讨论议题
discussion_topics (id, title, description, category, created_by_agent,
                   is_active, participant_count, created_at, ended_at)

-- 议题意见
topic_opinions (id, topic_id FK, content, participant_label, created_at)

-- 反馈收集
feedback_items (id, topic, opinion, source, sentiment, created_at)
```

### 支撑表（6 张）

`user_profile`（role/name/student_id 字段）、`knowledge_base`、`courses`、`exams`、`events`、`club_activities`。

### 治理健康度算法

```
健康度 = 解决率(40%) + 速度分数(35%) + 积压分数(25%)

- 解决率 = 已解决 / 总工单数
- 速度分数 = 1 - min(1, 平均解决天数 / 14)  # 14 天为满分基准
- 积压分数 = 1 - min(1, 待处理 / 30)         # 30 件为满分基准
- 等级：优(>=80) 良(>=60) 中(>=40) 差(<40)
```

## 九、关键技术决策

### 9.1 为什么 DeepSeek 而非 GPT-4？

| 考量 | DeepSeek | GPT-4 | 结论 |
|------|----------|-------|------|
| Function Calling | 完整支持 `tools` + `tool_choice: "auto"` | 原生支持 | 平手 |
| 中文能力 | 中国团队开发，治理术语理解优秀 | 优秀 | 平手 |
| 成本 | 约 1/10 | — | **DeepSeek 胜出** |
| 可达性 | 国内直连 | 需代理 | **DeepSeek 胜出** |
| 模型无关性 | `ChatOpenAI(base_url=...)` 切换模型只需改 3 行 | — | 架构层面解耦 |

### 9.2 为什么在 AgentExecutor 外加预处理/后处理？

直接用 LangChain AgentExecutor 可以跑通"输入→工具→输出"，但实际使用中暴露出几个问题：
- **LLM 对"现在是几点、天气如何"没有感知** → 加 Observe 层在对话前收集环境数据，减少不必要的工具调用
- **LLM 容易把"查询我的工单"和"上报新问题"搞混** → 加 Orient 层做关键词意图路由，比让 LLM 自己判断更快更准
- **LLM 有时编造假工单号而不调用 report_issue** → 加 Reflect 层做安全网检测，强制执行被跳过的工具
- **单条工单背后可能有统计规律，但 LLM 不会主动查** → 加 Associate 层用 SQL + z-score 做关联分析

这种"预处理层 + AgentExecutor + 后处理层"的三段式结构，本质上是把 LLM 的不可靠性关进了工程围栏里——让它专注于自己擅长的事（自然语言理解和生成），而环境感知、意图消歧、质量检查、统计推理这些事由确定性代码完成。

### 9.3 为什么 Streamlit？

比赛场景（单用户 Demo）下，Streamlit 的开发效率优势压倒性胜出。内置 `st.chat_message`/`st.chat_input`、Altair 图表、session_state 状态管理、多页面导航——单人可完成完整 UI。感知引擎的"后台推送"限制通过空闲刷新机制巧妙规避。
