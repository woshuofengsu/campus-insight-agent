## 三、核心架构：工作流编排

本项目以 LangChain AgentExecutor 为执行核心，在其前后增加了预处理层（环境感知 + 意图路由）和后处理层（质量控制 + 关联分析）。参照 OODA（Observe-Orient-Decide-Act-Reflect-Associate）循环的阶段划分来组织各层逻辑——不是因为 OODA 本身有特殊的技术含义，而是因为它的阶段划分恰好能将预处理和后处理逻辑组织到清晰的边界里：

```
用户输入
   │
   ▼
┌──────────────────────────────────────────────────┐
│  [预处理] Observe — 环境感知                     │
│  查询天气 API、统计工单热点、获取时间上下文      │
│  纯数据收集，不涉及 LLM 调用                     │
├──────────────────────────────────────────────────┤
│  [预处理] Orient — 意图路由 + 上下文注入         │
│  关键词匹配检测意图 → 选择角色提示               │
│  拼接时间/天气/热点/告警 → 形成消息前缀          │
├──────────────────────────────────────────────────┤
│  [核心] Decide + Act — Agent 执行                │
│  LangChain AgentExecutor + 16 个工具             │
│  DeepSeek 编排工具调用顺序                       │
│  return_intermediate_steps=True 捕获完整调用链   │
├──────────────────────────────────────────────────┤
│  [后处理] Reflect — 质量检查                     │
│  提取 <think> 块 → 过滤日志泄露行                │
│  校验工具调用：LLM 未调用的关键工具强制执行      │
│  失败时如实返回，不编造结果                      │
├──────────────────────────────────────────────────┤
│  [后处理] Associate — 关联分析（反射器）         │
│  解析工具调用链 → 10 维 SQL 分析                 │
│  独立 LLM 调用生成治理洞察                       │
│  构建结构化推理链 → 前端可视化                   │
└──────────────────────────────────────────────────┘
   │
   ▼
结构化响应 + 推理链 + 建议 → 渲染到聊天界面
```

关于 OODA 命名的说明：这不是引入新的理论框架——本质上是 LangChain Agent 的工程增强。前置了环境感知和意图路由来减少无效的 LLM 调用，后置了质量检查和关联分析来弥补 LLM 输出的不确定性。工程实现比概念命名更重要。

### 与普通对话机器人的区别

| 维度 | 普通对话机器人 | 本项目 |
|------|-------------|-------|
| 环境感知 | 无——只响应用户输入 | 主动——每次对话前查询天气/热点/工单状态 |
| 意图路由 | 依赖 LLM 自行判断 | 关键词匹配——零延迟，可调试 |
| 工具调用 | 单次 LLM 决策，失败无感知 | 可追溯 + 校验——捕获每步调用，遗漏时补执行 |
| 质量控制 | 无——输出即结果 | 多层检查——空回复/告警遗漏/短回复自动补救 |
| 关联分析 | 无 | 统计驱动——z-score 异常检测 + 跨周对比 |
| 容错降级 | LLM 不可用则服务中断 | 三层降级——重试 → 规则引擎 → 数据库直查 |
| 闭环反馈 | 无 | 上报→分类→追踪→解决→通知 |

## 四、Agent 自主决策机制

### 4.1 工具选择策略

Agent 根据用户输入自主决定调用哪些工具，而非走预设分支。核心机制：

**Persona 信号 → 工具偏好**：`detect_persona()` 检测到"上报诉求"意图后，System Prompt 中对应角色的工具描述会前置，提高 LLM 选择接诉相关工具的概率。这是"引导"而非"限制"——Agent 仍然可以调用任意工具。

**工具描述即决策依据**：每个工具的 `description` 字段是 Agent 的唯一决策信息来源。工具描述采用结构化格式：`[阶段] 功能描述。参数: ...。适用于: ...。` 确保 LLM 能准确判断在什么场景下应该调用哪个工具。

**参数推断**：Agent 从自然语言输入中推断工具参数。例如"3号楼2单元楼道灯不亮" → `report_issue(title="3号楼2单元楼道灯不亮", category="设施维修", location="3号楼2单元", urgency="普通")`。分类推断结合了 LLM 语义理解和关键词匹配降级——LLM 分类失败时，回退到 8 大分类关键词的确定性匹配。

### 4.2 多步编排逻辑

复杂请求需要 Agent 编排多个工具调用。以"上报诉求+查询历史+统计趋势"组合请求为例：

```
用户: "3号楼电梯又坏了，最近这类问题多吗"
  │
  ├─ Step 1: report_issue(title="3号楼电梯故障", category="设施维修", ...)
  │     └─ 返回工单号 #42
  │
  ├─ Step 2: query_issues(category="设施维修", status="待处理", limit=10)
  │     └─ 返回同类别待处理列表（含楼栋分布）
  │
  └─ Step 3: get_governance_stats()
        └─ 返回类别分布统计 → Agent 回复"最近7天设施维修类已有8件，主要集中在3号楼和2号楼区域"
```

每一步的工具调用由 LLM 根据前一步的返回结果动态决定。`return_intermediate_steps=True` 确保完整调用链被捕获，前端可展示推理过程。

### 4.3 自主纠错循环

Agent 的 `enforce.py` 模块在 LLM 完成后检查工具调用完整性：

- **漏调检测**：用户输入匹配到上报关键词但 `intermediate_steps` 中没有 report_issue → 强制补调用
- **空回复检测**：Agent 返回空字符串或过短回复 → 触发降级回复逻辑，走 DB 直查
- **幻觉检测**：Agent 回复中包含工单号但对应工具调用不存在 → 标记为不可信，替换为如实描述

这个循环让 Agent 具备了"知道自己可能犯错并修正"的能力。

## 五、反射器——后处理分析

反射器（[agent/reflector/](agent/reflector/)，已模块化拆分）在 Agent 回复完成后运行，执行三层分析：

### 5.1 工具步骤解析

将 LangChain `intermediate_steps` 转换为结构化步骤卡片，包含阶段分类（observe/act）、工具摘要（16 工具分发表）、输入/输出截取。

### 5.2 文本动作回退解析（12 条正则规则）

当 LLM 在文本中直接描述动作（如"已为你生成工单 #42"）而未走 LangChain 正式工具调用时，反射器通过正则匹配恢复伪步骤。这体现了工程上的防御性设计——不假设 LLM 行为始终符合预期。

### 5.3 10 维 SQL 关联分析

| 维度 | 分析方法 | 治理价值 |
|------|----------|----------|
| **空间关联** | 提取输入中的地点关键词，查同区域待处理工单 | 发现问题集中楼栋/区域 |
| **时间趋势** | 按类别统计近 7 天新增量 | 发现上升趋势 |
| **复发检测** | 关键词匹配已解决工单 | 发现重复问题 |
| **异常检测** | 本周 vs 前 4 周均值对比（阈值 1.5x + ≥3 件） | 发现激增预警 |
| **类别关联** | 同地点不同类别工单共现分析 | 发现连锁问题 |
| **提案关联** | 热门待处理类别匹配相关提案 | 推动报→议升级 |
| **解决效率** | 按类别统计平均解决天数 | 发现低效环节 |
| **跨时间对比** | 本周 vs 上周新增与解决对比 | 判断治理趋势改善/恶化 |
| **Z-score 异常** | 按类别 4 周窗口均值与标准差，统计学异常检测 | 比简单阈值更可靠的异常发现 |
| **报→议升级** | 检测工单密集但无对应提案的类别 | 推动问题升级为治理提案 |

### 5.4 治理洞察生成

当关联数据达到阈值（空间 ≥3、时间 ≥5、任意异常），反射器调用独立 LLM（openai.OpenAI 直连 DeepSeek）生成 2-3 句自然语言洞察。该调用独立于主对话链路，即时失败也不影响回复质量。

## 七、容错与降级设计

系统在三个层级提供容错能力，确保单点故障不导致服务中断：

### 7.1 LLM 调用层

`utils/retry.py` 提供指数退避重试（初始 1s，倍增，最多 2 次），总超时 30s。重试失败后抛出可捕获异常，由上层决定降级策略。

### 7.2 Agent 执行层

LLM API 不可用时，`engine.py` 捕获异常后自动切换到 `OfflineAgent`（[agent/offline_agent.py](agent/offline_agent.py)）——一个基于规则引擎的无 LLM 依赖降级方案：

- **意图路由**：回退到纯关键词匹配（同一套 `_PERSONA_SIGNALS`，368 个关键词全覆盖）
- **工具调用**：工单查询/提案查询/社区脉搏/天气 → 直接 SQL 查询，跳过 LLM 编排
- **诉求分类**：LLM 分类失败 → 8 大分类关键词确定性匹配（设施维修/环境卫生/安全隐患/停车管理/噪音扰民/物业服务/邻里矛盾/社区事务）
- **回复生成**：使用预置回复模板 + 数据填充（如"当前共有 {pending} 件待处理工单，最近一件是 {title}"）

离线模式下功能有退化（无法做开放式对话和复杂推理），但核心治理操作全部可用。

### 7.3 数据层

`fallback.py` 在数据库异常时提供最后一道防线——内存缓存的关键统计数据（最近一次成功的 `get_governance_stats` 结果），有效期 5 分钟。过期后返回预设的静态快照数据。天气 API 不可用时自动切换为模拟气象数据。

### 7.4 降级可观测性

每次降级触发均记录到 `activity_log`（操作日志表），并在 UI 中通过 `st.warning` 提示用户当前处于降级模式。这确保了降级不是无声的——用户和开发者都能感知到系统状态的切换。

## 八、Persona Router——轻量级意图路由

`detect_persona()` 函数（[agent/prompt.py](agent/prompt.py)）使用关键词匹配实现意图检测，将用户输入映射到 4 种角色：

| 角色 | 关键词数 | 典型场景 |
|------|:------:|----------|
| 接诉助手 | 141 | "3号楼楼道灯坏了" → 自动分类+定级+生成工单 |
| 议事顾问 | 108 | "建议延长活动室开放时间" → 查重→引导附议或创建 |
| 数据分析师 | 77 | "统计最近诉求趋势" → 调取治理统计数据 |
| 社区观察员 | 42 | "社区脉搏" → 获取快照+播报 |

优先级规则：强数据关键词（统计/分析/趋势）→ 数据分析师优先；提案关键词出现时议事顾问覆盖观察员；状态查询词（修好了吗/解决了吗）触发接诉助手转向数据查询。

## 九、数据库设计

15 张表，SQLite WAL 模式，外键约束。迁移使用 `ALTER TABLE ADD COLUMN` + try/except 兼容历史数据库。

### 治理核心表（5 张）

```sql
-- 社区工单
community_issues (id, title, category, location, description, urgency, status,
                  author, reported_at, resolved_at)

-- 提案
proposals (id, title, description, category, supporter_count, status,
           response_text, author, created_at)

-- 讨论议题
discussion_topics (id, title, description, category, created_by_agent,
                   is_active, participant_count, created_at, ended_at)

-- 议题意见
topic_opinions (id, topic_id FK, content, participant_label, created_at)

-- 反馈收集
feedback_items (id, topic, opinion, source, sentiment, created_at)
```

### 业务支撑表（6 张）

`user_profile`（role/name/resident_id）、`knowledge_base`（社区百科）、`meal_points`（助餐点）、`activity_rooms`（活动室）、`community_events`（社区活动安排）、`community_notices`（社区通知公告）。

### 系统支撑表（4 张）

`health_surveillance`（疾控监测数据）、`notifications`（通知推送）、`activity_log`（操作日志）、`perception_log`（感知巡检记录）。

### 治理健康度算法

三维加权评分（`compute_health_score()` in [data/db_health.py](../data/db_health.py)）：

```
健康度 = 解决率(40%) + 速度分数(35%) + 积压分数(25%)

- 解决率 = 已解决 / 总工单（空库时 100）
- 速度分数 = max(0, min(100, 120 - 平均解决天数 × 8))
  （7 天为满分基准线，无数据时为中性 70）
- 积压分数 = 近 7 天新增 vs 解决对比
  新增=0 → 100 | 解决≥新增 → 60+(解决-新增)/新增×40 | 解决<新增 → 解决/新增×100+10（上限95）
- 等级：优(≥80) | 良(≥50) | 需改进(<50)
- 趋势：↓改善中(≥75) | →持平(≥45) | ↑需关注(<45)
```

审计模块（[agent/governance_audit.py](../agent/governance_audit.py)）在此基础上增加四维度交叉分析（工单管理/提案参与/居民参与/热点检测），参考 ISO 37120 市政治理指标体系，输出 A/B/C/D 等级 + Top 3 优先行动建议。

## 十一、关键技术决策

### 11.1 模型选择

| 考量 | DeepSeek | GPT-4 | 结论 |
|------|----------|-------|------|
| Function Calling | 完整支持 `tools` + `tool_choice` | 原生支持 | 持平 |
| 中文能力 | 国产模型，治理术语理解良好 | 良好 | 持平 |
| 调用成本 | 约 1/10 | — | DeepSeek |
| 网络可达性 | 国内直连 | 需代理 | DeepSeek |
| 模型可替换性 | `ChatOpenAI(base_url=...)` 切换只需改 3 行 | — | 架构层面解耦 |

### 11.2 为什么在 AgentExecutor 外增加预处理/后处理

直接使用 LangChain AgentExecutor 可以实现"输入→工具→输出"的基本流程，但实际使用中暴露出几个问题：
- **LLM 对环境无感知**——不知道当前时间、天气、工单热点 → 增加 Observe 层在对话前收集环境数据
- **LLM 容易混淆意图**——"查询我的工单"和"上报新问题"可能被误判 → 增加 Orient 层做关键词意图路由
- **LLM 可能编造结果**——描述"工单 #42 已创建"但实际未调用工具 → 增加 Reflect 层校验并补执行
- **单条数据背后的统计规律 LLM 不会主动分析** → 增加 Associate 层做 SQL + z-score 关联分析

这种结构将 LLM 的不可靠性限制在可控范围内——让 LLM 专注自然语言理解和生成，环境感知、意图判断、质量检查、统计推理由确定性代码完成。

### 11.3 为什么 Streamlit

比赛场景（单用户演示）下，Streamlit 的开发效率优势明显。内置 `st.chat_message`/`st.chat_input`、Altair 图表、session_state 状态管理、多页面导航——单人可在短时间内完成完整的交互界面。

## 十二、Prompt Engineering 策略

### 12.1 System Prompt 结构

System Prompt 由 `agent/prompt.py` 中的 `get_system_prompt()` 动态生成，包含以下固定块：

1. **角色定义**（~80 tokens）：根据 `detect_persona()` 的结果选择对应角色描述
2. **工具映射表**（~200 tokens）：16 个工具的结构化清单，每个工具一行：`[阶段] 函数名 — 参数 — 一句话说明`
3. **预取数据标注**（~150 tokens）：当前已预取的社区脉搏/天气/工单数据，标记为可直接使用
4. **行为约束**（~100 tokens）：禁止编造工单号、禁止跳过必要工具调用、失败时如实告知

总长度控制在 600-800 tokens，确保在 DeepSeek 的上下文窗口内为对话历史留出足够空间。

### 12.2 工具描述设计

每个 LangChain Tool 的 `description` 是 Prompt Engineering 的关键——它是 LLM 判断是否调用该工具的唯一信息来源。设计原则：

- **阶段前缀**：`[知]/[报]/[议]/[督]` 让 LLM 快速理解工具的治理定位
- **触发条件显式化**：不写"查询工单"，写"当用户询问某类别/状态的工单列表时使用"
- **参数范围约束**：`category 参数可选值：设施维修/环境卫生/安全隐患/停车管理/噪音扰民/物业服务/邻里矛盾/社区事务`
- **反例引导**：对于查询类工具，添加"如果系统已预取数据则跳过此调用"

### 12.3 Few-Shot 示例注入

在 System Prompt 中嵌入 4 组典型交互示例（每组 2 轮对话 + 工具调用），覆盖上报诉求、查询、提案、闲聊四个场景。示例展示的不是"正确答案"而是"正确的工具调用模式"——让 LLM 学会在什么情况下应该调用哪个工具、应该传递什么参数。

## 十六、可迁移性：架构的场景无关设计

### 16.1 架构的场景无关性

治理工作流（OODA 五阶段）、工具层（16 个 Tool + 自动发现）、数据库结构（15 张表）、校验机制（enforce + closed_loop）、降级链路（重试→规则引擎→DB 直查）——全部保持场景无关。场景特定内容仅存在于 4 个文件中，替换即可迁移：

| 耦合点 | 文件 | 迁移操作 |
|--------|------|----------|
| 意图关键词 | `agent/prompt.py` → `_PERSONA_SIGNALS` | 替换 4 组 368 个关键词 |
| 工具描述 | `tools/*.py` 16 个工具的 docstring | 替换文档字符串与返回值模板 |
| System Prompt | `agent/prompt.py` → `get_system_prompt()` | 替换角色上下文段落 |
| 种子数据 | `data/seed.py` | 替换人物与场景名，保留数据规模和叙事结构 |

**工作流引擎、15 张表结构、UI 组件、校验逻辑、328 个测试——不需要代码改动。** 单场景迁移预计 6-8 小时。

## 十七、部署与运维

### 17.1 部署方式

项目通过 Streamlit Cloud 部署，连接到 GitHub 仓库自动构建。`.streamlit/config.toml` 中配置主题和服务器参数。部署流程：

1. 推送代码到 GitHub 主分支
2. Streamlit Cloud 自动检测更新并重新构建
3. 依赖安装依据 `requirements.txt`（11 个直接依赖）
4. 环境变量（API Key 等）通过 Streamlit Secrets 管理，不入仓库

从 `git push` 到线上生效约 2-3 分钟。

### 17.2 CI/CD

`.github/workflows/test.yml` 配置了 push 和 PR 触发器：Python 3.10 + 安装依赖 + `pytest tests/ -q`。328 个测试在 30 秒内完成。CI 失败时阻止合并。

### 17.3 监控与日志

`utils/logger.py` 统一日志格式，关键路径均有 `_log.info` 埋点。`activity_log` 表记录所有操作（用户行为 + 系统事件 + 降级触发），可按时间范围和事件类型检索。感知巡检（`perception_log`）每次扫描记录快照，用于追踪系统健康度变化。

### 17.4 运行成本

- DeepSeek API：每次对话约 2-5K tokens（含 System Prompt + 工具描述 + 多轮对话历史 + 工具调用结果），反射器额外一次独立 LLM 调用
- Streamlit Cloud：免费层可用于演示（单用户场景）
- 和风天气 API：免费层 1000 次/天
- 演示场景下运营成本极低，生产环境成本取决于实际调用量
