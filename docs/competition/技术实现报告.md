## 一、技术栈总览

| 层 | 选型 | 说明 |
|---|---|---|
| 主服务 | **FastAPI + Uvicorn**（`api_web.py`，:8000） | 130 条路由，14 个路由模块；同时托管 Vue3 构建产物 |
| 前端 | **Vue3 + Vite + Naive UI** | 三端分离：居民 14 页 / 网格员 9 页 / 老年 8 页；设计令牌体系；移动端适配 |
| 多智能体 | 自研编排（`agent/orchestrator.py`）+ 黑板（`agent/blackboard.py`） | 9 个声明式角色、消息队列真协商、双层防线、全程留痕 |
| 大模型 | DeepSeek（`deepseek-chat`，OpenAI 兼容协议） | 四个特性开关可独立控制；规则优先以保确定性并降本 |
| 向量模型 | 阿里云百炼 `text-embedding-v3`（1024 维） | 与词法检索经 RRF 融合（`agent/rag.py`） |
| 数据层 | **SQLite（WAL）** + 原生 `sqlite3` | schema **v46**，46 个版本化迁移，50 张业务表；演进路径见 `docs/scaling.md` |
| 安全 | 标准库实现 HS256 JWT + **AES-256-GCM** 字段加密 + 脱敏 + 安全响应头 | 密钥生产姿态 **fail-closed** |
| 外部数据 | 和风天气 API（按社区 adcode 取数） | 不可用时降级模拟数据，降级有留痕 |
| 备线/插件 | `app.py`（Streamlit，:8501）为历史备线；`api.py`（:18800）为扣子插件入口 | 二者仅共用 `data/` 服务层，**均非主线** |

**为什么主链路从 Streamlit 迁到 FastAPI + Vue3**：Streamlit 适合单用户演示，但做不了三端差异化、角色级权限、WebSocket 实时通知、移动端适配与无障碍达标。比赛要展示的是"基层治理平台"，不是"一个能对话的页面"，所以把主链路重做成真正的服务端 + 三端前端；Streamlit 版仅作为历史备线存档。

## 三、多智能体：角色、黑板与真协商

### 3.1 九个声明式角色

角色注册在 `agent/roles/__init__.py` 的 `AGENT_CLASSES`（角色 id 有状态，不得随意改）：

| 角色 | key | 职责 | 可见工具范围 |
|---|---|---|---|
| 接待员 | `receptionist` | 入口路由、意图定性、汇总回复 | 查询类 |
| 报修调度 | `repair_dispatch` | 建单、分类、定级、派单、SLA | 报修全流程 |
| 提案协商 | `proposal_collab` | 提案查重、附议、里程碑、回复 | 议事类 |
| 政策专员 | `policy_expert` | 政策检索增强问答、引用强制 | 知识库 + 检索 |
| 健康顾问 | `health_advisor` | 健康建议、用药提醒、就医引导（不诊断） | 健康类 |
| 天气守护 | `weather_guardian` | 天气取数、恶劣天气提示、主动预警 | 天气 + 脉搏 |
| 通知管理员 | `notification_manager` | 站内信、多通道触达、已读回执 | 通知类 |
| 网格助手 | `grid_assistant` | 网格员侧统计、热点、下钻 | 统计类 |
| 合规审计 | `compliance_auditor` | **所有业务输出必过**的合规检查 | 无（只读） |

**声明式**的含义：角色 = 一份配置（`key` / `name` / `persona` / `tools` / `intents` / `prompt` 片段），
执行逻辑统一由基类提供。新增角色不改编排代码，只加一份声明 + 注册。

### 3.2 黑板（`agent/blackboard.py`）

```
Blackboard
├── write(key, value, source) / read(key) / read_meta(key)   # 共享上下文
├── post_message(agent, msg) / get_messages(agent) / clear_messages(agent)
├── lock(name) / unlock(name)                                 # 互斥（BlackboardLockError）
├── get_history() / to_dict()                                 # 执行链留痕
└── 历史上限 500 条（超限裁剪，防内存增长）
```

消息类型：`task_request` / `task_response` / `notify` / `error` / `handoff`。
每条消息带 `from` / `to` / `type` / `payload` / `priority`，**可序列化、可投屏、可追责**。

### 3.3 编排流程（`Orchestrator.run`）

```
用户输入
  │
  ├─ 1) 属地解析（每轮一次）：resolve_region(ctx) → 政策 boost / 天气 adcode
  │      （失败只 warning 并回落全国，不阻断）
  ├─ 2) 意图 → 角色派发 _dispatch()
  │      接待员定性 → 目标角色 _call_agent()（超时重试一次）
  │      → 目标角色可 post_message 给第三方（handoff / notify）
  ├─ 3) 协商消费 _drain_negotiations()
  │      按 priority 排序处理目标队列 → 回复发起方（task_response）
  │      → 响应可能再触发第三方（天气 → 健康 → 通知），链式往返
  │      → 循环防护：单目标累计协商 ≥ 2 轮强制转人工；遍历上限 5 轮兜底
  ├─ 4) 合规审计（所有业务输出必过）
  │      不通过 → Arbiter 裁决 → 转人工处理包（handoff_id 可追）
  └─ 5) _finish()：回复 + 动作按钮 + 执行链留痕（黑板上每个 Agent 步骤落 agent_logs）
```

**为什么这算"真协商"而不是工作流**：

| 维度 | 静态工作流 | 本项目 |
|---|---|---|
| 调用谁 | 编排代码写死 | 运行时由角色按消息决定，可跨角色多轮往返 |
| 能否改变执行链 | 不能 | 能——如"高温预警"由天气守护主动触发健康顾问与通知管理员 |
| 可追责性 | 日志靠打印 | 黑板消息 + `agent_logs` 双留痕（含仲裁规则名与决策） |
| 失败处置 | 重试/报错 | Arbiter 规则裁决 → 转人工处理包（不静默失败） |

### 3.4 双层防线

**Verifier（`agent/verifier.py`）** — 事实与安全校验，按域分流（`_general_checks` / `_policy_checks` / `_health_checks` / `_grid_checks`）：

- 幻觉：回复中出现未在本次工具结果里出现过的编号/数字（工单号、提案号）
- 隐私：手机号等 PII 泄露到回复里
- 医疗：诊断性句式（"你患了…"）——健康顾问只做建议与引导，不做诊断
- 政策：引用下标越界或无检索材料却作答 → 转人工

**Arbiter（`agent/arbiter.py`）** — 冲突仲裁，5 条规则**顺序**裁决，首个命中即生效：

| 顺序 | 规则 | 条件 | 裁决 |
|---|---|---|---|
| 1 | `compliance_first` | 合规审计不通过 | `block`（合规有否决权） |
| 2 | `safety_first` | 涉及人身安全 | `human` |
| 3 | `professional_first` | 专业域判断冲突 | `professional`（以专业 Agent 意见为准） |
| 4 | `manual_required` | 涉及费用或不可逆操作 | `human` |
| 5 | `data_version` | 数据版本冲突 | `latest_version` |
| — | 兜底 | 无法裁决 | `human`（保守优先） |

每次裁决都写入 `agent_logs`（`routed=仲裁/<规则名>`、`status=裁决结果`），网格端 `/agent/logs?intent=仲裁` 可直接查。

### 3.5 人在环（Human-in-the-loop）

以下情形一律**不自动作答**，改为生成"人工处理包"（`handoff_id` 可追）：

1. 合规审计不通过；2. Verifier 判定高风险的幻觉/隐私/诊断问题；3. 协商超过 2 轮（可能死循环）；
4. 政策问答检索不到任何达标材料；5. Arbiter 兜底裁决。
> 设计底线：**宁可转人工，也不给居民一个可能错的答案。**

## 五、知识增强与检索

### 5.1 知识库与混合检索

- **语料**：62 条知识（61 条已发布、55 条公开政策摘要、43 条带"适用地区"），政策摘要均可溯源。
- **两路检索并存**：
  - 线上问答路径 `data/db_policy.search_published_knowledge`：加权和打分 + 阈值（`_match_threshold = 2.0`）判定"能否自动作答"。
  - 智能体路径 `agent/rag.search_hybrid`：词法（同义词/方言扩展）+ 向量（1024 维）+ **RRF 融合（k=60）**重排。
- **为什么两套**：问答要的是"够不够格自动回答"（需要阈值与确定边界）；Agent 要的是"给出最相关的上下文"（需要排序质量）。两套共用同一份属地权重常量，口径不会分叉。

### 5.2 评测（可复算）

| 指标 | 值 |
|---|---|
| 金标用例 | **48 条**（口语化提问，含 6 条属地用例） |
| 混合检索 hit@1 | **48/48 = 100%** |
| 纯词法基线 hit@1 | 85.7% |
| 属地用例 Top-1 正确 | 4/4 |
| 命令 | `python scripts/rag_eval.py` |

> **诚实口径**：金标是自建的，所以 100% 只说明"在这 48 条上混合检索优于纯词法"，
> **不作为泛化能力结论**。可复算的消融对比才是它的价值。

### 5.3 轻量知识图谱

- 规模：**89 实体 / 202 关系 / 772 提及**（`_m45_knowledge_graph` 迁移落地；工单覆盖 96%，（可用 `python scripts/rebuild_kg.py --stats` 复核））。
- 用途**不是可视化**，而是"按实体反查"：从一条工单里的地址/设施/类别，反查历史同类工单与相关政策。
- 网格端与 Agent（`grid_assistant`）都能查。不做图可视化的理由：比赛时间应投在能验证的链路上，
  一个好看的图回答不了"它解决什么问题"。

## 六、属地化（地区识别）——本项目的人文落点

### 6.1 设计原则

> **属地只影响"选谁"，绝不影响"能不能自动回答"。**
> 而且**不采 GPS**：居民的网格归属是确定事实（由账号/社区登记决定），不需要、也不应该靠设备定位。

### 6.2 实现（`utils/region.py`，唯一入口）

```
Region(community, province, city, city_id, district, street, source)
   ├─ chain()        # 社区 → 街道 → 区 → 市 → 省 的行政区划链
   ├─ label()        # "北京市海淀区·海淀小区"（三端展示口径统一）
   └─ cache_key()    # 天气缓存键（adcode 优先）
normalize_area(text)      # 复合地名归一："北京市海淀区" → {北京市, 海淀区}
resolve_region(...)       # 账号社区 → 区域链；未登记社区 warning 一次后回落全局默认
policy_region_boost(...)  # 政策属地加成：街道/区 1.5 · 市 1.0 · 省 0.5 · 全国 0 · 跨区 −0.5
rrf_region_bonus(...)     # Agent 路径的属地加成（与上面同一套权重常量）
```

**政策打分（`data/db_policy.search_published_knowledge`）**

```
base_score = 词法/语义相关度                # 决定"能不能答"
score      = base_score + region_boost      # 决定"优先选谁"
answer_entry = final 排序中第一条 base_score ≥ 阈值 的条目   # 选答只看 base
```

- 加成只作用于 `base_score > 0` 的条目（不把无关政策抬上来）。
- **跨区惩罚**：`_is_district_token` 识别到"用户在外区"时，本区政策给 −0.5（不给城市级加成），避免"朝阳用户被推海淀政策"。
- 历史坑：`海淀小区` 以"区"结尾会被误判为行政区 —— 用 `_NOT_DISTRICT_SUFFIX = ("小区","社区","园区","学区","景区","地区")` 排除。
- **最有价值的一条测试**：`test_answer_entry_never_downgrades_answerability` —— 通过 monkeypatch 强制制造"排序倒挂"
  （属地加成把低分条目顶到第一），断言系统仍能自动作答，而不是因为 top1 不达标就转人工。

**天气**：按社区 adcode 取数，`refresh_weather(city, city_id)` 用 `city_id or city` 做缓存键，
`get_daily_advice` 的每日缓存 action 带 key（否则跨社区串味）。
居民端、老年端、Agent 文本链路**三端同批接入**——同场演示不能出现两套地名。

### 6.3 演示价值

同一个问题（"我们社区高龄老人有什么补贴？"）在两个演示社区得到不同结果：

| 演示账号社区 | 命中 | 属地级别 |
|---|---|---|
| 海淀小区（海淀区） | 《海淀小区社区助餐补贴与代办服务指引》 | `local_street` |
| 朝阳试点社区（朝阳区） | 《北京市高龄老人津贴申领实施细则》等北京市级政策 | `local_city` |

**这就是"一区一策"落地在系统里的样子**：不是给所有人同一份全国政策，也不是凭定位猜，而是按确定的网格归属选对政策，选不到就退回全国兜底。

## 七、LLM 的使用与降级

### 7.1 原则：规则为骨、LLM 为脑

| 能力 | 实现 | 是否依赖 LLM |
|---|---|---|
| 角色路由 | 确定性关键词 + 同义词/方言归一 + 优先级规则 | 否（可选 LLM 兜底） |
| 权限、脱敏、风控、阈值 | 确定性代码 | 否 |
| 状态机、迁移、留痕 | SQLite + 版本化迁移 | 否 |
| 模糊意图兜底 | `RECEPTION_LLM_FALLBACK` | 是（可关） |
| 政策问答生成 | `POLICY_LLM_RAG`（闭集 + 引用强制） | 是（可关） |
| 跨角色协商决策 | `LLM_NEGOTIATION` | 是（可关） |
| 编排选人 | `LLM_ORCHESTRATION` | 是（可关） |

**四个开关全部可在 `.env` 一键关闭**，关掉后系统仍是完整可用的规则版（演示可现场对比"同一问题、两种姿态"）。
代码默认全关（确定性优先、成本可控）；**使用姿态**可全开（本机 `.env` 全开用于演示）。
> 陷阱记录：改 `.env` 必须重启服务才生效（否则你测的是旧姿态）；
> 依赖开关的测试必须显式 `monkeypatch` 钉住姿态，否则本机一开开关就会真打网络造成假失败（本轮实测踩到 2 条，已修）。

### 7.2 用量与成本可观测

- 所有 LLM 调用统一走 `agent/llm_client.py`，逐笔写入 `llm_usage` 表（模型、tokens、费用）。
- **记账不许静默丢账**：`_record` 失败会懒初始化重试并 warning（有子进程回归测试守着）。
- 实测：库内记账快照（2026-09-14）：**57 次调用 / ¥0.0139**（评测 40 题 ¥0.0109 + 跨角色协商 15 次 ¥0.0030；稳定口径是单次均价 **¥0.0002**）；演示姿态下单轮对话约 **+0.9 秒 / +¥0.0002**。
- 网格端工作台可见费用卡，评委可现场核对。

### 7.3 降级链路

```
LLM 可用  → 规则 + LLM（闭集输出、引用校验）
LLM 不可用 → 纯规则路径（意图关键词、模板回复、SQL 直查）——功能退化但核心治理操作全可用
外部 API 不可用（天气等） → 缓存 → 模拟数据，且**降级必留痕**（不静默）
```

## 八、数据层

### 8.1 Schema 与迁移纪律

- 纯标准库 `sqlite3`（`data/db_core.get_db`），WAL 模式，schema **v46**，**50 张业务表**。
- **46 个版本化迁移**：函数命名 `_m{N}_{name}`，注册进 `post` 列表；`_add_column` 用 `PRAGMA` 判存，幂等。
- **禁止运行时裸 ALTER**：v46 已把历史遗留的运行时补列全部收回迁移链（第九轮复审发现并修复）。
- 新建库与存量升级走**同一条路径**，保证"评委拿到的库"和"我们的库"结构一致。

### 8.2 数据安全

| 措施 | 实现 | 验证 |
|---|---|---|
| 手机号加密落库 | **AES-256-GCM**（`utils/crypto.py`，密文带 `g1$` 算法版本前缀；旧格式仅解密兼容） | `python scripts/audit_phone_encryption.py` → 8 张表**明文计数 0** |
| 展示脱敏 | `_mask_phone()`，留痕 `activity_log.detail` 不含完整手机号 | 审计脚本 + 端到端验收断言 |
| 注销级联 | 账号注销级联清理密文与关联记录 | 单元测试覆盖 |
| 密钥姿态 | `CRYPTO_KEY` / `WEB_JWT_SECRET` 在 `DEMO_MODE=false` 且缺失或是仓库占位值时**拒绝启动**（fail-closed） | `python scripts/demo_preflight.py` 姿态行 |
| 自由文本 PII | **未治理**（边界，见第十二节） | 已列入计划 |

覆盖的 8 张表：`community_issues`、`user_profile`、`emergency_contacts`、`health_consults`、
`emergency_calls`、`proposals`、`proposal_drafts`、`issue_drafts`。

### 8.3 鉴权与安全响应头

- **JWT HS256**：标准库 HMAC 实现（不引第三方库），token 内嵌角色与社区，支撑属地解析。
- 角色权限：网格端指标端点按角色锁定；老年端支持免登录演示账号（受 `DEMO_MODE` 约束）。
- 安全响应头：CSP（`script-src 'self'`，**禁止内联脚本**）、HSTS、`X-Frame-Options`、`X-Content-Type-Options` 等。
- 限流为进程内实现（单机够用，多进程需 Redis——已列入演进路径）。

### 9.1 三端差异化

| 端 | 页数 | 设计取向 |
|---|---|---|

### 9.2 工程化

- **设计令牌体系**（`web/src/style.css`）：颜色/字号/间距/圆角全部令牌化；
  **语义文字色一律用亮暗成对令牌**（写死 hex 在暗色下不随主题切换，`ui_audit` 会抓——第九轮抓到 6 处）。
- **禁用内联脚本**：调试入口是同源外部文件 `web/public/debug.js`（`?debug=1`），避免 CSP 报错被评委看见。
- **`web/dist` 不进 git**：两个审计脚本内置"dist 落后于源码直接红字退出"的新鲜度闸（复审 F4 的教训：
  不 build 就审计，测的是旧包，会得出"修了没生效/没修也报绿"的假结论）。
- **PWA 口径**：只做到"可添加到主屏幕 + 全屏类 App 体验"，**没有 service worker，不做也不宣称离线能力**
  （政策与工单缓存过期会误导居民）。该口径由 `tests/test_claims_consistency.py` 门禁守着。

### 10.2 故障注入：证明门禁真的会红

只证明"测试是绿的"不够，还要证明"出问题时会红"。本轮做了**故障注入验证**：
故意埋入典型缺陷（越权、明文手机号、跨社区政策串味、静默吞异常返回成功、审计阈值失效等），
**8 次注入 8 次被门禁拦下**；属地化专项 4 次注入 4 次拦下（详见 `docs/spec/dev-log.md` 四十七节）。

### 10.3 关于"661 项测试"的口径（主动说明）

`661 = 660 通过 + 1 需外部服务跳过`。其中 `tests/test_ablation.py` 的 6 项是给消融报告**供数的冒烟项**（只跑通、不断言）；
对外引用的两个指标另有**硬断言**守住：`test_persona_routing_is_accurate`（断言路由准确率 `== 100.0`）、
`test_tool_discovery_covers_expected`。新增任何不做断言的 `test_*` 都会被门禁拦下——**不给数字留注水空间**。

### 10.4 测试隔离踩过的坑（工程真实感）

一次"两两跑都过、三个文件一起跑 21 条失败"的诡异现象，根因是三处叠加：
`test_dispatch` 退出时把全局 `_DB_PATH` 留在已删除的临时库 + `api_web._ensure_db` 因 `_db_path_seeded` 提前返回。
修复做了三层（fixture 保存/恢复全局、`_db_path_seeded` 重置、模块级 autouse 隔离），并立下纪律：
**绝不并发跑两个 pytest 会话**（会互相清库，产生假失败）。

## 十三、可迁移性：架构与场景解耦

治理闭环（感知 → 理解 → 协作 → 处置 → 留痕）、多智能体编排、双层防线、属地解析、加密与审计链路
**全部与"社区"这个场景无关**。场景相关内容集中在少数几处，替换即可迁移到其他基层场景（园区、校园、乡镇、政务服务窗口）：

| 耦合点 | 位置 | 迁移操作 |
|---|---|---|
| 角色声明 | `agent/roles/`（9 份声明） | 换 persona / 工具范围 / 意图关键词 |
| 工具集 | `tools/`（16 个） | 增删文件即自动注册 |
| 政策语料 | `data/seed.py` + 知识库表 | 换本地政策摘要，保留结构与属地字段 |
| 属地映射 | `config.REGION_BY_COMMUNITY` | 换社区名单与行政区划 |
| 端形态 | `web/src/views/{resident,grid,elderly}` | 换页面与文案 |
| 种子数据 | `data/seed.py` | 换场景名与数据规模 |

**不动的东西**：编排器、黑板、Verifier/Arbiter、数据层与迁移机制、加密/脱敏/审计、全部质量门禁。
> 这正是一个**平台**与一个**demo** 的区别。

## 十四、开发方法

- **单人全栈 + AI 辅助编码**：架构决策、安全边界、评测口径由人定；重复性代码与测试编写借助 AI 加速。
- **分阶段推进**：数据层 → 工具层 → 智能体编排 → 三端前端 → 质量门禁 → 属地化与交付材料。
- **每轮外部复审都留回执**：`docs/review/` 收录多轮外部复审报告与**逐条处理回执**（含未修复项与理由），
  完整开发日志（48 节）在 `docs/spec/dev-log.md`——**过程可查，比结论更有说服力**。
- **门禁即文档**：把"我们做得好"翻译成可执行的脚本，任何人（包括未来的我）都能复算。
