## 三、核心架构：工作流编排

本项目以 LangChain AgentExecutor 为执行核心，在其前后增加了预处理层（环境感知 + 意图路由）和后处理层（质量控制 + 关联分析）。参照 OODA（Observe-Orient-Decide-Act）循环的阶段划分来组织各层逻辑——不是因为 OODA 本身有特殊的技术含义，而是因为它的阶段划分恰好能将预处理和后处理逻辑组织到清晰的边界里：

```
用户输入
   │
   ▼
┌──────────────────────────────────────────────────┐
│  [预处理] Observe — 环境感知                       │
│  查询天气 API、统计工单热点、获取时间上下文           │
│  纯数据收集，不涉及 LLM 调用                        │
├──────────────────────────────────────────────────┤
│  [预处理] Orient — 意图路由 + 上下文注入             │
│  关键词匹配检测意图 → 选择角色提示                   │
│  拼接时间/天气/热点/告警 → 形成消息前缀              │
├──────────────────────────────────────────────────┤
│  [核心] Decide + Act — Agent 执行                  │
│  LangChain AgentExecutor + 16 个工具               │
│  DeepSeek 编排工具调用顺序                          │
│  return_intermediate_steps=True 捕获完整调用链      │
├──────────────────────────────────────────────────┤
│  [后处理] Reflect — 质量检查                        │
│  提取 &lt;think&gt; 块 → 过滤日志泄露行              │
│  校验工具调用：LLM 未调用的关键工具强制执行            │
│  失败时如实返回，不编造结果                          │
├──────────────────────────────────────────────────┤
│  [后处理] Associate — 关联分析（反射器）             │
│  解析工具调用链 → 10 维 SQL 分析                    │
│  独立 LLM 调用生成治理洞察                          │
│  构建结构化推理链 → 前端可视化                       │
└──────────────────────────────────────────────────┘
   │
   ▼
结构化响应 + 推理链 + 建议 → 渲染到聊天界面
```

关于 OODA 命名的说明：这不是引入新的理论框架——本质上是 LangChain Agent 的工程增强。前置了环境感知和意图路由来减少无效的 LLM 调用，后置了质量检查和关联分析来弥补 LLM 输出的不确定性。工程实现比概念命名更重要。

### 与普通对话机器人的区别

| 维度 | 普通对话机器人 | 本项目 |
|------|-------------|-------|
| 环境感知 | 无——只响应用户输入 | 主动——每次对话前查询天气/热点/工单状态 |
| 意图路由 | 依赖 LLM 自行判断 | 关键词 + 语义回退——零延迟，可调试 |
| 工具调用 | 单次 LLM 决策，失败无感知 | 可追溯 + 校验——捕获每步调用，遗漏时补执行 |
| 质量控制 | 无——输出即结果 | 多层检查——空回复/告警遗漏/短回复自动补救 |
| 关联分析 | 无 | 统计驱动——z-score 异常检测 + 跨周对比 |
| 容错降级 | LLM 不可用则服务中断 | 三层降级——重试 → 规则引擎 → 数据库直查 |
| 闭环反馈 | 无 | 上报→分类→追踪→解决→通知 |

## 四、反射器——后处理分析

反射器（[agent/reflector/](agent/reflector/)，已模块化拆分）在 Agent 回复完成后运行，执行三层分析：

### 4.1 工具步骤解析

将 LangChain `intermediate_steps` 转换为结构化步骤卡片，包含阶段分类（observe/act）、工具摘要（16 工具分发表）、输入/输出截取。

### 4.2 文本动作回退解析（13 条正则规则）

当 LLM 在文本中直接描述动作（如"已为你生成工单 #42"）而未走 LangChain 正式工具调用时，反射器通过正则匹配恢复伪步骤。这体现了工程上的防御性设计——不假设 LLM 行为始终符合预期。

### 4.3 7 维 SQL 关联分析

| 维度 | 分析方法 | 治理价值 |
|------|----------|----------|
| **空间关联** | 提取输入中的地点关键词，查同区域待处理工单 | 发现问题集中区域 |
| **时间趋势** | 按类别统计近 7 天新增量 | 发现上升趋势 |
| **复发检测** | 关键词匹配已解决工单 | 发现重复问题 |
| **异常检测** | 本周 vs 前 4 周均值对比（阈值 1.5x + ≥3 件） | 发现激增预警 |
| **类别关联** | 同地点不同类别工单共现分析 | 发现连锁问题 |
| **提案关联** | 热门待处理类别匹配相关提案 | 推动报→议升级 |
| **解决效率** | 按类别统计平均解决天数 | 发现低效环节 |

### 4.4 治理洞察生成

当关联数据达到阈值（空间 ≥3、时间 ≥5、任意异常），反射器调用独立 LLM（openai.OpenAI 直连 DeepSeek）生成 2-3 句自然语言洞察。该调用独立于主对话链路，即时失败也不影响回复质量。

## 六、Persona Router——轻量级意图路由

`detect_persona()` 函数（[agent/prompt.py](agent/prompt.py)）使用关键词匹配实现意图检测，将用户输入映射到 4 种角色：

| 角色 | 关键词数 | 典型场景 |
|------|:------:|----------|
| 报修助手 | 60+ | "教三楼灯坏了" → 自动分类+定级+生成工单 |
| 议事顾问 | 45+ | "建议延长图书馆时间" → 查重→引导附议或创建 |
| 数据分析师 | 45+ | "统计最近报修趋势" → 调取治理统计数据 |
| 校园观察员 | 25+ | "校园脉搏" → 获取快照+播报 |

优先级规则：强数据关键词（统计/分析/趋势）→ 数据分析师优先；提案关键词出现时议事顾问覆盖观察员；状态查询词（修好了吗/解决了吗）触发报修复向到数据查询。

## 七、数据库设计

11 张表，SQLite WAL 模式，外键约束。迁移使用 `ALTER TABLE ADD COLUMN` + try/except 兼容历史数据库。

### 治理核心表（5 张）

```sql
-- 校园工单

               author, reported_at, resolved_at)

-- 提案

-- 讨论议题

                   is_active, participant_count, created_at, ended_at)

-- 议题意见
topic_opinions (id, topic_id FK, content, participant_label, created_at)

-- 反馈收集
feedback_items (id, topic, opinion, source, sentiment, created_at)
```

### 支撑表（6 张）

`user_profile`（role/name/student_id）、`knowledge_base`、`courses`、`exams`、`events`、`club_activities`。

### 治理健康度算法

三维加权评分（`compute_health_score()` in [data/db_health.py](../data/db_health.py)）：

```
健康度 = 解决率(40%) + 速度分数(35%) + 积压分数(25%)

- 解决率 = 已解决 / 总工单（空库时 100）
- 速度分数 = max(0, min(100, 120 - 平均解决天数 × 8))
  （7 天为满分基准线，无数据时为中性 70）
- 积压分数 = 近 7 天新增 vs 解决对比
  新增=0 → 100 | 解决≥新增 → 60+(解决/新增)×40 | 解决<新增 → 0-95
- 等级：优(≥80) | 良(≥50) | 需改进(<50)
- 趋势：↓改善中(≥75) | →持平(≥45) | ↑需关注(<45)
```

审计模块（[agent/governance_audit.py](../agent/governance_audit.py)）在此基础上增加四维度交叉分析（工单管理/提案参与/公民参与/热点检测），参考 ISO 37120 市政治理指标体系，输出 A/B/C/D 等级 + Top 3 优先行动建议。

## 九、关键技术决策

### 9.1 模型选择

| 考量 | DeepSeek | GPT-4 | 结论 |
|------|----------|-------|------|
| Function Calling | 完整支持 `tools` + `tool_choice` | 原生支持 | 持平 |
| 中文能力 | 国产模型，治理术语理解良好 | 良好 | 持平 |
| 调用成本 | 约 1/10 | — | DeepSeek |
| 网络可达性 | 国内直连 | 需代理 | DeepSeek |
| 模型可替换性 | `ChatOpenAI(base_url=...)` 切换只需改 3 行 | — | 架构层面解耦 |

### 9.2 为什么在 AgentExecutor 外增加预处理/后处理

直接使用 LangChain AgentExecutor 可以实现"输入→工具→输出"的基本流程，但实际使用中暴露出几个问题：
- **LLM 对环境无感知**——不知道当前时间、天气、工单热点 → 增加 Observe 层在对话前收集环境数据
- **LLM 容易混淆意图**——"查询我的工单"和"上报新问题"可能被误判 → 增加 Orient 层做关键词意图路由
- **LLM 可能编造结果**——描述"工单 #42 已创建"但实际未调用工具 → 增加 Reflect 层校验并补执行
- **单条数据背后的统计规律 LLM 不会主动分析** → 增加 Associate 层做 SQL + z-score 关联分析

这种结构将 LLM 的不可靠性限制在可控范围内——让 LLM 专注自然语言理解和生成，环境感知、意图判断、质量检查、统计推理由确定性代码完成。

### 9.3 为什么 Streamlit

比赛场景（单用户演示）下，Streamlit 的开发效率优势明显。内置 `st.chat_message`/`st.chat_input`、Altair 图表、session_state 状态管理、多页面导航——单人可在短时间内完成完整的交互界面。

## 十三、可迁移性：架构的场景无关设计

### 13.1 设计原则

本项目的治理工作流、工具层、数据库结构、校验机制、降级链路在设计上保持场景无关。所有场景特定内容集中在以下文件中：

| 耦合点 | 文件 | 迁移方式 |
|--------|------|----------|
| 意图关键词 | `agent/prompt.py` → `_PERSONA_SIGNALS` | 替换关键词列表 |
| 工具描述与参数 | `tools/*.py` → 16 个工具的 docstring + 回复文案 | 替换文档字符串与返回值模板 |
| System Prompt | `agent/prompt.py` → `get_system_prompt()` | 替换角色上下文段落 |
| 种子数据 | `data/seed.py` | 替换人物与场景名，保留数据规模和叙事结构 |

**工作流引擎、数据库结构、UI 组件、校验逻辑、测试体系——不需要代码改动。**

### 13.2 验证的迁移路径

校园先知以大学校园（几万人、边界清晰、问题类型全）为原型验证环境。以下是三组可行的迁移路径：

| 治理维度 | 校园 → | 社区治理 | 养老机构 | 企业园区 |
|---------|--------|---------|---------|---------|
| 知 | 校园脉搏 | 社区周报 | 老人日报 | 园区简报 |
| 报 | 随手报修 | 居民上报 | 一键求助 | 员工反馈 |
| 议 | 有话说 | 居民议事 | 银龄之声 | 员工建言 |
| 督 | 治理透明窗 | 治理公开 | 服务监督 | 运维看板 |
| 角色 | 学生/教师 | 居民/网格员 | 老人/护工 | 员工/行政 |

每组迁移的工程投入约 6-8 小时（关键词替换 + 工具文案替换 + 种子数据重写 + UI 标题替换）。核心架构完全不动。

| 特质 | 校园 | 对验证的意义 |
